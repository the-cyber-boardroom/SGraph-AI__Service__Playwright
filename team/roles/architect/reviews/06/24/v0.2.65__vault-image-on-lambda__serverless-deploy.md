# Architect Briefing — Deploying the SG/Vault image on Serverless (Lambda first)

> **Reality-doc rule applied.** Every "exists today" claim is cross-checked against the reality docs and cited source files. Everything in §4–§6 is **PROPOSED — does not exist yet.**

> **Relationship to the 2026-06-13 brief.** A prior Architect brief (`…/06/13/10/architecture__sg-api-vault__lambda-container-vs-zip.md`) covered container-vs-zip Lambda for the **Chromium SG/API image** and, in its §3.4, recommended *against* Lambda for the vault server (15-min cap + statefulness). **This brief narrows to the `sg-send-vault` image specifically and revisits that conclusion** in light of one fact the earlier brief noted but did not act on: **the vault already runs `SEND__STORAGE_MODE=memory` on Fargate** — it is *already* ephemeral-per-task. That changes the Lambda calculus for the vault in a way it does not for the stateful-disk reading of §3.4. I do not re-derive the container-vs-zip table here; I build on it.

## 1. The honest headline (read this first)

1. **"This image should already be compatible with Lambda" cannot be confirmed from this repo.** The `sg-send-vault` **Dockerfile is not in this repository** — it is built in the SG/Send product repo and consumed here only as a published image (`diniscruz/sg-send-vault:latest`, pulled by `Vault_App__Fargate__Image__Mirror`). Grep across the repo for a vault Dockerfile returns nothing. **So the compatibility question is genuinely open and must be answered against the SG/Send repo, not this one** (see §2 for the exact checklist).

2. **The vault is the *good* serverless candidate** — far better than the Chromium SG/API image the 06-13 brief studied: no browser, no 1 GB+ base, already stateless (`STORAGE_MODE=memory`), single FastAPI web surface on `:8080`. The user's instinct is right *for this image*.

3. **"Not much to do" is true for the runtime image, but false for this repo's tooling.** The single blocking gap is the same one the 06-13 brief identified: **there is no container-image Lambda deploy path in the codebase.** `Lambda__Deployer` only emits `Code={'ZipFile'|'S3…'}` — there is **no `PackageType='Image'` / `Code={'ImageUri'}` branch anywhere** (`Lambda__Deployer.py:106-114`; `verb_deploy.py` is `--code-path` folder-only). That branch is the one real piece of new code.

4. **"Where" has a clean answer:** a new `sg_compute_specs/vault_app/lambda/` sub-app **mirroring the existing `fargate/` sub-app**, reusing `Vault_App__Fargate__Spec`, `Vault_App__Fargate__Image__Mirror`, and the IAM/ECR seams; plus the image-Lambda branch added under `sg aws lambda`. No new architectural boundary is introduced.

## 2. Is the image actually Lambda-runnable? — the verification checklist

Lambda runs a container image only if the image satisfies the **Lambda Runtime API** contract. A normal web-server image does **not** by default. Two ways to satisfy it; the image must already do **one** of them, and **this is what must be checked in the SG/Send Dockerfile**:

| Path | What the image must contain | How to check (in SG/Send repo) |
|------|------------------------------|-------------------------------|
| **A — Lambda Web Adapter (LWA)** *(preferred — keeps "one image, many targets")* | `COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter … /opt/extensions/`; the app keeps running its normal uvicorn server; `AWS_LWA_PORT` set to the app's listen port. | Does the Dockerfile copy the adapter extension? Is the listen port exported as `AWS_LWA_PORT` (vault listens on **8080**)? |
| **B — Lambda Runtime Interface Client (RIC)** | An AWS base image (`public.ecr.aws/lambda/*`) **or** the `awslambdaric` entrypoint wrapping a handler. | Is the base an AWS Lambda base image, or is `aws-lambda-ric` the ENTRYPOINT? |

**If the SG/Send image has neither, it is NOT Lambda-runnable as-is** — and "not much to do" becomes "add an LWA layer to the SG/Send Dockerfile" (a one-line `COPY` + two `ENV`s), which is **work in the SG/Send repo, not this one.** That is the single most important thing to confirm before any work here.

Beyond the runtime contract, three image-level facts must hold (all plausible for this image, none verifiable here):

- **Listen port** is fixed/known (`Vault_App__Fargate__Spec.http_port = 8080`) and bindable as `AWS_LWA_PORT`.
- **Statelessness under memory mode** — `env_for_run` already forces `SEND__STORAGE_MODE=memory` (`Vault_App__Fargate__Spec.py:27`). Lambda gives only ephemeral `/tmp`; the disk-mode `/data` volume from compose has no analogue. Memory mode is the right (and already-chosen) setting. **Caveat:** memory mode means **each cold start is an empty vault** unless secrets/keys are re-seeded per invocation (they are, via env — see §4.3) and unless no cross-request persistence is expected (see Q3).
- **No TLS termination inside the container.** On Fargate the vault optionally self-terminates TLS (`SEND__TLS_ENABLED`, ACME on `:80/:443`). On Lambda, TLS is terminated by the Function URL / CloudFront — the container must be runnable **plain-HTTP on 8080** with `SEND__TLS_ENABLED` unset. (It already supports this — that is the Fargate `with_tls=False` path.)

## 4. Proposed shape — *where the code goes*

> **PROPOSED — does not exist yet.**

### 4.1 Module layout — a `lambda/` sibling to `fargate/`

```
sg_compute_specs/vault_app/
├── service/                      (existing — EC2/compose era)
├── fargate/                      (existing — VAF; the template)
│   ├── cli/  service/  schemas/  enums/  primitives/  collections/
└── lambda/                       (NEW — mirror of fargate/, fewer phases)
    ├── cli/
    │   ├── Cli__Vault_App__Lambda.py            # `sg vault-app lambda ...` group
    │   ├── Cli__Vault_App__Lambda__Setup.py     # setup/check/update/delete
    │   └── Cli__Vault_App__Lambda__Deploy.py    # deploy + url + health
    ├── service/
    │   ├── Vault_App__Lambda__Spec.py           # extends/reuses the Fargate Spec constants
    │   ├── Vault_App__Lambda__Setup.py          # ECR→IAM→LOGS→IMAGE_MIRROR→FUNCTION
    │   └── Vault_App__Lambda__Deployer.py       # create/update PackageType=Image  ← the one real new thing
    ├── schemas/  enums/  primitives/  collections/
```

**Why a vault-scoped sub-app and not just a flag on `sg aws lambda deploy`?** Because the unit of work is "stand up a *vault instance*" — ECR mirror + role + function + URL + health — exactly as `vault-app fargate` is "stand up a vault task." Putting it under `vault_app/lambda/` keeps the vault lifecycle in one place and lets it reuse the Fargate `Spec`/`Image__Mirror` directly. The low-level `sg aws lambda` verbs stay generic.

### 4.2 The one new low-level primitive — image-package deploy

Add to the generic `sg aws lambda` surface (so it is reusable beyond the vault), additively, zip-default-unchanged:

- `Enum__Lambda__Package_Type` — `ZIP` / `IMAGE` (new enum class; **no Literal**, CLAUDE.md rule 3).
- `Schema__Lambda__Deploy__Request` gains optional `package_type` + `image_uri` (both default to today's ZIP behaviour).
- `Lambda__Deployer` gains an **image branch**: `create_function(PackageType='Image', Code={'ImageUri': …})` and `update_function_code(ImageUri=…)`. The existing `_wait_for_update` / config-update logic is shared; only the `Code=` payload and the `PackageType`/`Architectures` args differ. (Documented `boto3` carve-out already covers this file.)
- `verb_deploy.py` gains `--image-uri` (mutually exclusive with `--code-path`), still mutation-gated by `SG_AWS__LAMBDA__ALLOW_MUTATIONS=1`.

`Vault_App__Lambda__Deployer` then composes this: mirror image → ECR, resolve `image_uri`, call the image branch with vault-appropriate `MemorySize`/`Timeout`/`Environment`.

### 4.3 Function configuration (vault-appropriate defaults)

```
Lambda function: sg-send-vault            (PackageType=Image, x86_64)
  ├─ MemorySize: 512–1024 MB              (matches Fargate default_cpu/default_memory; no Chromium → modest)
  ├─ Timeout:    30–60 s                  (request/response; NOT a long-lived session — see §5)
  ├─ Env:        SEND__STORAGE_MODE=memory
  │              SEND__ACCESS_TOKEN=<from CI secret / Secrets Manager, NEVER Git>
  │              SEND__SEED_VAULT_KEYS=<optional>      (reuse Vault_App__Fargate__Spec.env_for_run)
  │              (SEND__TLS_ENABLED unset — Function URL terminates TLS)
  ├─ Role:       sg-send-vault-lambda      (basic-execution logs + optional secretsmanager:GetSecretValue)
  └─ Invoke:     Lambda Function URL (AuthType=NONE) + app-layer access-token check
```

**Secrets (CLAUDE.md rules 12/13):** env-var pass-through for the short-lived `SEND__ACCESS_TOKEN` (mirrors the Fargate `env_for_run` model, values injected at deploy time from CI secrets), Secrets Manager via `osbot-aws` for anything long-lived. No keys in Git.

## 5. The architectural tension — engage it honestly

The 06-13 brief said "do **not** Lambda-host the vault server" (§3.4). That stands **for one reading of "vault instance" and not the other.** The deciding question for Dinis:

| "A vault instance" means… | Fits Lambda? | Why |
|---------------------------|--------------|-----|
| **A stateless request/response vault API** — each call carries its token, reads/writes go to a real backing store (S3/DDB) or are request-scoped; no addressable long-lived process. | **Yes.** | No 15-min cap problem (each request is short), memory mode already chosen, no Chromium. This is the *natural* Lambda shape and what makes the user's instinct correct. |
| **A long-lived, addressable vault *session*** — a human logs in, the in-memory store accumulates across requests for the life of the instance (today's Fargate "task per session" model). | **No.** | Lambda gives no sticky long-lived process; memory mode means **every cold start is an empty vault** and concurrent invocations are **separate sandboxes with separate memory**. Cross-request in-memory state silently diverges. Keep this on Fargate (VAF). |

**So the recommendation is conditional, not a flat yes/no:** Lambda is a sound *additional* target for the vault **as a stateless API** (and as a cheap, scale-to-zero dev/demo/ephemeral instance). It is **not** a replacement for the Fargate session model. The two coexist — exactly the "one image, many targets" pattern. This is consistent with §3.4 once you separate the two meanings of "instance."

## 6. Phased plan (all PROPOSED)

**Phase 0 — Verify the image (blocking, in SG/Send repo, not here).** Confirm the `sg-send-vault` Dockerfile satisfies §2 path A or B. If not, add the LWA `COPY` + `AWS_LWA_PORT=8080` there first. **No work in this repo should start until this is answered** — it determines whether "not much to do" holds.

**Phase 1 — Image-package deploy branch (this repo, generic).** `Enum__Lambda__Package_Type`, additive `Schema__Lambda__Deploy__Request` fields, the `Lambda__Deployer` image branch, `--image-uri` on `verb_deploy`. Unit-tested with injected fake client (no mocks). *This is the one piece that unblocks everything.*

**Phase 2 — `vault_app/lambda/` sub-app.** `Vault_App__Lambda__Spec` (reuse Fargate constants), `Vault_App__Lambda__Setup` (`ECR→IAM→LOGS→IMAGE_MIRROR→FUNCTION` phase loop, copied shape), `Vault_App__Lambda__Deployer` (compose mirror + image deploy + env). Mutation-gated.

**Phase 3 — Invoke surface + IAM.** `sg-send-vault-lambda` execution role (basic-execution + optional Secrets-Manager read); Function URL (AuthType=NONE) + app-layer token check; reuse the two-statement Function-URL permission fix.

**Phase 4 — CLI + health.** `sg vault-app lambda setup|deploy|url|health|delete`, reusing the generic `sg aws lambda url|invoke|logs|delete` verbs under the hood. Health check reuses the Fargate `Vault_App__Fargate__Health` against the Function URL + `/info/health`.

**Phase 5 — Deploy-via-pytest + reality/CLAUDE.md reconciliation.** Numbered deploy tests (`test_1__mirror_image`, `test_2__create_function`, `test_3__invoke__health`, …) gated on real AWS. Update `team/roles/librarian/reality/{infra,vault}/index.md`. **Also reconcile CLAUDE.md** — its stack table still lists "AWS Lambda Web Adapter 1.0.0" as if live; the 06-13 brief flagged this as stale for SG/API. This vault-Lambda work would make LWA genuinely live again *for the vault image* — note that precisely so the doc stops being ambiguous.

**Reused as-is:** `Vault_App__Fargate__Spec`, `Vault_App__Fargate__Image__Mirror`, ECR/IAM/logs service clients, `Lambda__AWS__Client` + url/invoke/logs/delete verbs, Function-URL permission fix, `Vault_App__Fargate__Health`, deploy-via-pytest harness.
**Must be built:** the image-package deploy branch (Phase 1) + the `vault_app/lambda/` sub-app (Phases 2–4). Bounded; no new boundary.

## 8. Bottom line

- **The vault image is the right serverless candidate** (no Chromium, already `STORAGE_MODE=memory`) — the user's instinct holds *for this image*, unlike the Chromium SG/API image of the 06-13 brief.
- **"Already compatible" is unproven from here** — the `sg-send-vault` Dockerfile lives in **SG/Send, not this repo**. Compatibility hinges on it carrying the Lambda Web Adapter (or a RIC). **Verify that first (Q1).**
- **Where:** a `sg_compute_specs/vault_app/lambda/` sub-app mirroring `fargate/`, reusing `Spec` + `Image__Mirror` + IAM/ECR/logs seams. **How:** the one new capability is the **image-package (`PackageType=Image`) branch** on `Lambda__Deployer` — the existing deployer is ZIP-only.
- **Scope honestly:** Lambda suits the **stateless vault API / ephemeral instance**; the **long-lived session vault stays on Fargate.** Both run the same image — "one image, many targets," now genuinely including Lambda for the vault.
