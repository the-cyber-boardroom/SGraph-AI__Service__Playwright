# Architect Plan — `sg journey`

> **PROPOSED — does not exist yet.** This document defines contracts and boundaries
> for a new top-level `sg_compute` spec. No code has been written.

A new spec that lets an operator (or an LLM) **provision an ephemeral EC2 running the
existing Playwright service + a mitmproxy sidecar, drive declarative browser *journeys*
against it, and assert on both the browser result and the captured proxy traffic** — with
or without a custom mitmproxy interceptor. A *journey* is a named, scripted browser
sequence + assertions; run one for functional QA, run a suite for regression, run many
concurrently for load. Exposed four ways: CLI, HTTP API, a Textual TUI, and LLM-chat; and
made consumable by an external LLM agent via the agentic manifest/skills surface.

---

## 1. Context & goal

The repo already contains every major piece. This spec is **composition + a thin client
layer + four front-ends**, not new browser-automation machinery.

Goal, in one sentence: *spin up a chromium+mitmproxy box, run a declarative browser journey
through it, and get back pass/fail plus the intercepted flows — repeatably, in CI, and
interactively — and replay journeys under concurrency for load.*

Three facets, one model (a journey = sequence + assertions):

- **Functional QA** — run one journey, assert on result + flows.
- **Regression / CI** — run a suite of journeys against an ephemeral stack, top-down.
- **Load** — replay journeys with a concurrency/repeat knob, fanning out across one or more
  stacks. (v1 ships the single-run path; load is a recognized later slice — see §7/§8.)

What we explicitly are **not** building (per the locked decisions in §2):

- No new CDP-connect path in `Browser__Launcher` (we drive the **remote service's HTTP
  API**, not a remote browser over CDP).
- No per-request proxy field and no hot-reload of interceptors (ephemeral stacks make both
  unnecessary for the regression/smoke goal — see §8).

## 4. Target architecture

Three layers: the **stack** (what runs on EC2), the **control plane** (the spec service +
remote clients running wherever `sg` runs), and the **surfaces** (CLI / HTTP / TUI / chat).

```
  operator / LLM
        │
   ┌────┴─────────────────────────────────────────────┐
   │  surfaces:  CLI (sg journey …)                    │
   │             HTTP (/api/specs/journey/…)            │
   │             TUI  (Journey__Screen, Textual)        │
   │             chat (Chat__Engine + journey tools)    │
   └────┬─────────────────────────────────────────────┘
        │
   ┌────┴───────────────── control plane (Journey__Service) ──────────────┐
   │  EC2 lifecycle (Spec__Service__Base / EC2__Platform)                  │
   │  Playwright__Remote__Client  ──HTTP──┐                                │
   │  Mitmproxy__Control__Client  ──HTTP──┤                                │
   │  Journey__Runner (orchestrates the two + assertions + concurrency)    │
   └──────────────────────────────────────┼───────────────────────────────┘
                                           │  (public_ip from info)
   ┌───────────────────────────────────────┴── ephemeral EC2 stack ───────┐
   │  ┌─ sg-playwright container (:8000) ─┐   ┌─ agent_mitmproxy (:8080) ─┐ │
   │  │  SG_PLAYWRIGHT__DEFAULT_PROXY_URL │──▶│  proxy + addons/active.py │ │
   │  │   = http://mitmproxy:8080         │   │  control API + /ca/cert   │ │

   │  └───────────────────────────────────┘   └───────────────────────────┘ │
   │  host-control sidecar (:19009)  ← optional pod/shell/host introspection │
   └────────────────────────────────────────────────────────────────────────┘
```

### 4.1 The stack (EC2)

A **composed** stack — the first spec that provisions *two* service containers. Both images
already exist; user-data pulls and composes them.

- **playwright container** — `diniscruz/sg-playwright:{version}`, the unmodified service.
  Env at boot:
  - `SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy:8080`
  - `SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS=true` (default; CA-trust is the hardening option in §8)
- **mitmproxy sidecar** — the `agent_mitmproxy` image from `sg_compute_specs/mitmproxy/`
  (chosen over the official `mitmproxy/mitmproxy` image used by `vnc`/`firefox` **because we
  need its control API** for smoke + flow assertions: `/ca/info`, `/config/interceptor`, `/metrics`).
- **interceptor selection** at create time:
  - none → defaults only (`default_interceptor` + `audit` + `prometheus` always loaded)
  - `--interceptor-script FILE` → custom source embedded into user-data → `active.py` (reuse
    the `*__Interceptor__Resolver` pattern)
- **host-control sidecar** — installed automatically by `Section__Sidecar` on every node.

Two launch backends (mirror the documented playwright-spec model, §2.1/2.2 of
`v0.2.11__sp-playwright-spec-design.md`):

- **EC2-node (primary, per the request):** dedicated box via `EC2__Platform`; carries the
  auto-terminate timer.
- **Pod-on-host (fast/cheap option):** both containers as pods on an existing host via the
  sidecar `/pods` API. Note for later; EC2-node ships first. (Also the natural fan-out unit
  for load — many pods/boxes, many concurrent journeys.)

### 4.2 The control plane — `Journey__Service`

`Spec__Service__Base` subclass. Standard CRUD comes from the base; the spec adds:

- `Playwright__Remote__Client` — typed HTTP client for the remote service
  (`run_one_shot`, `execute_sequence`, `screenshot`, `health`). Mirrors `Sidecar__Client`'s
  shape (`host_api_url`, `api_key`). **It is an HTTP client — it never imports Playwright and
  never touches `page.*`**, so the `Step__Executor`-only boundary is preserved by construction.
- `Mitmproxy__Control__Client` — typed HTTP client for the sidecar control API
  (`ca_info`, `interceptor_source`, `metrics`, captured-flow read).
- `Journey__Runner` — orchestrates: (1) optionally clear/baseline the proxy, (2) call
  `execute_sequence` on the remote service, (3) read flows/metrics from the control client,
  (4) evaluate assertions, (5) return a typed result. Holds an optional `concurrency`/`repeat`
  knob (load): fan N runs at the remote service and aggregate. **No `page.*`, no sink writes**
  (artefacts are written by the remote service's `Artefact__Writer`, not here).

### 4.3 Journey + assertion model (schemas)

Reuse the existing step language; wrap it with assertions.

| Schema | Purpose |
|--------|---------|
| `Schema__Journey__Definition` | `name` + an embedded `Schema__Sequence__Request` (the steps) + `List__Journey__Assertion` |
| `Schema__Journey__Assertion` | one assertion: `kind` (`Enum__Journey__Assertion__Kind`) + target + expected |
| `Enum__Journey__Assertion__Kind` | `HTTP_STATUS`, `CONTENT_CONTAINS`, `URL_EQUALS`, `FLOW_SEEN`, `FLOW_HEADER`, `FLOW_BLOCKED`, `SCREENSHOT_TAKEN` (no Literals) |
| `Schema__Journey__Result` | per-journey verdict: `passed` + `List__Journey__Assertion__Result` + timings + flow summary |
| `Schema__Journey__Assertion__Result` | per-assertion `passed` + `actual` + `message` |
| `Schema__Journey__Flow__Summary` | normalized view of mitmproxy-captured flows used by `FLOW_*` assertions |

Stack lifecycle schemas (mandated by the spec contract):
`Schema__Journey__Create__Request` (+ `interceptor_script` field),
`Schema__Journey__Create__Response`, `Schema__Journey__Info`,
`Schema__Journey__List`, `Schema__Journey__Delete__Response`.

> Naming note: the spec name `journey` describes the capability; `Create/Info/List/Delete`
> suffixes mark **stack-lifecycle** schemas, while `Definition/Result/Assertion` mark the
> **run** model. `list` (from the builder) lists *stacks*, consistent with every other spec.

All `Type_Safe`, zero raw primitives, one class per file, `Safe_*` primitives for ids/urls.

### 4.4 CLI surface

From `Spec__CLI__Builder` (free): `create`, `list`, `info`, `wait`, `health`, `connect`,
`exec`, `delete`, `ami …`, `cert …`.

Spec extras:

| Verb | Does |
|------|------|
| `sg journey create [--interceptor-script FILE] [--max-hours N]` | provision the composed stack |
| `sg journey smoke <name>` | run the deploy-via-pytest smoke checks against the live stack (§4.7 / §7) |
| `sg journey run <name> --file journey.json [--repeat N] [--concurrency C] [--json]` | run one journey (or N for load), print `Schema__Journey__Result` |
| `sg journey flows <name> [--filter …]` | dump the captured flow summary from the control client |
| `sg journey interceptor <name>` | show the active interceptor source (`/config/interceptor`) |
| `sg journey tui <name>` | launch the Textual screen bound to a stack |
| `sg journey chat <name>` | launch the chat screen (LLM drives the harness via tools) |

### 4.5 HTTP surface

`api/routes/Routes__Journey__Stack.py` (extends `Fast_API__Routes`, declares
`service: Journey__Service`) auto-mounts at `/api/specs/journey` via `Spec__Routes__Loader`.
Standard stack CRUD (`GET /stacks`, `GET /stack/{name}`, `POST /stack`, `DELETE /stack/{name}`,
`GET /stack/{name}/health`) plus:

- `POST /stack/{name}/run` → `Schema__Journey__Result`
- `GET  /stack/{name}/flows` → `Schema__Journey__Flow__Summary`
- `GET  /stack/{name}/interceptor` → interceptor source

Routes are pure delegation (no logic). Every handler returns `.json()` on a `Type_Safe`
schema.

### 4.6 TUI surface

`Journey__Screen` subclasses `Tui__App` (reusing its Header/Footer/Debug-panel chrome and
`populate()` hook). Panes: stack picker (from `list_stacks`), journey runner + live result, a
flow viewer (from the control client), and an interceptor pane. Bindings reuse the base
(`r` refresh, `d` debug, `q` quit).

### 4.7 Chat-native (both modes)

- **Human chat (TUI):** reuse `Chat__Engine` + `send_turn_agentic` (the existing tool loop).
  A `Journey__Tools` registry maps harness operations (`run_journey`, `get_flows`,
  `get_interceptor`, `health`, `screenshot`) to tools the LLM can call. Backend is the
  operator's choice (Bedrock / Ollama / OpenRouter — all already wired). The chat screen can
  embed in or sit beside `Journey__Screen`.
- **External-agent discovery:** add `skill__agent.md` describing the journey verbs +
  journey/assertion schema, and a manifest entry so an external LLM agent can discover and
  drive the `/api/specs/journey` surface. Optional MCP wrapper is a stretch (the repo has no
  MCP today) — note, don't build in v1.

## 6. Boundaries this design preserves (guard table)

| Rule | How it holds |
|------|--------------|
| `Step__Executor` is the only class touching `page.*` | The harness is a pure HTTP client; the *remote* service owns the browser. No `page.*` anywhere in `journey/`. |
| `Artefact__Writer` is the only sink writer | Artefacts (screenshots/HTML/video) are written by the remote service. The harness only reads results over HTTP. |
| `osbot-aws` only, never boto3 | `Journey__AWS__Client` + `EC2__Platform` reuse the existing AWS layer. |
| Routes have no logic | `Routes__Journey__Stack` delegates to `Journey__Service`. |
| Type_Safe / no primitives / no Literals / one-class-per-file | All schemas/enums/collections above follow the catalogue rules. |
| JS allowlist not widened | Journeys run on the remote service, which keeps its deny-all `JS__Expression__Allowlist`. The harness adds no new `evaluate` capability. |
| One image, five targets | **No image change.** The stack pulls two existing images; the spec itself is control-plane code that runs wherever `sg` runs. |

## 8. Open questions & risks

1. ~~Spec name~~ — **RESOLVED: `journey`** (2026-05-26).
2. **`agent_mitmproxy` image publish location.** The stack's user-data must `docker pull`
   the `agent_mitmproxy` image. The Playwright image is on Docker Hub; the host-control image
   is on ECR. **DevOps: confirm where `sg_compute_specs/mitmproxy/`'s image is published**
   (and that the EC2 instance-profile can pull it). If it isn't published, that's a prerequisite.
3. **CA trust vs `ignore_https_errors`.** v1 uses `SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS=true`
   (simplest; acceptable for an ephemeral test box). Hardening option: fetch `/ca/cert` from
   the sidecar at boot and install into the chromium trust store (the Firefox stack already
   does NSS import — precedent exists). Recommend shipping the env-flag path first.
4. **"With and without interceptors" = two stacks, not hot-swap.** mitmproxy hot-reload
   (`PUT /config/interceptor`) is a deferred Phase-2 of the mitmproxy spec and not built.
   For regression/CI we create one stack per interceptor config (ephemeral, cheap). Interactive
   hot-swap depends on the mitmproxy PUT endpoint landing.
5. **Composed-stack precedent.** This is the first spec to provision two service containers.
   The `Section__*` user-data modules + a docker-compose template support it, but it's worth a
   quick DevOps review of the compose path on a real instance during Slice 1.
6. **Auth between harness and remote service.** The remote Playwright service enforces an
   API key (`FAST_API__AUTH__API_KEY__VALUE`); the per-node key is in SSM (`host_api_key`).
   `Playwright__Remote__Client` must read it the same way `Sidecar__Client` / `Pod__Manager`
   do. No new secret-handling pattern.
7. **Load scaling caveat.** Real-browser load is heavy (one Chromium process per session).
   Concurrency within a stack is bounded by the box; heavier load fans out across multiple
   ephemeral stacks/pods. mitmproxy capture volume under load is also a consideration. Slice 6
   should set explicit per-stack concurrency caps and prefer fan-out for scale.
