# Architect Plan — `sg browser user-journey`

> **PROPOSED — does not exist yet.** This document re-architects the prior `journey`
> plan around a **container-driven, execution-on-EC2** model. No code has been written.

Provision an ephemeral EC2 that runs a **conductor** container + a **mitmproxy** sidecar.
The conductor runs **suites**: it fans out **worker** containers — each worker is one
browser *user-journey* (visit a site and browse N pages, open a vault and do N actions, …)
routed through mitmproxy — and aggregates their results. **Load is controlled by how many
worker containers you run; the journey is controlled by which worker image + params you
run.** All execution happens on the box. The operator's CLI only **starts/stops and
monitors**; the rich experience is **powerful, visual TUIs** (a live cockpit + an
LLM-chat cockpit) that talk to the conductor.

---

## 1. Context & goal — what changed from the prior plan

The earlier plan put the run-loop on the **CLI side** (a `Journey__Runner` calling a remote
service over HTTP). That is now **wrong**. Per the new direction:

- **Execution runs on the EC2 instance**, not on the operator's machine.
- A journey is a **container** (image + params); **N copies = N×load**. "Run it 10×" = launch
  that container ten times.
- A **conductor container** owns *suites* (which worker image, which params, how many, at
  what concurrency), fans workers out, and exposes status.
- **No real work on the CLI** — it just start/stop/monitor. The **TUIs are the product**.

Three facets, one model (a journey = a container, a suite = a set of journeys × counts):

- **Functional QA** — run one worker, assert on result + captured flows.
- **Regression / CI** — run a suite of journeys against an ephemeral stack, gate on the aggregate.
- **Load** — raise the worker count / concurrency; fan out across pods (and later, boxes).

### 4.1 Topology

```

   │  ┌─ conductor container ─────────────┐   ┌─ agent_mitmproxy ─┐  ┌─ host-plane ──┐  │
   │  │  suite API: start/stop/status     │   │  proxy :8080      │  │  :19009       │  │
```

### 4.2 The worker container (one journey execution)

- **Image:** `diniscruz/sg-playwright:{version}` (the existing image — no new build).
- **Command (overridden at `docker run`):** `python -m sg_compute_specs.playwright.core.journey.worker`
  — a **new module added to the playwright spec** (ships in the image). It calls
  `Playwright__Service.execute_sequence()` **in-process**, so `Step__Executor` remains the
  only `page.*` caller (boundary preserved by construction).
- **Config via env** (the only knob the launcher has, plus command): proxy URL
  (`SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy:8080`), `IGNORE_HTTPS_ERRORS`, the
  journey reference (a small inline `Schema__Journey__Definition` JSON, **or** a
  `conductor_url + journey_id` the worker fetches — large defs go by reference), a
  `replica_index`, and a `conductor_callback_url + token`.
- **Reporting:** on completion the worker **POSTs `Schema__Journey__Result`** to the
  conductor and exits. Artefacts (screenshots/HTML) go to S3 via the existing
  `Artefact__Writer` sink (instance-profile creds) and are referenced by URL in the result.
- **Custom journeys** (e.g. vault actions richer than the 16-step language) are just a
  **different worker image** — the platform is journey-agnostic; it runs containers and
  aggregates. The `sg-playwright` worker covers the declarative common case.

### 4.3 The conductor container (the brain)

- **A new image** in this spec. Mounts `/var/run/docker.sock` (same accepted pattern as the
  host-plane sidecar; **no `--privileged`**). 
- **Owns suites.** A `Schema__Suite__Definition` is a list of `Schema__Suite__Entry`
  (`worker_image`, `env`/params, `count`, `concurrency`). On `start`, the conductor launches
  `count` workers per entry in waves of `concurrency` (concurrency is conductor-managed since
  the pod schema has no cgroup limits — see §6), labelling each container for tracking, on
  the shared stack network so `mitmproxy` resolves.
- **Aggregates.** Collects worker `POST`ed results, pulls flow/metric summaries from the
  `agent_mitmproxy` control API, and computes the suite verdict + latency percentiles.
- **Exposes a suite/status API** (FastAPI, `Type_Safe` schemas) for the TUIs and the
  control-plane: `POST /suites` (start), `POST /suites/{id}/stop`, `GET /suites/{id}`
  (status + per-worker grid), `GET /suites/{id}/results`, `GET /flows`. API-key auth like
  the host-plane sidecar (per-node key from SSM).

### 4.4 Two API layers (don't conflate them)

| Layer | Where it runs | Owns | Consumed by |
|-------|---------------|------|-------------|
| **Control-plane spec API** `/api/specs/user-journey` | wherever `sg` runs | **Stack** lifecycle: create/info/list/delete | `sg` CLI provisioning, dashboard |
| **Conductor API** (on the EC2) | the conductor container | **Suite** lifecycle + monitoring + fan-out | the TUIs + chat (directly, via `public_ip`+key), and optionally proxied by a couple of control-plane convenience routes |

This split is what keeps "no work on the CLI" honest: provisioning is control-plane;
execution + monitoring is the conductor; the CLI is a thin remote to both.

### 4.5 Schemas (Type_Safe, one class per file)

| Schema | Purpose |
|--------|---------|
| `Schema__Suite__Definition` | a suite: `name` + `List__Suite__Entry` + optional global tags |
| `Schema__Suite__Entry` | `worker_image` + `env` (params) + `count` + `concurrency` + optional per-replica overrides |
| `Schema__Suite__Run__Status` | suite state: counts (pending/running/passed/failed) + `List__Worker__Status` + aggregates (latency p50/p95, flow summary) |
| `Schema__Worker__Status` | one worker: container id/label, state, started/finished, exit, result ref |
| `Schema__Journey__Definition` | a declarative journey: embedded `Schema__Sequence__Request` (steps) + `List__Journey__Assertion` |
| `Schema__Journey__Assertion` / `Enum__Journey__Assertion__Kind` | one assertion; kinds `HTTP_STATUS`, `CONTENT_CONTAINS`, `URL_EQUALS`, `FLOW_SEEN`, `FLOW_HEADER`, `FLOW_BLOCKED`, `SCREENSHOT_TAKEN` (no Literals) |
| `Schema__Journey__Result` | per-worker verdict: `passed` + `List__Journey__Assertion__Result` + timings + artefact refs + flow summary |
| `Schema__Journey__Flow__Summary` | normalized mitmproxy flow view for `FLOW_*` assertions |
| `Schema__User_Journey__{Create__Request,Create__Response,Info,List,Delete__Response}` | **stack** lifecycle (mandated by the spec contract); create takes `--interceptor-script` |

### 4.6 CLI surface (deliberately thin)

`sg browser user-journey …` — stack lifecycle from `Spec__CLI__Builder`
(`create/list/info/wait/health/connect/exec/delete`) plus a few passthroughs:

| Verb | Does |
|------|------|
| `create [--interceptor-script FILE] [--max-hours N]` | provision the conductor+mitmproxy stack |
| `suite start <stack> --file suite.json` | POST the suite to the conductor (thin passthrough) |
| `suite stop <stack> [--id ID]` | tell the conductor to stop |
| `status <stack> [--id ID] [--json]` | one-shot conductor status (for scripts/CI) |
| `flows <stack>` | dump the flow summary |
| `tui <stack>` | **launch the cockpit** (the main interface) |
| `chat <stack>` | **launch the chat cockpit** |

CI uses `create` → `suite start --file regression.json` → poll `status --json` → gate →
`delete`. No orchestration logic in the CLI.

### 4.7 The cockpit TUI (the product)

`User_Journey__Cockpit__Screen` (subclasses `Tui__App`). Talks to the conductor API +
mitmproxy control API. Panes:

- **Suite/worker grid** — one cell per worker (state, progress, exit), updating live; raise
  `count` and watch the grid grow (load made visible).
- **Aggregates** — pass/fail counts, latency percentiles, throughput.
- **Live flow feed** — intercepted requests from `agent_mitmproxy` (the with/without-interceptor signal).
- **Drill-down** — per-worker logs (`host-plane /pods/{}/logs` or conductor proxy), result, screenshot refs.
- **Interceptor pane** — active interceptor source.

### 4.8 Chat-native (both)

- **Chat cockpit (TUI):** reuse `Chat__Engine` + `send_turn_agentic`. A `User_Journey__Tools`
  registry exposes conductor ops as LLM tools (`start_suite`, `scale_suite`, `get_status`,
  `get_flows`, `stop_suite`). "Run the checkout journey 50× and tell me the p95" becomes a
  tool sequence. Backend is operator's choice (Bedrock/Ollama/OpenRouter — already wired).
- **External-agent discovery:** the conductor exposes a manifest + `skill__agent.md`
  describing suites/journeys so an external LLM agent can drive it over HTTP. Optional MCP
  wrapper noted as a stretch (no MCP in the repo today) — not v1.

### 4.9 Placement — `sg browser` group

- New thin aggregator `sg_compute/cli/Cli__Browser.py` (a Typer that `add_typer`s browser
  sub-tools). `Cli__SG.py` gains one line: `app.add_typer(browser_app, name='browser')`.
- This spec registers under it as `user-journey` → `sg browser user-journey …`.
- `manifest.nav_group = BROWSERS` (enum value already exists).
- **Migrating `vnc`/`firefox`/`neko`/`playwright` under `sg browser` is explicitly out of
  scope here** — a later, separate ontology slice (and it touches the Librarian's ontology
  proposal — see §6).

## 6. Constraints discovered + required follow-ups

1. **Pod-start schema is minimal** (`{name, image, ports, env, type_id}`; no command/volume/
   limit override). → Conductor uses the **Docker socket** for full control. Optional
   follow-up with the host-plane owners: extend `Schema__Pod__Start__Request` with
   command/args + resource limits so `/pods` becomes a viable fan-out path too.
2. **No cgroup limits at launch** → per-worker CPU/mem isolation relies on the box + the
   conductor's concurrency cap. Set conservative concurrency defaults; prefer fan-out over
   piling sessions on one box (real Chromium is heavy).
3. **Registry auth** — the worker image is public Docker Hub (`sg-playwright`), so no auth
   needed. A custom/private worker image would need ECR + instance-profile auth.
4. **`agent_mitmproxy` publish location** — confirm where `sg_compute_specs/mitmproxy/`'s
   image is published and that the instance profile can pull it (carried over open item).
5. **CA trust vs `ignore_https_errors`** — v1 uses `IGNORE_HTTPS_ERRORS=true` per worker;
   CA-into-trust-store is the hardening path (Firefox NSS import is precedent).
6. **Ontology tension (Librarian).** The ontology proposal
   (`team/roles/librarian/reviews/05/17/v0.2.25__ontology-and-taxonomy-proposal.md`)
   currently **opposes grouping specs under CLI super-categories**, while a `BROWSERS`
   **nav-group** already exists for the dashboard. Introducing `sg browser` is a deliberate
   step toward category grouping — **needs Librarian + human ratification**. Recommendation:
   ship the group with `user-journey` only (lowest blast radius); defer migrating existing
   specs.

## 7. Boundaries this design preserves (guard table)

| Rule | How it holds |
|------|--------------|
| `Step__Executor` only touches `page.*` | Only the **worker** runs browser code, and it does so via `Playwright__Service.execute_sequence()` → `Step__Executor`. Conductor, clients, CLI, TUIs are pure HTTP/orchestration — no `page.*`. |
| `Artefact__Writer` only sink writer | Artefacts written by the reused service core inside the worker; conductor only references them. |
| `osbot-aws` only, never boto3 | `User_Journey__AWS__Client` + `EC2__Platform`. |
| Routes have no logic | `Routes__User_Journey__Stack` and the conductor routes delegate to services. |
| Type_Safe / no primitives / no Literals / one-class-per-file | All schemas/enums/collections above. |
| JS allowlist not widened | Workers reuse the service's deny-all `JS__Expression__Allowlist`. |
| One image, five targets | Worker reuses the existing image (default CMD intact). The **conductor is a new image** — assess it like host-control: small Alpine+uvicorn, ECR-published, EC2-only (not a Lambda/5-target artefact). |

## 9. Open questions & risks

1. **Confirm Slice-5/6 picks (§2 rows 5–6)** — worker = reused `sg-playwright` image with
   command override (vs a dedicated slim image), and conductor = dedicated container (vs
   extending the host-plane sidecar). These came back recommended-by-research after the
   question result was lost to a tool error; flag if you'd prefer the alternatives.
2. **`sg browser` grouping** needs Librarian + human ratification (ontology tension, §6).
3. **Conductor as a new image** = a new CI build + ECR repo + EC2-only artefact. DevOps to
   confirm the build/publish path (mirror the host-control image flow).
4. **Worker module in the playwright image** is a cross-spec change to a STABLE spec — Dev +
   Architect sign-off on touching the playwright image (default CMD stays intact).
5. **Docker-socket access in the conductor** — root-equivalent host control. Accepted pattern
   (host-plane does it, no `--privileged`), but call it out in the security review.
6. **Result/artefact transport** — workers POST results to the conductor; artefacts to S3 via
   the existing sink. Confirm worker containers get instance-profile creds (IMDS reachable) or
   route artefacts through the conductor.
