# Architect Plan — `sg browser-test`

> **PROPOSED — does not exist yet.** This document defines contracts and boundaries
> for a new top-level `sg_compute` spec. No code has been written. Naming
> (`browser-test`) is provisional — see §8.

A new spec that lets an operator (or an LLM) **provision an ephemeral EC2 running the
existing Playwright service + a mitmproxy sidecar, drive browser-automation scenarios
against it, and assert on both the browser result and the captured proxy traffic** —
with or without a custom mitmproxy interceptor. Exposed three ways: CLI, HTTP API, and a
Textual TUI; and made consumable by an external LLM agent via the agentic
manifest/skills surface.

---

## 1. Context & goal

The repo already contains every major piece. This spec is **composition + a thin client
layer + three front-ends**, not new browser-automation machinery.

Goal, in one sentence: *spin up a chromium+mitmproxy box, run a declarative browser
scenario through it, and get back a pass/fail plus the intercepted flows — repeatably, in
CI, and interactively.*

What we explicitly are **not** building (per the locked decisions in §2):

- No new CDP-connect path in `Browser__Launcher` (we drive the **remote service's HTTP
  API**, not a remote browser over CDP).
- No per-request proxy field and no hot-reload of interceptors (ephemeral stacks make both
  unnecessary for the regression/smoke goal — see §8 risks).

---

## 2. Decisions locked (from human, 2026-05-26)

| # | Question | Decision | Consequence |
|---|----------|----------|-------------|
| 1 | How to drive the browser? | **Remote Playwright service** | Harness is an HTTP client of the remote `sg-playwright` service. Browser routes through the mitmproxy sidecar via the service's boot-time proxy env. `Browser__Launcher` is untouched. |
| 2 | What does "test … with/without interceptors" mean? | **Regression/CI + stack smoke/health** | Two surfaces: (a) a `smoke` verb that checks a live stack is healthy + proxying + CA-trusted; (b) numbered deploy-via-pytest scenarios run against ephemeral stacks. *Not* interactive diffing, *not* a live-flow exploration tool (those are possible later but out of scope). |
| 3 | Where does it live? | **New `sg_compute` spec** | Follows the spec-authoring contract: `manifest.py` + `schemas/` + `service/` + `api/routes/Routes__Browser_Test__Stack.py` + `cli/Cli__Browser_Test.py` via `Spec__CLI__Builder`. Auto-mounts at `/api/specs/browser-test`. |
| 4 | What does "LLM chat native" mean? | **Both** | A Textual chat screen where the LLM drives the harness via tools (reusing `Chat__Engine` + `send_turn_agentic`), **and** an agentic skills/manifest surface so an external LLM agent can drive it over HTTP. |

## 4. Target architecture

Three layers: the **stack** (what runs on EC2), the **control plane** (the spec service +
remote clients running wherever `sg` runs), and the **surfaces** (CLI / HTTP / TUI / chat).

```
  operator / LLM
        │
   ┌────┴─────────────────────────────────────────────┐
   │  surfaces:  CLI (sg browser-test …)               │
   │             HTTP (/api/specs/browser-test/…)       │
   │             TUI  (Browser_Test__Screen, Textual)   │
   │             chat (Chat__Engine + harness tools)    │
   └────┬─────────────────────────────────────────────┘
        │
   ┌────┴───────────────── control plane (Browser_Test__Service) ─────────┐
   │  EC2 lifecycle (Spec__Service__Base / EC2__Platform)                  │
   │  Playwright__Remote__Client  ──HTTP──┐                                │
   │  Mitmproxy__Control__Client  ──HTTP──┤                                │
   │  Scenario__Runner (orchestrates the two + assertions)                 │
   └──────────────────────────────────────┼───────────────────────────────┘
                                           │  (public_ip from info)
   ┌───────────────────────────────────────┴── ephemeral EC2 stack ───────┐
   │  ┌─ sg-playwright container (:8000) ─┐   ┌─ agent_mitmproxy (:8080) ─┐ │
   │  │  SG_PLAYWRIGHT__DEFAULT_PROXY_URL │──▶│  proxy + addons/active.py │ │
   │  │   = http://mitmproxy:8080         │   │  control API + /ca/cert   │ │
   │  │  IGNORE_HTTPS_ERRORS=true (or CA) │   │  mitmweb :8081            │ │
   │  └───────────────────────────────────┘   └───────────────────────────┘ │
   │  host-control sidecar (:19009)  ← optional pod/shell/host introspection │
   └────────────────────────────────────────────────────────────────────────┘
```

### 4.1 The stack (EC2)

A **composed** stack — the first spec that provisions *two* service containers. Both images
already exist; user-data pulls and composes them.

- **playwright container** — `diniscruz/sg-playwright:{version}`, the unmodified service.
  Env at boot:
  - `SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy:8080`
  - `SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS=true` (default; CA-trust is the hardening option in §8)
- **mitmproxy sidecar** — the `agent_mitmproxy` image from `sg_compute_specs/mitmproxy/`
  (chosen over the official `mitmproxy/mitmproxy` image used by `vnc`/`firefox` **because we
  need its control API** for smoke assertions: `/ca/info`, `/config/interceptor`, `/metrics`).
- **interceptor selection** at create time:
  - none → defaults only (`default_interceptor` + `audit` + `prometheus` always loaded)
  - `--interceptor-script FILE` → custom source embedded into user-data → `active.py` (reuse
    the `*__Interceptor__Resolver` pattern)
- **host-control sidecar** — installed automatically by `Section__Sidecar` on every node.

Two launch backends (mirror the documented playwright-spec model, §2.1/2.2 of
`v0.2.11__sp-playwright-spec-design.md`):

- **EC2-node (primary, per the request):** dedicated box via `EC2__Platform`; carries the
  auto-terminate timer.
- **Pod-on-host (fast/cheap option):** both containers as pods on an existing host via the
  sidecar `/pods` API. Note for later; EC2-node ships first.

### 4.2 The control plane — `Browser_Test__Service`

`Spec__Service__Base` subclass. Standard CRUD comes from the base; the spec adds:

- `Playwright__Remote__Client` — typed HTTP client for the remote service
  (`run_one_shot`, `execute_sequence`, `screenshot`, `health`). Mirrors `Sidecar__Client`'s
  shape (`host_api_url`, `api_key`). **It is an HTTP client — it never imports Playwright and
  never touches `page.*`**, so the `Step__Executor`-only boundary is preserved by construction.
- `Mitmproxy__Control__Client` — typed HTTP client for the sidecar control API
  (`ca_info`, `interceptor_source`, `metrics`, captured-flow read).
- `Scenario__Runner` — orchestrates: (1) optionally clear/baseline the proxy, (2) call
  `execute_sequence` on the remote service, (3) read flows/metrics from the control client,
  (4) evaluate assertions, (5) return a typed result. **No `page.*`, no sink writes** (artefacts
  are written by the remote service's `Artefact__Writer`, not here).

### 4.3 Scenario + assertion model (schemas)

Reuse the existing step language; wrap it with assertions.

| Schema | Purpose |
|--------|---------|
| `Schema__Browser_Test__Scenario` | `name` + an embedded `Schema__Sequence__Request` (the steps) + `List__Browser_Test__Assertion` |
| `Schema__Browser_Test__Assertion` | one assertion: `kind` (`Enum__Assertion__Kind`) + target + expected |
| `Enum__Assertion__Kind` | `HTTP_STATUS`, `CONTENT_CONTAINS`, `URL_EQUALS`, `FLOW_SEEN`, `FLOW_HEADER`, `FLOW_BLOCKED`, `SCREENSHOT_TAKEN` (no Literals) |
| `Schema__Browser_Test__Result` | per-scenario verdict: `passed` + `List__Assertion__Result` + timings + flow summary |
| `Schema__Assertion__Result` | per-assertion `passed` + `actual` + `message` |
| `Schema__Flow__Summary` | normalized view of mitmproxy-captured flows used by `FLOW_*` assertions |

Stack lifecycle schemas (mandated by the spec contract):
`Schema__Browser_Test__Create__Request` (+ `interceptor_script` field),
`Schema__Browser_Test__Create__Response`, `Schema__Browser_Test__Info`,
`Schema__Browser_Test__List`, `Schema__Browser_Test__Delete__Response`.

All `Type_Safe`, zero raw primitives, one class per file, `Safe_*` primitives for ids/urls.

### 4.4 CLI surface

From `Spec__CLI__Builder` (free): `create`, `list`, `info`, `wait`, `health`, `connect`,
`exec`, `delete`, `ami …`, `cert …`.

Spec extras:

| Verb | Does |
|------|------|
| `sg browser-test create [--interceptor-script FILE] [--max-hours N]` | provision the composed stack |
| `sg browser-test smoke <name>` | run the deploy-via-pytest smoke checks against the live stack (see §4.7 / §7) |
| `sg browser-test scenario <name> --file scenario.json [--json]` | run one scenario, print the `Schema__Browser_Test__Result` |
| `sg browser-test flows <name> [--filter …]` | dump the captured flow summary from the control client |
| `sg browser-test interceptor <name>` | show the active interceptor source (`/config/interceptor`) |
| `sg browser-test tui <name>` | launch the Textual screen bound to a stack |
| `sg browser-test chat <name>` | launch the chat screen (LLM drives the harness via tools) |

### 4.5 HTTP surface

`api/routes/Routes__Browser_Test__Stack.py` (extends `Fast_API__Routes`, declares
`service: Browser_Test__Service`) auto-mounts at `/api/specs/browser-test` via
`Spec__Routes__Loader`. Standard stack CRUD (`GET /stacks`, `GET /stack/{name}`,
`POST /stack`, `DELETE /stack/{name}`, `GET /stack/{name}/health`) plus:

- `POST /stack/{name}/scenario` → `Schema__Browser_Test__Result`
- `GET  /stack/{name}/flows` → `Schema__Flow__Summary`
- `GET  /stack/{name}/interceptor` → interceptor source

Routes are pure delegation (no logic). Every handler returns `.json()` on a `Type_Safe`
schema.

### 4.6 TUI surface

`Browser_Test__Screen` subclasses `Tui__App` (reusing its Header/Footer/Debug-panel chrome
and `populate()` hook). Panes: stack picker (from `list_stacks`), scenario runner + live
result, a flow viewer (from the control client), and an interceptor pane. Bindings reuse the
base (`r` refresh, `d` debug, `q` quit).

### 4.7 Chat-native (both modes)

- **Human chat (TUI):** reuse `Chat__Engine` + `send_turn_agentic` (the existing tool loop).
  A `Browser_Test__Tools` registry maps harness operations
  (`run_scenario`, `get_flows`, `get_interceptor`, `health`, `screenshot`) to tools the LLM
  can call. Backend is the operator's choice (Bedrock / Ollama / OpenRouter — all already
  wired). The chat screen can embed in or sit beside `Browser_Test__Screen`.
- **External-agent discovery:** add `skill__agent.md` describing the harness verbs +
  scenario/assertion schema, and a manifest entry so an external LLM agent can discover and
  drive the `/api/specs/browser-test` surface. Optional MCP wrapper is a stretch (the repo
  has no MCP today) — note, don't build in v1.

## 6. Boundaries this design preserves (guard table)

| Rule | How it holds |
|------|--------------|
| `Step__Executor` is the only class touching `page.*` | The harness is a pure HTTP client; the *remote* service owns the browser. No `page.*` anywhere in `browser_test/`. |
| `Artefact__Writer` is the only sink writer | Artefacts (screenshots/HTML/video) are written by the remote service. The harness only reads results over HTTP. |
| `osbot-aws` only, never boto3 | `Browser_Test__AWS__Client` + `EC2__Platform` reuse the existing AWS layer. |
| Routes have no logic | `Routes__Browser_Test__Stack` delegates to `Browser_Test__Service`. |
| Type_Safe / no primitives / no Literals / one-class-per-file | All schemas/enums/collections above follow the catalogue rules. |
| JS allowlist not widened | Scenarios run on the remote service, which keeps its deny-all `JS__Expression__Allowlist`. The harness adds no new `evaluate` capability. |
| One image, five targets | **No image change.** The stack pulls two existing images; the spec itself is control-plane code that runs wherever `sg` runs. |

## 8. Open questions & risks

1. **Spec name.** `browser-test` is provisional. Alternatives: `pw-mitm`, `intercept`,
   `browser-harness`. Cheap to change before Slice 0 — needs a one-word ratification.
2. **`agent_mitmproxy` image publish location.** The stack's user-data must `docker pull`
   the `agent_mitmproxy` image. The Playwright image is on Docker Hub; the host-control image
   is on ECR. **DevOps: confirm where `sg_compute_specs/mitmproxy/`'s image is published**
   (and that EC2 instance-profile can pull it). If it isn't published, that's a prerequisite.
3. **CA trust vs `ignore_https_errors`.** v1 uses `SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS=true`
   (simplest; acceptable for an ephemeral test box). Hardening option: fetch `/ca/cert` from
   the sidecar at boot and install into the chromium trust store (the Firefox stack already
   does NSS import — precedent exists). Recommend shipping the env-flag path first.
4. **"With and without interceptors" = two stacks, not hot-swap.** mitmproxy hot-reload
   (`PUT /config/interceptor`) is a deferred Phase-2 of the mitmproxy spec and not built.
   For regression/CI we create one stack per interceptor config (ephemeral, cheap). If
   interactive hot-swap is later wanted, it depends on the mitmproxy PUT endpoint landing.
5. **Composed-stack precedent.** This is the first spec to provision two service containers.
   The `Section__*` user-data modules + a docker-compose template support it, but it's worth a
   quick DevOps review of the compose path on a real instance during Slice 1.
6. **Auth between harness and remote service.** The remote Playwright service enforces an
   API key (`FAST_API__AUTH__API_KEY__VALUE`); the per-node key is in SSM (`host_api_key`).
   `Playwright__Remote__Client` must read it the same way `Sidecar__Client` / `Pod__Manager`
   do. No new secret-handling pattern.
