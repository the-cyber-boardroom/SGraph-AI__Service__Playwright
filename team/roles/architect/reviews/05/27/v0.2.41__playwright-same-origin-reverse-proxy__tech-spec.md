# Architect Tech Spec — Config-driven same-origin reverse proxy

> **PROPOSED — does not exist yet.** Nothing in this document is implemented. The
> file names under §3 are a proposed layout, not a reality-doc claim.

**Trigger:** A live `sg va create --with-playwright --wait` stack exposes the vault on
`https://<ip>` (TLS-terminated by `sg-send-vault` itself) and the Playwright service on
`http://<ip>` (plain HTTP, host `:80` → container `:8000`). A script running **inside the
vault's browser page** cannot call the Playwright API: an `https://` page issuing
`fetch('http://<ip>/...')` is blocked by the browser as **mixed content**. The vault must
stay HTTPS (Web Crypto / secure-context dependency — see the TLS options parent doc).

This is a *good failure*: it surfaced a real architectural gap — we have two first-class
HTTP surfaces on one host at two schemes, and the browser security model won't let them
talk.

---

## 1. The problem, precisely

```
Browser page origin : https://<ip>          (sg-send-vault, :443, TLS self/LE)
Wants to call        : http://<ip>/...       (sg-playwright,  host :80 → :8000)
Browser verdict      : blocked — mixed active content (HTTPS page → HTTP fetch)
```

Constraints that rule options in/out:

- The vault **must** be HTTPS (secure-context requirement). Not negotiable.
- The Claude sandbox egress allows **only `:80` / `:443`** (see the compose comment at
  `sg_compute_specs/vault_app/service/Vault_App__Compose__Template.py:100`). Any new HTTPS
  port (`:8443`) is unreachable from the sandbox, though reachable from a normal browser.
- We want **no new container** (rules out a dedicated Caddy/nginx gateway).

---

## 2. Decision — Option A (same-origin path proxy on the TLS terminator)

Mount a reverse-proxy router on the FastAPI app that already terminates TLS on `:443`, so
that `https://<ip>/pw/{path}` forwards internally to `http://sg-playwright:8000/{path}`
over the `vault-net` bridge.

Because the proxied path is **same-origin** with the vault page:

- no mixed-content block;
- no CORS (no preflight, no `Access-Control-*` wiring);
- it rides the existing vault `X-API-Key` middleware → one auth gate;
- it stays on `:443` → satisfies the sandbox egress rule.

Generalised per the request: the docker host supplies a list of `prefix → upstream`
mappings via **one env var**; the app mounts one proxy router per entry at boot. Adding a
new internal surface to the public origin becomes a config change, not a code change.

### 2.1 Options considered and rejected

| Option | Verdict | Why |
|--------|---------|-----|
| **A — path proxy on the TLS app** | **CHOSEN** | Same-origin, no CORS, no new container, `:443` only. |
| B — sg-playwright self-terminates TLS on `:8443` | Fallback | In-repo, reuses the cert-init cert, but: needs CORS, `:8443` blocked from the sandbox, self-signed cross-origin cert trust is fragile. |
| C — dedicated Caddy/nginx gateway on `:443` | Rejected | Adds a container (explicitly out of scope). Pattern already proven by the `vnc` spec's `Vnc__Caddy__Template`. |
| D — SSM tunnel to `http://localhost:PORT` | N/A | Only works for non-browser callers; the caller here is in-page. |
| E — flip: playwright owns `:443`, proxies vault | Rejected | Inverts the product hierarchy. |
| via `host-plane` (already running) | Rejected | `host-plane` mounts the docker socket — must never be the public front door. |

### 2.2 How A lands — A1 (upstream PR) vs A2 (runtime injection)

The proxy must mount on the app that binds `:443` — that is `sg-send-vault`, built from the
separate `SGraph-AI__App__Send` repo (server in `sgraph_ai_app_send__docker/`, pure
`osbot-fast-api-serverless`, no `sg_compute` dependency). Two ways to get our mount in:

- **A1 — upstream PR** to the Send repo: add the proxy + a two-line mount in
  `Fast_API__SGraph__Send__Container.setup_routes()`, rebuild `diniscruz/sg-send-vault`. The
  durable fix. See the companion handover brief.
- **A2 — runtime injection (BUILT, v0.2.41)**: we control the launch, so we **bind-mount a
  `sg_overrides` package** into the container and **override its `command`** to our own
  entrypoint that wraps the stock boot — `create_app()` (their app, untouched) → mount the
  proxy → their `Fast_API__TLS__Launcher.serve()`. **Zero edits to the image; no rebuild.**
  The only coupling is two import names (`create_app`, `Fast_API__TLS__Launcher`), which fail
  loud at boot if the image ever renames them. This is the **chosen v1 path** and the first
  case study of a reusable "runtime injection" pattern — fast to ship, testable on live EC2
  via SSM, and it converges with A1 (same `Fast_API__Reverse_Proxy` source feeds both).

#### A2 — implemented surface (this repo, branch `claude/cool-bell-GLbss`)

| File | Role |
|------|------|
| `sg_compute/fast_api/reverse_proxy/Fast_API__Reverse_Proxy.py` | Shared, testable, dependency-light proxy (fastapi + httpx + osbot_utils). Generalises `Routes__Web`. Self-contained — no `sg_compute` imports — so it can be shipped into a container we don't build. |
| `sg_compute_specs/vault_app/service/Vault_App__Reverse_Proxy__Override.py` | Assembles the three override files (`__init__.py`, the shipped proxy source read via `find_spec`, and `serve_with_proxy.py`) into a heredoc write-block. |
| `Vault_App__Compose__Template.py` | When `with_playwright`: adds `command:` override, the `/opt/vault-app/overrides:/app/sg_overrides:ro` mount, and `FAST_API__REVERSE_PROXY__ROUTES: "pw=http://sg-playwright:8000"`. |
| `Vault_App__User_Data__Builder.py` | Writes the overrides to `/opt/vault-app/overrides` **before** `compose up`. |

**Auth translation:** inbound `x-sgraph-access-token` (vault) is stripped; `X-API-Key` is
injected from `SGRAPH_SEND__ACCESS_TOKEN` for the upstream. Same token value, so the browser
script sends nothing special.

**Live test via SSM (no rebuild, reversible)** — for an instance launched *before* this code:
SSM-write the three files to `/opt/vault-app/overrides/`, patch the `sg-send-vault` service
in `/opt/vault-app/docker-compose.yml` (add the mount + `command` + env), then
`docker compose -f /opt/vault-app/docker-compose.yml up -d sg-send-vault` (recreates that one
container, ~seconds; revert by restoring the compose). No true hot-patch of a running
uvicorn — it is a container recreate.

## 3. Design

### 3.1 Where the generic mechanism lives — `sg_compute/fast_api/reverse_proxy/`

The reusable piece belongs in the **shared FastAPI infra layer in this repo**, next to its
sibling `Fast_API__TLS__Launcher` (`sg_compute/fast_api/Fast_API__TLS__Launcher.py`). It
mirrors that launcher's `config_from_env()` → Type_Safe schema → act-on-app shape.

| Proposed file | Class | Role |
|---------------|-------|------|
| `reverse_proxy/Schema__Reverse_Proxy__Route.py` | `Schema__Reverse_Proxy__Route` | `prefix`, `upstream`, `strip_prefix: bool`, `forward_auth: bool` |
| `reverse_proxy/List__Reverse_Proxy__Route.py` | `List__Reverse_Proxy__Route` | typed collection |
| `reverse_proxy/Schema__Reverse_Proxy__Config.py` | `Schema__Reverse_Proxy__Config` | `enabled: bool`, `routes`, `timeout_sec` |
| `reverse_proxy/Fast_API__Reverse_Proxy.py` | `Fast_API__Reverse_Proxy` | `config_from_env()`, `assert_ready()`, `mount(app)` |

Conventions (per Architect quality gates): all `Type_Safe`; one class per file; `Safe_*`
primitives (`Safe_Str__*` for prefix, `Safe_Str__Url` for upstream, `Safe_Int__*` for
timeout) — **no raw primitives**; `Enum__*` for any fixed-value set — **no Literals**.

The forwarding logic is a near-verbatim generalisation of the **already-proven**
`sg_compute_specs/mitmproxy/api/routes/Routes__Web.py` (httpx async client, `ALL_METHODS`,
hop-by-hop header stripping). The single behavioural change: `Routes__Web` *strips*
`X-API-Key` before forwarding (mitmweb is internally unauthenticated); our version makes
that a per-route `forward_auth` flag.

A reverse proxy returns a raw `Response`, not `.json()` on a Type_Safe schema — this is the
same accepted exception already used by `Routes__Web` and `/browser/screenshot`.

### 3.2 The env var (the config value)

Recommended grammar — comma-separated `prefix=upstream_base_url`:

```
FAST_API__REVERSE_PROXY__ROUTES = "pw=http://sg-playwright:8000"
# multiple:
FAST_API__REVERSE_PROXY__ROUTES = "pw=http://sg-playwright:8000,mitm=http://agent-mitmproxy:8081"
```

**Push-back on literal `path:port`:** on a docker network you need scheme + service-name +
port (`http://sg-playwright:8000`), and a full base URL future-proofs proxying to `https`
or non-bridge hosts. Parsing lives in `config_from_env()`, exactly mirroring
`Fast_API__TLS__Launcher.config_from_env()` reading `FAST_API__TLS__*`.

### 3.3 Mount point — THE CROSS-REPO SEAM

> **Open blocker.** The `sg-send-vault` *application* source is **not in this working
> tree.** This repo carries the vault-app *spec* (`sg_compute_specs/vault_app/` — compose
> template, AWS client, CLI, user-data) and references the prebuilt `diniscruz/sg-send-vault`
> Docker Hub image. Grepping for `Fast_API__Send` / `sg_send` / `SEND__STORAGE_MODE` app
> code returns nothing here.

The app bound to `:443` must call `Fast_API__Reverse_Proxy().mount(self.app())` in its
`setup_routes()`, **after** its own routes and **inside** the auth middleware. If the vault
is built on osbot-fast-api (it uses `FAST_API__AUTH__API_KEY__*` and `FAST_API__TLS__*`, so
almost certainly yes) this is a one-line addition plus a dependency on the `sg_compute`
package. **This single line + the env var + an image rebuild are the only changes outside
this repo.** We need to locate that composition root before Dev starts.

## 4. Side effects — ranked by likelihood of surprise

1. **Sub-path / base-href (the issue already flagged).** Apps that assume they are served
   from `/` emit absolute asset/API URLs (`/static/...`, `/openapi.json`) that 404 under
   `/pw/`. **Clean fix for our own upstreams (playwright is ours): set the upstream app's
   `root_path` (Starlette/FastAPI) or have the proxy send `X-Forwarded-Prefix: /pw`** —
   Starlette honours it and the app generates correct prefixed URLs. Third-party UIs
   (mitmweb) won't honour it and need real body rewriting or a dedicated subdomain — do not
   proxy those the same way.
2. **Redirects.** Upstream `Location: /foo` resolves against `https://<ip>/foo`, not
   `/pw/foo`. Rely on `root_path` / `X-Forwarded-Prefix` (preferred) or rewrite `Location`
   on 3xx in the proxy.
3. **WebSockets are not handled.** The httpx request/response pattern does not proxy WS.
   `host-plane`'s `/shell/stream` and mitmweb's live-flow socket won't work through it. The
   Playwright REST surface needs no WS, so this is a non-issue for v1 — but it caps the
   generality.
4. **Auth translation.** Playwright requires `X-API-Key`; the browser currently holds the
   token as the `x-sgraph-access-token` **cookie**. Choose one: (a) the page sends
   `X-API-Key` itself; (b) `forward_auth=true` passes the client header through; (c) the
   proxy **bridges cookie → `X-API-Key` header server-side** so the token never enters JS.
   (c) is the nicest UX; the token value is shared so all three work.
5. **Large / streamed bodies.** Screenshots are multi-MB PNGs; the `Routes__Web` pattern
   buffers the whole body (`response.content`). Fine for screenshots, wasteful for video —
   stream if `video_*` is ever proxied.
6. **Timeouts.** `Routes__Web` hard-codes 30 s; long `/sequence/execute` runs exceed it.
   Make `timeout_sec` configurable and align with the Playwright watchdog hard cap.
7. **Prefix collisions / route shadowing.** A proxy prefix overlapping a real vault path
   (e.g. `/auth`, which the vault uses) breaks one side. Validate prefixes in
   `assert_ready()` against the app's existing routes; reject reserved ones.
8. **Security — the public origin becomes a gateway.** Each entry tunnels an internal-only
   service to `:443`. **Never** add `host-plane` (docker socket). `mitmweb` captures all
   traffic — sensitive. The env var IS the allowlist; treat each addition as a security
   decision. Because the proxy mounts *inside* the vault app, the vault's API-key middleware
   covers `/pw/*` too — confirm the mounted prefix is not in `AUTH__EXCLUDED_PATHS`.

**Wins, for the record:** mixed content solved; no CORS; cookie `path=/` already spans
`/pw/*`; single auth gate; zero new containers.

## 5. Sequence of work

1. **[blocker] Locate the vault app composition root** and confirm it is osbot-fast-api +
   depends on `sg_compute`. Everything downstream forks on this.
2. **Build the generic mechanism** in `sg_compute/fast_api/reverse_proxy/` (this repo): the
   four classes in §3.1 + unit tests (no mocks — real `Fast_API` app + a `_Fake` upstream
   via in-memory composition; assert status / headers / body pass-through and prefix
   stripping).
3. **Decide the auth strategy** (§4.4) — recommend the cookie→header bridge.
4. **Wire the mount** into the vault app's `setup_routes()` (the cross-repo line); ensure
   `/pw/*` stays inside the auth middleware.
5. **Fix sub-path on the upstream:** set Playwright's `root_path=/pw` (or proxy sends
   `X-Forwarded-Prefix`). This is in our `sg-playwright` image — verify the index UI and
   `/openapi.json` render correctly under the prefix.
6. **Compose + env:** add `FAST_API__REVERSE_PROXY__ROUTES=pw=http://sg-playwright:8000` to
   the vault container env in `Vault_App__Compose__Template.py` + the `.env` written by
   `Vault_App__User_Data__Builder` (this repo — we own these).
7. **Rebuild + push** `diniscruz/sg-send-vault` (only if the wiring lands in that image).
8. **Update the reality docs** — `playwright-service` / `sg-compute` indexes + changelog,
   in the same commit as the code (Librarian rule).
9. **End-to-end test** on a fresh `sg va create --with-playwright --wait`:
   `curl https://<ip>/pw/health/status`, then a browser `fetch('/pw/sequence/execute')`
   from the vault page.
