# Agent Guide — Playwright API via the vault `/pw` proxy

> Hand this to the agent writing the automation that runs **inside the SG/Send vault**
> (a vault page script, sg-vfs content, or a sandboxed iframe). It supersedes the
> root-path assumptions in `library/guides/v0.2.6__playwright-api-for-agents.md` for the
> vault-hosted case.

## 0. The two values

```
BASE_URL     = https://<vault-ip>/pw        # same host as the vault, under the /pw prefix
ACCESS_TOKEN = <the vault access token>     # same token that opens the vault
```

There is **no separate Playwright host or port**. The Playwright service is reached through
the vault's own HTTPS origin under `/pw`. A reverse proxy on the vault forwards `/pw/<x>` to
the internal Playwright service and injects its API key server-side.

## 1. Authentication — use `x-sgraph-access-token`, NOT `x-api-key`

Every request **must** carry:

```
x-sgraph-access-token: <ACCESS_TOKEN>
```

**Do not send `x-api-key`.** This is the single most important rule:

- Vault content runs in a **null-origin sandbox**, so calls to `/pw/*` are **cross-origin**
  and trigger a CORS preflight.
- The vault's CORS allow-list permits `x-sgraph-access-token` (and `Content-Type`) but
  **not** `x-api-key`. Sending `x-api-key` → `blocked by CORS policy: Request header field
  x-api-key is not allowed`.
- `x-sgraph-access-token` is also the vault's own auth header, so it passes the vault gate;
  the proxy then strips it and injects the Playwright `X-API-Key` for you. You never send
  `x-api-key` yourself.

## 2. Quick start

```js
const BASE  = location.origin + '/pw';            // same-origin; or hard-code https://<ip>/pw
const TOKEN = '<ACCESS_TOKEN>';
const AUTH  = { 'x-sgraph-access-token': TOKEN, 'Content-Type': 'application/json' };

// is it up?
await fetch(`${BASE}/health/status`, { headers: AUTH }).then(r => r.json());

// one-shot screenshot → raw PNG bytes
const png = await fetch(`${BASE}/screenshot`, {
  method: 'POST', headers: AUTH,
  body: JSON.stringify({ url: 'https://sgraph.ai', full_page: true })
}).then(r => r.blob());

// multi-step sequence — the right call for >=2 actions on one page
const seq = await fetch(`${BASE}/sequence/execute`, {
  method: 'POST', headers: AUTH,
  body: JSON.stringify({ steps: [
    { action: 'navigate', url: 'https://sgraph.ai' },
    { action: 'screenshot', full_page: true },
    { action: 'get_url' }
  ]})
}).then(r => r.json());
```

## 3. Endpoints (all under `/pw`)

| Method | Path | Returns |
|--------|------|---------|
| GET  | `/pw/health/status` | health JSON (readiness gate) |
| GET  | `/pw/health/info` | service name/version |
| POST | `/pw/screenshot` | raw PNG bytes (`image/png`) |
| POST | `/pw/screenshot/batch` | batched JSON |
| POST | `/pw/sequence/execute` | per-step results + timings |
| POST | `/pw/browser/navigate` \| `/click` \| `/fill` \| `/get-content` \| `/get-url` \| `/screenshot` | one-shot helpers |
| GET  | `/pw/docs`, `/pw/openapi.json` | Swagger UI + machine-readable spec |

`/pw/browser/*` are stateless one-shots (fresh Chromium each). Use `/pw/sequence/execute`
for any multi-step flow — same browser, shared DOM, lower overhead.

## 4. Step language — `/pw/sequence/execute`

`steps` is a list of `{ "action": "<verb>", ...fields }`. 16 verbs:
`navigate, click, fill, press, select, hover, scroll, wait_for, screenshot, video_start,
video_stop, evaluate, dispatch_event, set_viewport, get_content, get_url`.

Per-step failures return **HTTP 200** with `status:"failed"` on the offending step — the
sequence reports its own outcome in the body; it does not raise an HTTP error.

## 5. Gotchas

- **`evaluate` is deny-by-default allowlisted** — only constant, side-effect-free reads
  (`document.title`, `window.location.href`) pass. For bulk DOM extraction use `get_content`
  (no allowlist).
- **Proxy/interception is fixed at boot** — do not set a proxy in `browser_config`; the
  stack already routes browser traffic through mitmproxy.
- **Screenshots are raw bytes** on `/pw/screenshot` (use `.blob()`); `/pw/screenshot/batch`
  returns JSON with base64.
- **No CORS config needed on your side** — just use `x-sgraph-access-token` and the
  preflight passes.
- **Discovery:** if a field/shape isn't covered here, fetch `${BASE}/openapi.json` — it is
  the ground truth for the running service.

## 6. Prerequisites (must be live for `/pw` to work)

This guide assumes the deployment has:
1. the **vault launched with the reverse-proxy override** (`sg va create --with-playwright`
   on the merged `vault_app` spec) — provides `/pw/*`;
2. the **prefix-aware `diniscruz/sg-playwright` image** (rebuilt from this branch) +
   `SG_PLAYWRIGHT__ROOT_PATH=/pw` on the playwright container — makes the UI and `/pw/docs`
   resolve correctly.

Until both are live, `/pw/*` API calls work but the bundled UI/`/docs` may 404. If your
automation only makes API calls (the common case), item 1 alone is sufficient.
