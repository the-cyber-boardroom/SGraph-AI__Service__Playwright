# Architect Brief — First Set of CF-Log TUIs (All on Real-Time Data)

> Companion to `…tui-cf-logs-and-architecture-visualisation.md`. That brief sets the model (S3→S3 LETS chains; TUI as the lens). This one names the **first screens to prototype**, each grounded in data flowing **today**. Framing borrowed deliberately from the SG/Edge first-five-screens brief: **explore the art of the possible**, keep effort per screen bounded (1–2 days), expect some to be kept and some discarded.

---

## 1. The framing — exploration, on real data

Unlike the SG/Edge screens (which would render PROPOSED control-plane state), **every screen here reads real CloudFront data** via the existing primitives:

```
S3__Inventory__Lister  →  S3__Object__Fetcher  →  CF__Realtime__Log__Parser  →  Bot__Classifier
sg aws cf distributions list   ·   sg aws s3 ls   ·   sg aws logs groups list
```

No Elasticsearch in the loop (§3 of the parent brief). Bucket: `745506449035--sgraph-send-cf-logs--eu-west-2`, prefix `cloudfront-realtime/{YYYY}/{MM}/{DD}/{HH}/`.

Six screens. Five visualise; one simulates. Sketches below are starting points, **not specifications** — the implementing agent should deviate and document what worked and what didn't.

---

Newest `.gz` objects in `cloudfront-realtime/`, fetched and parsed on the fly. The data-plane equivalent of `tail -f` for the website.

│                                                                                          │
│ 23:04:08  GET  /sources/cv          200  1842B  US  Hit   142ms  ● human                │
│ 23:04:07  GET  /robots.txt          200   31B   DE  Miss   18ms  ◆ bot   (wpbot)         │
│ 23:04:05  GET  /enhancecp           404    0B   CN  Error  21ms  ◆ bot   (generic)       │
│ 23:04:03  GET  /assets/app.js       200  9.1KB  GB  Hit     9ms  ● human                │
│ 23:04:01  GET  /sgit/info/refs      200   512B  US  Miss   88ms  ● human (sgit?)         │
│                                                                                          │
│ this hour: 41 objects  ·  618 events  ·  ▆▇█▆▅▄▃▄▆▇ (events/min)                         │
│ bot/human: ▓▓▓▓▓▓░░░░ 61% bot                                                            │
│                                                                                          │
│ [Space] pause   [b]ots only   [h]umans only   [Enter] inspect record   [q]uit            │

**Real data path:** list newest keys → fetch → `gzip.decompress` → `CF__Realtime__Log__Parser.parse()` → `Bot__Classifier`.
**Teaches:** is full-speed tail readable or does it need throttling; is the bot/human split legible at a glance; is the sgit-vs-web distinction visible in the raw data (informs the reality-doc gap on which distributions are wired).
**Interactivity:** medium (pause, filter, drill to Screen 3). **Update:** real-time, throttled 5–10 Hz.

│  │ ● fresh  │       │ ◐ 2m ago │        │ ○ stale  │       │ ○ none   │         │
│  └──────────┘       └──────────┘        └──────────┘       └──────────┘         │
│       │                                                                         │

**Real data path:** count objects per prefix via `S3__Inventory__Lister`; "fresh/stale" from last-modified vs upstream.

**Interactivity:** medium → high (trigger stages). **Update:** 5–10 s. *Note:* the `parsed`/`enriched`/`aggregated` prefixes are **PROPOSED** (generalising consolidate); until built, this screen renders RAW + the existing consolidated artefact and shows the rest as `○ absent`.

## 7. Screen 6 — Transformation Simulator (the "simulate" art-of-the-possible)

The one screen that is about *simulating* a transformation, not just viewing data. Pick a stage, pick an input prefix, preview the output and field mapping **without writing to S3**.

```
┌─ Transform Simulator · DRY-RUN ──────────────────────────────────────────┐
│ stage:  [parsed → enriched ▾]    input: lets/parsed/2026-05-20/  (9,140)   │
│                                                                            │
│ PREVIEW (no S3 writes)                                                     │
│  in:  9,140 records          out: 9,140 records   (1:1)                    │
│  + adds:  bot_category, geo_country_name, is_probe                         │
│  ~ changes: status_class normalised                                       │
│  - drops:  (none)                                                          │
│                                                                            │
│  sample row 0:                                                             │
│    bot_category  HUMAN → HUMAN        geo  US → United States              │
│    is_probe      (new) → false                                            │
│                                                                            │
│  est. output:  ~0.9 MB ndjson.gz  →  lets/enriched/2026-05-20/            │
│                                                                            │
│ [s] sample another   [c] change stage   [W] WRITE (needs ALLOW_MUTATIONS)  │
│ [q]uit                                                                     │
└────────────────────────────────────────────────────────────────────────────┘
```

**Real data path:** runs the pure transform over real input records, computes the diff in-memory, **skips `S3__Object__Writer`** unless explicitly committed (mirrors the existing `--dry-run`; write gated by the stage's `ALLOW_MUTATIONS` env, consistent with `sg aws s3`/`cf`).
**Teaches:** whether a visual dry-run makes designing new LETS stages dramatically faster; whether field-diff (adds/changes/drops) is the right contract to show before a write.
**Interactivity:** high. **Update:** on demand.

## 8. What the six teach together

| # | Screen | Question answered | Real data today? | Interactivity | Update |
|---|--------|-------------------|------------------|---------------|--------|
| 1 | Live Raw Tail | What's hitting the site now? | ✅ yes | Medium | Real-time (5–10 Hz) |
| 2 | Transformation Pipeline | What stages exist and are they fresh? | ✅ RAW + consolidated; rest PROPOSED | Med→High | 5–10 s |
| 3 | Field Lineage Inspector | What does each transform do to the fields? | ✅ yes | High | Per record |
| 4 | Deployed Architecture | How is it all wired? | ✅ via `sg aws` (Firehose inferred) | Medium | On demand |
| 5 | Traffic Reality | What's going on on the website? | ✅ yes | Medium | 10–30 s |
| 6 | Transform Simulator | What will this new stage produce? | ✅ dry-run over real input | High | On demand |

The sixth conversation (after a week of use): which of these become tabs of one `sg-cf-tui`, which stay standalone commands, which get dropped.

---

## 9. Constraints (from the deployment chain)

Carried verbatim from the SG/Edge brief addendum — all six must hold over SSM + `docker exec`:
- update rates throttled to 5–10 Hz, never 60;
- first frame < 100 ms (render "loading" panes immediately);
- clean re-layout on resize; no broken frames;
- keyboard-primary, no mouse-required interaction;
- `LANG`/`TERM` set at the container level, not inherited through three hops.
