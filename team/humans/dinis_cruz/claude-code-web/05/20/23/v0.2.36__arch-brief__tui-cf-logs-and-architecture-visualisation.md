# Architect Brief — TUIs for Visualising CF Logs (Raw → Transformed) and the CF Deployed Architecture

> **Status legend.** EXISTS = code-verified against the reality docs / source tree. PROPOSED = designed here, does not exist yet. Every TUI screen in this brief and its companion is **PROPOSED**; the data and primitives they sit on are mostly **EXISTS**.

---

## 1. Why this is the right first TUI (and why the vault detour is dropped)

The two SG/Edge TUI briefs (rich-tui-experiments, first-five-screens) make the case for a visually-rich TUI over the SG/Edge control plane. The problem: most of that control plane — proxy launcher/terminator, wake orchestration, slug→instance mapping — is **PROPOSED, not built**. A TUI shipped against those screens today renders mostly synthetic state.

The CloudFront-logs case is the opposite. The data is **real and flowing right now**:

- AWS Firehose continuously writes CloudFront real-time logs to S3 — `s3://745506449035--sgraph-send-cf-logs--eu-west-2/cloudfront-realtime/{YYYY}/{MM}/{DD}/{HH}/` — ~300–400 gzipped objects/day, ~1–2 KB each. **EXISTS** (the addendum confirms it: *"already producing data ... currently not being looked at"*).
- The LETS pipeline (`sp el lets cf …`) already lists, fetches, parses (38-field schema), bot-classifies, consolidates, and indexes those logs. **EXISTS** (≈499 mock-free tests).
- `sg aws cf / s3 / logs` already enumerate the live CloudFront / S3 / CloudWatch surface. **EXISTS**.

**The vault-for-history idea is withdrawn.** The real work is not "store history in a vault" — it is a **chain of LETS transformations from S3 to S3**, where each stage reads an S3 prefix, applies a pure transformation, and materialises the result to another S3 prefix. S3 is already the source of truth; it is also the right home for every intermediate and aggregate. What was missing was never storage — it was **a powerful way to *see and simulate* those transformations.** That is exactly what a TUI gives us.

---

## 2. The model — LETS as S3 → S3 transformation chains

Today the LETS pipeline's terminal sink is Elasticsearch (the ephemeral Kibana stack). The reframe generalises it: **make S3 both the input and the output of every stage**, and treat Elasticsearch as one optional downstream *consumer*, not the spine.

This is not speculative — the **consolidate slice already does S3 → S3** (EXISTS): it reads many raw `.gz` objects and writes one `events.ndjson.gz` + `manifest.json` per day under `lets/{compat-region}/{YYYY/MM/DD}/`, with `S3__Object__Writer.put_object_bytes()` as the sole write boundary. We are generalising a pattern that already works.

A medallion-style chain, every hop persisted to S3:

```
   cloudfront-realtime/{date}/         ← RAW      (Firehose-owned, immutable)  EXISTS
        │  L: list + fetch .gz
        ▼
   lets/parsed/{date}/                 ← PARSED   26 TSV → typed records       (consolidate proves the write path)
        │  E: gunzip + TSV parse + URL-decode + status_class + cache_hit
        ▼
   lets/enriched/{date}/               ← ENRICHED + bot classification, geo rollups, derived fields
        │  T: Bot__Classifier (28 named + 5 generic), derivations
        ▼
   lets/aggregated/{date}/             ← AGGREGATED daily rollups (counts, top-URIs, bot/human, latency pctl)
        │  S: write rollup artefacts (NDJSON / parquet-later)
        ▼
   [optional consumers] Elasticsearch / Kibana   ·   a future API   ·   the TUI itself
```

Two properties carry over from the existing pipeline and must hold for every stage:

1. **Every `load` has a matched `wipe`** — each S3 output prefix is reproducible from the prefix upstream of it; nothing is precious except `cloudfront-realtime/`.
2. **Pure transforms, single write boundary** — the transformation functions (`CF__Realtime__Log__Parser`, `Bot__Classifier`) are already pure and ES-independent; the only side effect is `S3__Object__Writer`.

The TUI's job is to make this chain — and the field-level transformation inside each hop — **visible and simulatable**.

---

## 3. The architectural seam that makes the TUI cheap and live

Today, "look at the traffic" means `sp el create` (≈80 s to boot Kibana) → load → open dashboards. Too heavy for a live TUI, and it couples viewing to Elasticsearch.

But the LETS **extract/transform layer is pure code with no ES dependency** — it runs in-memory across the mock-free test suite. So the TUI calls:

```
S3__Inventory__Lister  →  S3__Object__Fetcher  →  CF__Realtime__Log__Parser  →  Bot__Classifier
   (list prefix)            (GetObject bytes)         (TSV → 38-field record)      (UA → category)
```

…**directly against S3, with no Elasticsearch in the loop.** Kibana stays available for deep historical exploration; the TUI does not need it for the live view or for previewing a transformation. This is the single most important enabling fact in this brief: the primitives we want to visualise are already a clean, importable library.

## 4. Two visualisation domains

The TUI work splits cleanly into two domains. Both read real data; the companion brief (`…tui-cf-first-screens-realtime-data.md`) gives concrete first screens for each.

### 4A. The data plane — CF logs from raw to transformed
What is *in* the logs and what each transformation does to it:

- **Live raw tail** — newest `.gz` objects in `cloudfront-realtime/`, parsed on the fly. "What is hitting the website right now."
- **Transformation pipeline** — the S3→S3 chain (§2) as live boxes-and-arrows, with per-stage object counts, byte volumes, and lag.
- **Field lineage / transform inspector** — one log line walked through all 38 fields: 26 raw TSV → 4 derived (`status_class`, `cache_hit`, …) → 5 lineage (`doc_id` = `{etag}__{idx}`, source key/etag) → 3 pipeline metadata. This is the "fields captured / transformed" view you asked for.
- **Simulate / dry-run** — point a stage at an input prefix, preview the output records and field mapping **without writing to S3** (the existing `--dry-run` flag already builds the queue and skips writes — the TUI surfaces that).

### 4B. The control plane — CF deployed architecture
How the pieces are actually wired, enumerated from live AWS state via `sg aws`:

- CloudFront distribution(s) → real-time-log config → Firehose stream → S3 bucket/prefix → LETS stages → consumers.
- Resource identities pulled live: `sg aws cf distributions list`, `sg aws s3 ls`, `sg aws logs groups list`.
- This turns the hand-drawn ASCII diagram in `00__cloudfront-lets-architecture-review.md` into a **generated, data-backed, live** topology.

## 5. Module shape (carried from the SG/Edge briefs)

Same discipline the SG/Edge briefs set out, and it applies unchanged:

1. **CLI/LETS primitives stay as they are** — flag-driven, agent-friendly, scriptable, the source of truth.
2. **The TUI is a thin, replaceable layer on top** — it subscribes to primitive output; it never holds parallel state.
3. **Separate module** (e.g. `sg-cf-tui` / `sg-lets-tui`), so it does not bloat the LETS package.
4. **Framework: Textual + Rich (Python)** — already in-stack, matches the SG/Edge brief's recommendation, container-friendly over the SSM + `docker exec` chain.

Deployment-chain constraints from the SG/Edge brief addendum hold verbatim: throttle updates to 5–10 Hz (not 60), first frame < 100 ms, `LANG`/`TERM` set at the container level, keyboard-primary, graceful resize. The TUI runs as a foreground process; the LETS services it reads are separate and survive it.

## 7. Risks & honesty notes

- **Don't imply the SG/Edge control plane exists.** The slug/wake/edge-proxy screens in the source briefs visualise PROPOSED machinery. The CF-logs screens here visualise real data — keep that distinction explicit so the team doesn't mistake mockups for reality.
- **Reality-doc gap.** We have not verified *which* CloudFront distributions (website / api / tools-sgit) have real-time logging enabled and pointed at the Firehose. The architecture view will surface this honestly (show what's wired; mark unknowns) and the gap should be closed in the reality doc.
- **Volume.** Raw is ~400 tiny objects/day; aggregates are small. The TUI live-tail must page/sample, not load a full day into memory.
- **TUI drift.** Keep the TUI thin over primitives; if a stage's schema changes, the TUI reads the new output, it does not encode a parallel copy.
