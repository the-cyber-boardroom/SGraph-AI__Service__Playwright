## The ask

Long-promised: let operators add arbitrary EC2 tags at create time
(`--tag Project=akeia --tag CostCenter=42`).

## The change

- `Schema__Vault_App__Create__Request.custom_tags : str` — newline-joined KEY=VALUE
  (same carrier shape as `interceptor_env`).
- `Vault_App__Service.parse_custom_tags(str) -> dict` — parses lines, splits on the
  **first** `=` (values may contain `=`), and **rejects reserved keys**
  (`RESERVED_TAG_KEYS`: Name/Purpose/StackName/StackType/CallerIP/CreatedBy + the
  vault-app extras + Namespace). Called in `create_stack` **before any AWS
  mutation**, so a bad `--tag` fails fast (no SG, no instance). The parsed dict is
  `extra.update(...)`-merged into the tag set before `tags.build`.
- CLI: repeatable `--tag KEY=VALUE` (List[str]); `_set_extras` validates the shape
  (non-empty key + `=`) and joins.

Reserved-key rejection matters: a `--tag Name=x` would create a **duplicate** `Name`
tag key (run_instance rejects that) or shadow a lifecycle filter. Custom tags also
flow through `apply_name_prefix`, so `--name-prefix` gives them prefixed-key
duplicates too (`acme-Project`), consistent with the rest of the tag set.

## Good failures

- **Fail-fast placement:** validated custom tags alongside the `--with-aws-dns`
  pre-flight, before the security group / instance are created — a reserved-key
  typo costs nothing.
- **`partition('=')` not `split('=')`** so tag values containing `=` survive
  (locked by `test_value_may_contain_equals`).
