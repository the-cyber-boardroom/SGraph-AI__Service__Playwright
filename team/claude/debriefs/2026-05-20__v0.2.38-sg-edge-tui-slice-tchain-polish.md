## 3. Key design decisions (the how)

- **One base App, five thin screens.** Each screen now subclasses
  `SG_Edge__TUI__App__Base`; Textual merges BINDINGS across the MRO, so the shared
  keys add to each screen's own. This *removed* code (the duplicated `action_leave` /
  `self.exited`) while adding the polish in one place — verified by the existing 66
  pilot tests staying green through the refactor.
- **Export key is `e`, not `c`.** `c` is the Events screen's "clear"; `e` also matches
  the sibling CF-logs TUI. Card export uses Textual's `copy_to_clipboard()` → OSC-52,
  which survives the SSH/SSM chain (playbook §4); a pilot test asserts `app.clipboard`
  holds the rendered card.
- **Help is context-aware without Textual internals.** `help_lines()` walks
  `type(self).__mro__`, collecting BINDINGS only from our own modules
  (`__module__.startswith('sg_compute_specs')`) so Textual's built-in ctrl-bindings
  don't pollute the overlay. Handles both raw tuples and normalised `Binding` objects.
- **Dockerfile: cheap env only.** The service image's requirements have neither typer
  nor textual — the TUI doesn't run there — so adding `ncurses-term`/`locales` would
  bloat it for no benefit. Set the UTF-8/`$TERM` env (good hygiene, one layer) and
  document the full snippet in the guide for a *dedicated* TUI image (Slice 5).

## 4. Gotcha worth remembering

`klass.__dict__['BINDINGS']` items are **`Binding` objects**, not the tuples you
wrote — Textual normalises them at class creation. `binding[0]` raises
`TypeError: 'Binding' object is not subscriptable`. Walk with `getattr(binding,
'key'/'description')` and handle both forms. **Good failure** (caught by a probe
before writing the formal test).
