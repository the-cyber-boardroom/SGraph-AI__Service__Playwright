# v0.2.38 SG/Edge TUI — Local Docker screen + tabbed Dashboard

Three asks: a screen for what's running on local Docker, surface it in Deployment,
and add Textual top-level navigation across all screens.

## What landed

| Piece | Where | Note |
|---|---|---|
| Docker source | `tui/source/SG_Edge__TUI__Docker__Source` | thin seam over the existing `Pod__Runtime` (shells out to `docker ps`; no SDK). Daemon down → empty + `available()` False |
| Docker render | `tui/screens/SG_Edge__TUI__Docker__Render` | `docker_lines()` (reused) + `docker_markup`/`_plain`; running ● / exited ✗ glyphs; honest "not reachable" |
| Docker screen | `tui/screens/SG_Edge__TUI__Screen__Docker` | `sg edge tui docker` (no-TTY → plain) |
| Deployment update | `Deployment__Render` + `Screen__Deployment` | optional `containers`/`docker_available` args → **LOCAL DOCKER** section; screen fetches via an injected docker source (None → omitted, backward compatible) |
| **Dashboard** | `tui/screens/SG_Edge__TUI__App` | one app, **Textual `TabbedContent`**, 6 tabs; `sg edge tui dashboard` |
| Tests | `test_SG_Edge__TUI__Docker`, `test_SG_Edge__TUI__App` | +16 (TUI total 81) |

Tests: **3.12 → 81 pass**; **3.11 → 52 pass, 29 gated-skip**. Full `sg_edge`: 246
pass, 6 skip, 1 pre-existing waker fail. No mocks — docker tests use a real
`Pod__Runtime` subclass with a canned `list()` (and a "down" one that raises).

## Key design decisions

- **Reuse, don't reinvent, Docker.** The host plane already has `Pod__Runtime__Docker`
  (CLI-based, typed `Schema__Pod__List`). The TUI source is a 15-line seam over it;
  tests inject a fake `Pod__Runtime` subclass — the proven inject-a-real-subclass
  pattern (no mocks, no daemon needed). `docker_lines()` is shared by the Docker
  screen and the Deployment section so they can't drift.
- **Dashboard uses `TabbedContent` (the idiomatic Textual nav).** Six tabs over the
  SAME pure renders + shared sources; one timer polls, the active tab redraws;
  `1..6`/`←→` switch (plus the clickable tab bar). Per-tab interaction kept to the
  high-value `↑/↓` select on Topology & Slug; the focused standalone commands keep
  full controls. The events feed accumulates continuously via the `Differ` regardless
  of which tab is active.
- **Lazy AWS/Docker fetch in the dashboard.** `compare`/`docker` tabs fetch their
  (network / subprocess) source only when rendered, not every tick.

## Gotcha

`docker ps` json's `State` field is the machine state (`running`/`exited`); `Status`
is the human string (`Up 2 hours`). The glyph keys on `State`, the row text shows
`Status`. (`Pod__Runtime__Docker.list()` populates both; `ports` is empty from `ps`
— it needs `inspect`, deferred.)

## What's next

This is the practical answer to part of the **"sixth conversation"**: the dashboard
*is* a candidate canonical app. Still standalone-app-based (the dashboard duplicates
a little per-tab state rather than hosting Textual `Screen`s); a full Screen-based
consolidation is the deeper refactor if the dashboard earns promotion. And the
pending panes (instance/cost/activity) light up with Slice 5 + observability.
