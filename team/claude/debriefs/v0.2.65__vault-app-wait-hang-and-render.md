## The report

`sg va create … --with-aws-dns --wait` **hung to the 600s timeout** even though the
stack was fully healthy: cert issued (`DNS converged … cert issued` in cert-init
logs), `external-http ✓ serving (149ms)`, 4 containers up. The check table showed
two stuck WARNs:

```
vault-http   ⚠ WARN   HTTP 000000 — up but not ready
cert-init    ⚠ WARN   not yet — stage file empty (cert-init has not started)
```

## Root cause — two false WARNs (NOT the DNS race, NOT the renderer)

`run_until_ok` only completes when every row is `ok`/`skip` (`OK_STATES`). Two
checks in `diagnose()` were wrong for a TLS stack:

1. **vault-http** always probed `http://127.0.0.1:8080`. A TLS stack binds **:443
   only** (the `_SG_SEND_VAULT_TLS` compose publishes 443, app on 443) — so the
   :8080 probe returns `000000` → permanent WARN.
2. **cert-init** keyed off the stage file `/var/lib/sg-compute/cert-init.stage`,
   which the deployed `diniscruz/sg-host-control:latest` image **doesn't write**
   (older cert_init). Empty file → "cert-init has not started" WARN — even though
   the container had **Exited (0)** with the cert issued.

So the operator's instinct (a + b) wouldn't have fixed this: **(a)** is cosmetic
and **(b)** doesn't apply (DNS converged fine). The hang was the diagnose checks.

## Fixes

**1. vault-http (TLS-aware)** — probe `https://127.0.0.1/info/health` with `-k`
when `tls_enabled`; keep `http://…:8080` otherwise. Normalised the "no response"
test so `000`/`000000`/`''` all read as connection-refused.

**2. cert-init (container-status primary)** — read the one-shot container's exit
status (`docker ps -a --filter name=cert-init`): `Exited (0)` → **ok**, non-zero →
fail, `Up …`/mid-stage → warn, absent → not started. The stage file is now only
*supplementary detail*, so an image that doesn't write it can't produce a false
WARN. (Mirrors what `sg va cert-renew` already trusts.)

> Both fixes are **client-side** (the CLI reads container state via SSM), so they
> take effect on the **next CLI run against the existing stack** — no recreate, no
> image rebuild. `sg va wait swift-watt` will now complete.

**3. (a) Off-TTY duplicated `--wait` rows** — `Spec__Diagnose__Renderer` now gates
`rich.Live` on `console.is_terminal`. Off a TTY (where Live can't do in-place
redraws, so each per-check `.update()` re-emitted the whole table → repeated
`attempt=N` blocks), it uses a sink and prints **one deduped snapshot per attempt**
(only when a check's state changes). On a real TTY, Live is unchanged.

**4. (b) DNS-wait robustness** — `cert_init.wait_for_dns_to_match` gains
`raise_on_timeout` (default True, preserves existing callers/tests). The hostname
flow calls it with `False`: on a box-side timeout it logs a warning and **proceeds
to ACME** instead of aborting, because Let's Encrypt validates from **its own**
resolvers — so a stale box NXDOMAIN cache (Route 53 negative TTL ~900s, longer than
the poll window) no longer kills a cert LE could issue. **Caveat: cert_init.py runs
in the prebuilt host-control image, so (b) only takes effect after that image is
rebuilt + pushed.** (Not the cause of the reported hang — a forward-looking
hardening for the legitimate `--with-aws-dns` race.)

## Good failures

- **Read the evidence, not the request.** The operator asked for a + b; the paste
  proved the stack was healthy and DNS had converged, so the real fault was the two
  diagnose checks. Fixing those is what actually unblocks `--wait`.
- **Container-status over stage-file:** chose the signal that's true regardless of
  which host-control image is deployed, instead of depending on an observability
  file the image may not emit.

## Bad failures

- **Pre-existing**: the cert-init/vault-http checks assumed non-TLS internals
  (:8080, stage file) on a stack shape that's TLS-by-default — a latent false-WARN
  that only surfaced once `create --wait` started rendering the table.
