# v0.2.38 SG/Edge TUI — DataTable prototype + reviews

Prototype of the Textual-widget approach (vs markup-into-a-Static) on one screen,
to inform the promotion decision. Plus reviews of the sibling CF-logs TUI and our
own Textual leverage (delivered in chat).

## What landed

| Piece | Where | Note |
|---|---|---|
| Generic Type_Safe→table | `tui/screens/widgets/SG_Edge__TUI__Table.type_safe_table()` | any Type_Safe list → (columns, rows) via `.json()`; pure, 3.11 |
| DataTable slug inventory | `tui/screens/SG_Edge__TUI__Screen__Slugs` | real `DataTable` widget — built-in row cursor (↑/↓), scroll, zebra, mouse, `RowSelected`; Enter/click → drill to Slug detail |
| CLI | `tui/cli/Cli__SG_Edge__Tui` (`slugs`) | no-TTY → plain rows |
| Tests | `test_SG_Edge__TUI__Screen__Slugs` | +5 (TUI total 86): helper (pure) + pilot (rows/cursor/select) |

3.12: 86 TUI tests; 3.11: 55 pass + 31 gated-skip. No mocks.

## DataTable vs markup — what the prototype shows

| | Markup-into-Static (the 5 screens) | DataTable widget (this prototype) |
|---|---|---|
| Row cursor / ↑↓ | hand-rolled (`selected_index`, `▸` marker, clamp) | **built in** |
| Scroll past screen | VerticalScroll on the whole blob | **per-row, built in** |
| Mouse / click-to-select | none | **built in** (`RowSelected`) |
| Columns / alignment | manual `ljust` padding | **built in**, + sortable |
| Content testable on 3.11 | yes (pure `*_markup`) | only the row-builder is pure; layout needs Textual |
| Lines of screen code | ~40 (incl. nav) | ~45 (but nav/scroll are free) |

**Takeaway:** DataTable removes the hand-rolled selection/scroll/mouse code and is
the clear win for *list* surfaces (slugs, events, containers, the CF files browser).
The cost: the cell content is no longer a single pure markup string (only the
row-builder stays pure), so the "render on 3.11 without Textual" property weakens for
those screens. For *non-list* surfaces (topology diagram, slug detail, the layered
deployment view) markup-into-Static is still the better fit — there's no table there.

## On the Fast_API Type_Safe→DataTable converter

The owner noted osbot-fast-api has a Type_Safe→table converter. It is **not installed
in this container** (only osbot-utils + osbot-aws are), so I could not reuse it; I
wrote a 12-line local stand-in (`type_safe_table`, via `.json()`). When the widget
approach is promoted, consolidate with the Fast_API class rather than keeping this.

## Reviews (delivered in chat, summarised)

- **CF-logs TUI (sibling):** same architecture as ours (pure render + thin App +
  source seam + glyphs + Card + lazy/gated). Does two things better — in-screen
  multi-level drill (`dir→file→record` via a mode + Esc stack) and a Field Lineage
  Inspector — both worth adopting when we consolidate. Lacks our shared base
  (help/theme/export) and tabbed dashboard. Heavy duplication across the two TUIs →
  a shared `tui_kit` is worth extracting post-promotion.
- **Textual leverage:** we lean on markup-into-Static; biggest unused levers are
  `DataTable` (this prototype), Screen-based composition (so the dashboard hosts full
  interactive screens), `Sparkline` widget, reactive attributes, and CSS multi-pane.

### Failure classification (per CLAUDE.md §27)
- **Good failures:** none — `DataTable` built-ins replaced hand-rolled nav cleanly.
- **Bad failures:** none. Local `type_safe_table` stand-in is flagged for
  consolidation with the Fast_API converter (couldn't reuse — not installed here).
