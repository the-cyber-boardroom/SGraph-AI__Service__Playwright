## 11. F1 + F4.2 addendum (2026-07-03) — health semantics, chromium 0.0.0, console render smoke

From the 07/03 review follow-ups: **F1** (the `chromium 0.0.0 · degraded` health badge) and **F4.2** (the JS-executing console render smoke promised in §9's follow-up line).

### F1 — `degraded` root cause (confirmed): vault connectivity gated liveness

`Playwright__Service.get_health()` computed `healthy = all(checks)` where one check was `Capability__Detector.connectivity_check()` → `healthy = bool(get_env(SG_SEND_BASE_URL))`. Any deployment without the vault env var — laptop, plain `docker run`, the CI sidecar — reported `healthy: false` forever, with a perfectly working browser. Vault reachability is a **capability** (already surfaced as `capabilities.has_vault_access`), not liveness.

**Fix:** `Schema__Health__Check` gained `gating : bool = True` (`Schema__Health__Check.py:14`); `connectivity_check()` sets `gating=False` (`Capability__Detector.py:200-206`); the aggregate is now `all(c.healthy for c in checks if c.gating)` (`Playwright__Service.py:124`). The connectivity check stays in the `checks` list with its detail and truthful per-dimension `healthy` — response shape backward-compatible (`healthy` bool + `checks` list; each check adds the `gating` field). Tests that pinned the old semantics were flipped deliberately with F1 comments: `test_Playwright__Service.py::test__healthy_even_when_vault_unreachable`, `test_Routes__Health.py::test__healthy_even_when_vault_unreachable`, plus a `gating`-is-informational assertion in `test_Capability__Detector.py`.

### F1 — `chromium 0.0.0` root causes (confirmed — there were THREE, not two)
