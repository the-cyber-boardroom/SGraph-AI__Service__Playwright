# v0.2.40 — shared AWS auth layer + `sg el lets cf iam`

## The trigger

`sp el lets cf tui sync` on a console with no usable AWS credentials dumped a raw
botocore `NoCredentialsError` traceback. The ask grew into: *capture the auth error and
give the user options* → *and let it transparently assume a scoped least-privilege role
by default*. Built in six phases, one commit each.

## What shipped

**P1 — credential chokepoint convergence.** Added
`aws/_shared/auth/Aws__Session__Factory.boto3_client_via_context(service, region)` — the
one place a boto3 client is born for the converged surface. The clients that called
`boto3.client()` directly (CloudFront, Logs, Firehose, and the two LETS S3 boundaries
behind `tui sync`) now call it from their existing seam (seam names unchanged → tests
still subclass-override). Behaviour-preserving: no SG role → bare boto3 exactly as before.

**P2 — generic auth guard.** `AWS__Auth__Classifier.is_auth_error` (NoCredentials +
botocore auth `ClientError` codes) and `@aws_auth_guard(family)`. On an auth failure:
interactive TTY → list stored keyring credentials, pick one, set it on `Sg__Aws__Context`,
**retry the command in-process**; non-interactive → remediation + exit 2. `store` +
`chooser` injectable, so it tests with no AWS and no TTY.

**P3 — role-profile registry.** `AWS__Role__Profiles` (register/get + `policy_document`
/ `trust_policy_document` / `role_arn` rendering) and the profile/statement schemas. The
`el-lets-cf` profile (role `sg-lets-cf`) lives in `elastic/lets/cf/iam/cf_role_profile.py`
and self-registers. One source of truth read by both the provisioner and the assumer.

**P4 — provisioner + `iam` CLI.** `AWS__Role__Provisioner` (plan-diff / apply / delete)
over `IAM__AWS__Client`, which gained `create_role_with_trust` (account-root trust JSON —
the service-principal `create_role` can't express it) and `update_assume_role_policy_raw`.
`sg el lets cf iam show|plan|create|update|test|delete`, gated by
`SG_AWS__IAM__ALLOW_MUTATIONS=1` + confirm.

**P5 — transparent assume by default.** `AWS__Auth__Context` (active family) +
`AWS__Auth__Resolver`: when a family is active the factory assumes its role from the base
identity, notifies once, caches the session; falls back (→ base identity → guard menu) if
the role is absent/denied. `Sg__Aws__Session` gained `assume_arn` / `account_id_via_sts`
/ `base_session_from_context`. `aws_auth_guard` sets the active family so least-privilege
is the default path; `aws_auth_guard('')` catches without assuming (used by `iam` mgmt).

**TUI extension.** Wrapped the S3-touching TUI commands
(`traffic`/`files`/`inspect`/`architecture`/`sync`) with the same guard so transparent
assume + clean errors cover the visual surface too; `cache`/`diagnose` touch no AWS.

## Design calls worth remembering

- **Reuse over rebuild.** Converged onto the existing `Sg__Aws__Session` chokepoint and
  the existing `IAM__AWS__Client` boto3 boundary rather than adding parallels — kept the
  "one place a client is born / one IAM boundary" invariants intact.
- **Profile = single source of truth.** Granted (provisioner) and assumed (resolver)
  privilege are rendered from the same `Schema__AWS__Role__Profile`, so they can't drift.
- **Transparent assume on by default** (the user's explicit choice): the broad base
  identity (SSO/iam-admin/IMDS) is never used directly for `sg el lets cf`; the scoped
  `sg-lets-cf` role is the path of least resistance, not an opt-in.
- **Per-family footprint** is one profile file + one import line — onboarding the next
  `sg aws` section is cheap.

## Failures (good / bad)

- **GOOD — fixed:** the original `NoCredentialsError` traceback. Now both native and TUI
  paths show a menu/remediation. Verified by smoke (exit 2 + remediation, no traceback)
  and the guard's in-process-retry test.
- **GOOD — caught early:** an accidental edit deleted `iam = self.client()` from
  `IAM__AWS__Client.delete_role`; spotted immediately and the new method was inserted
  *before* `delete_role` instead. No test masked it because it was caught pre-run.
- **GOOD — design:** discovered `create_role` only builds *service-principal* trust, so
  added `create_role_with_trust` rather than bending the family role into a service trust.
- **BAD — outstanding (flagged, not silenced):** the IAM mutation paths and the real STS
  assume are unit-tested against an **in-memory `Fake__IAM`** only. They are unverified
  against live IAM/STS. This is an explicit follow-up: run `sg el lets cf iam create` +
  `iam test` on a credentialed console and record the result. Until then `aws-auth.md`
  carries the LIVE-but-unverified caveat.

## Follow-ups

1. Live verification of `iam create`/`update`/`delete`/`test` (the BAD failure above).
2. The interactive guard menu re-invokes the whole command on "retry" — fine for reads,
   but create/delete re-prompt the gate + confirm; revisit if it annoys in practice.
3. Onboard a second family to exercise the registry's generality.

## Test footprint

`aws/_shared/auth/tests/` (classifier+guard, registry, provisioner, resolver+context+
factory) and `elastic/lets/cf/iam/tests/` (iam CLI with injected `Fake__IAM`). Full
regression green: 155 across `aws/`, `elastic/lets/cf/`, `credentials/`, `tui/`. No mocks,
no patches — all real subclasses.
