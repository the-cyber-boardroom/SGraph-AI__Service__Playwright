## The incident

`sg va create --with-playwright --wait --with-aws-dns` launched, then boot-failed
at line 323 (`docker compose up -d`). `sg-send-vault` never started; `vault-http`
was `000000`. cert-init logs:

```
RuntimeError: DNS for 'kind-planck.sg-compute.sgraph.ai' did not converge to
13.135.91.221 within 180s (last seen: '<resolution failed: Name does not resolve>')
```

## Root cause — NOT a code regression

Diffed the whole vault-app/TLS/cert/DNS surface between the last known-good version
and current `dev`: the cert path is **byte-identical** (only a cosmetic `--wait`
check-table wiring + dep bumps changed). Verified locally that cert-init
self-signed works and `build_csr` works for both IP and hostname.

The real cause (operator confirmed): **the stack was created on an AWS account that
does not host the `sg-compute.sgraph.ai` Route 53 zone.** So `--with-aws-dns`'s
A-record upsert had nowhere to go. And it failed **silently**:

- `--with-aws-dns` runs `Vault_App__Auto_DNS.run()` on a **post-launch background
  thread** (`_vault_app_post_launch`), so its zone-resolution error is only
  *printed*, never fatal.
- The EC2 is already launched; cert-init on the box then waits 180s for a name
  that will never resolve, exits non-zero, and fails the whole boot ~10 min later.

So a one-API-call misconfiguration became a 10-minute boot failure with a
misleading "DNS did not converge" symptom.

## The fix

`Vault_App__Service.create_stack` now runs `_preflight_aws_dns_zone(fqdn)` **before
`run_instance`** whenever `--with-aws-dns` is set. It reuses the same
`Route53__Zone__Resolver.resolve_zone_for_fqdn` the post-launch thread uses; if no
owning hosted zone is found in the account, it raises an actionable `ValueError`
**before any EC2 is launched**:

```
--with-aws-dns can't create DNS for 'kind-planck.sg-compute.sgraph.ai': no Route 53
hosted zone owning it was found in this AWS account (ValueError: ...).
  Fix it one of these ways:
    • switch to the AWS account/profile that hosts the zone, or
    • --tls-hostname <fqdn-you-control>  (create the A record yourself, no --with-aws-dns), or
    • drop auto-DNS:  --no-with-aws-dns  (+ --tls-mode self-signed, or --no-with-tls-check)
```

Injectable via `_aws_dns_zone_resolver_factory` so it unit-tests without AWS. Only
fires for `--with-aws-dns` (manual `--tls-hostname` users own their DNS, possibly
outside Route 53, so we don't block them).

## Good failures

- **Resisted the "dev broke it" assumption.** The diff proved the cert code was
  unchanged; the artifact (cert-init log) + operator memory pinpointed the wrong
  account. The fix addresses the *real* gap (silent post-launch DNS failure), not a
  phantom regression.
- **Fail-fast over fail-slow:** moved a detectable error from minute-10 (boot) to
  second-0 (pre-flight).

## Bad failures

- **Pre-existing**: `--with-aws-dns` ran its only zone check on a fire-and-forget
  thread after launch — a silent failure by construction. Now guarded up front.

## Noted bug (separate) — duplicated `--wait` check-table rows

The new `create --wait` live table (shared `Spec__Diagnose__Renderer.run_until_ok`,
wired in via the +9-line dev CLI change) **duplicates** header/rows:

```
Check   State   Detail  attempt=1  elapsed=0s
Check   State   Detail  attempt=1  elapsed=0s
Check   State   Detail  attempt=3  elapsed=22s
...
```

**Cause:** inside one `rich.Live(transient=False)` context, `run_checks` calls
`live.update(...)` once *per check* (~10×/attempt). When stdout isn't a clean TTY,
`rich.Live` can't do in-place cursor redraws, so each `update` re-emits the full
table instead of overwriting → repeated `attempt=N` blocks.

**Solvable — yes.** Options (in `sg_compute/cli/base/Spec__Diagnose__Renderer.py`):
1. Gate on `console.is_terminal`: use `Live` when interactive; otherwise print one
   table snapshot per *attempt* (not per check).
2. Or coalesce updates: update the Live once per attempt instead of per `_set`.
3. Or `Live(..., auto_refresh=False)` + a single `live.refresh()` per attempt.

It's shared CLI rendering (touches every spec's `wait`/`create --wait`), cosmetic,
and out of scope for this DNS fix — tracked as a follow-up.
