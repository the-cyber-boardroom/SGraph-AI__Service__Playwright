# v0.2.36 CF-logs TUI — Slice T1+S1 (data layer + Traffic Reality screen)

## 1. Why

The two CF-log TUI briefs (framing + first-screens) describe a TUI over the
CloudFront-logs pipeline — the data plane that is **real and flowing today**
(Firehose → S3), unlike the still-PROPOSED SG/Edge control plane. This slice builds
the shared data layer + the headline **Traffic Reality** screen ("what is going on
on the website"), mirroring the exact pattern the SG/Edge TUI established
(`sg_compute_specs/sg_edge/tui/`): a thin Textual app over a pure render module over
a source seam.

textual/typer) skip cleanly where absent; the aggregator/render/card/source suites
always run. No regressions in the CF events parser suite or the SG/Edge TUI suite
(both still green). **No mocks** — the S3 source is tested by subclassing the two LETS
S3 boundaries to return gzipped fixture bytes (the LETS no-mock pattern).

## 3. Key design decisions (the how)

- **S3-direct, no Kibana.** The live view runs `list → fetch → gunzip → parse →
  aggregate` entirely in memory. The LETS parsers are pure and ES-independent, so the
  TUI reuses them as a library — this is the architectural seam the framing brief
  named, proven here.
- **One source seam, two implementations.** In-memory (real golden lines, runs
  anywhere/CI) and S3 (the live bucket). Both produce the identical
  `Schema__CF_TUI__Traffic_Snapshot`, so the screen is source-agnostic.
- **No fabrication.** Every tally traces to a parsed record; empty input renders
  zeros and a "(no events)" sparkline, never invented traffic. The in-memory source
  labels itself "in-memory (fixtures)" on screen so it is never mistaken for live.
- **Content/view split + lazy/gated textual** — copied wholesale from the SG/Edge S1
  slice. `Cli__CF__Tui` imports the screen inside the command body so the
  `add_typer` mount never pulls textual; the rest of `sp el lets cf` works without it.
- **`asyncio.run()` pilot tests** — same as SG/Edge; no `pytest-asyncio` dep.

## 4. Gotchas the next session will hit

- **Single-command Typer collapse** — handled with the no-op `@app.callback()` (same
  lesson as the SG/Edge slice). Keep it as more screens land.
- **No live S3 test** — there are no AWS creds in the web container, so the S3 source
  is only exercised via injected in-memory boundaries. A real-bucket smoke test is a
  manual/local step.
- **Web-container deps to run the full suite**: `pip install textual typer rich boto3
  pytest` (osbot-utils/osbot-aws too). The project targets 3.12; the sandbox is 3.11
  and the pure layers run there, the textual/typer suites gate-skip.
- **`bot` vs `human` vs `unknown`** — `human` = `bot_category == HUMAN`; `unknown` =
  empty UA. Both fixture lines are wpbot (BOT_KNOWN), so the demo shows 100% bot —
  expected, not a bug.
