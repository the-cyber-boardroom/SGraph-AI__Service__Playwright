# v0.2.39 — TUI component library, local sync, firehose

Four asks from one message, built "TUI-first" and "component-first".

## 1. Shared component-first TUI library — `cli/tui/`

The backbone the user asked for so screens reuse instead of copy:
- `tui/render/Tui__Text` — shared pure helpers (`esc`, `human_size`/`count`, `ts_utc`).
- `tui/debug/Debug__Event_Log` — a bounded, **injectable under-the-hood feed** a
  service writes to (`s3.list` / `s3.get` / `fs.write` / `aws.*`). `Debug__Panel__Render`
  turns it into markup (pure, tested without textual).
- `tui/components/Debug__Panel` — a Textual widget pinning that feed to the right.
- `tui/components/Tui__App` — reusable base `App` owning the chrome: header, scrollable
  body, **collapsible Debug Panel (open by default, `d` toggles)**, footer + the shared
  log. A new screen is "subclass `Tui__App`, implement `populate()`".

## 2. raw-cf-logs local cache + sync — the S3 bottleneck

- Store: `_vaults/cf-logs/raw-cf-logs/{YYYY}/{MM}/{DD}/{HH}/{file}` (gitignored).
  `CF__Local__Store` maps S3 key↔local path, read/write, per-day stats rollup.
- `CF__Logs__Sync` reuses the LETS S3 boundaries **verbatim** (`S3__Inventory__Lister`
  + `S3__Object__Fetcher`). Two modes built on `plan()`: **list** (S3-vs-local diff for
  a date/day+hour) and **download** (fetch only missing — CF objects are immutable, so
  present files are never re-fetched; the only live question is "is today complete?").
- `CF_TUI__Screen__Sync` subclasses `Tui__App`; the download runs in a **Textual thread
  worker** with live per-file progress, and the shared Debug__Event_Log lights up the
  panel with every S3 call/write. `sp el lets cf tui sync --date --hour --mode`.

## 3. Local cache stats — `sp el lets cf tui cache`

`CF__Local__Store.stats()` → totals, partition coverage, per-day table. The screen is
another thin `Tui__App` subclass; the panel shows the fs scan. Baseline for the
"optimise this further" work the user flagged.

## 4. sg aws firehose (read-only) + architecture wiring

- New `aws/firehose/`: `Firehose__AWS__Client` (sole boto3 boundary; list/describe
  never raise) → `sg aws firehose ls|describe` with the resolved S3 destination.
- Wired into the Architecture screen: `CF_TUI__Arch_Source` now enumerates streams, so
  the **Firehose→S3 hop is VERIFIED** (stream name + destination shown). The genuinely
  un-introspectable bit — *which distribution's* real-time logs feed the stream —
  stays ⚠ UNVERIFIED. Honesty preserved, gap narrowed.

## Gotchas / failure classification (per CLAUDE.md §27)

- **GOOD:** persisted shell `cd` (into a dir with a `collections/` package) shadowed
  stdlib `collections` and broke `python -m pytest` at startup — always run from repo
  root with absolute paths. Surfaced immediately, fixed.
- **GOOD:** thread-worker download needed `await app.workers.wait_for_complete()` in the
  pilot, not just `pilot.pause()` — caught by the test.
- **BAD:** none. Live-AWS paths (firehose list/describe, S3 sync) are unverified against
  real credentials in this container — manual step, flagged.
