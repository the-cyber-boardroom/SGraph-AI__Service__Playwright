# Plan — SG-Compute S3-Twin Vault Container

> **PROPOSED — does not exist yet.** This packages an **existing** S3-compatible API
> (built in `SG-Compute__Spec__Storage-S3` / `SG_Send__Deploy`, the `Type__Twins`
> work) as an SG-Compute spec + Docker container, and adds the backend selection and
> credential mapping from the v0.33.33 brief. **The existing-code survey is still
> owed** (blocked on repo access — see §10); names/contracts below are the target
> shape and must be reconciled with `Type__Twins` before implementation.

---

## 1. Goal

Change *where files come from* without changing the consuming code. A container presents
a **boto3-transparent S3 API** (a "digital twin" of S3); any S3 client — boto3, AWS CLI,
osbot-aws, Memory-FS — is redirected by **pointing its `endpoint_url` at the container**.
Behind that identical front, the bytes are served from a **swappable backend**: vault, disk,
memory, or **real upstream S3**. The calling code cannot tell.

This is the vault-storage feature the project actually wants; it also **supersedes** the
`v0.2.64__cp-mitm-service__aws-credential-modes` workaround (§4.3).

---

## 2. Backend modes

| Backend | Source of bytes | Primary use |
|---------|-----------------|-------------|
| **vault** | SG/Send vault files served as S3 objects | the eventual point — governed, encrypted, versioned storage behind an S3 face |
| **disk** | local filesystem | dev / air-gapped / simplest |
| **memory** | in-process store | fastest, ephemeral, tests |
| **upstream-s3** ⭐ | **real AWS S3, authenticated with credentials available inside the EC2 instance (instance role via IMDS)** | transparent cache/proxy in front of an existing real bucket; **migration bridge**; removes AWS creds from downstream clients |

⭐ = the mode requested in this revision. Detailed in §4.

The S3-front is identical across all four (same v0.27.2 transparency contract); only the
byte source is selected at runtime.

---

## 3. The transparency contract (inherited from v0.27.2)

Non-negotiable: a boto3 client pointed at the twin has zero idea it is not real S3. That
means the container must already handle (these exist in `Type__Twins` — survey to confirm
coverage): SigV4 request signing, XML response + error formats, the AWS headers, and the
IAM/STS pre-flight calls boto3 makes (`STS GetCallerIdentity`, `S3 GetBucketLocation`).
The v0.27.2 call-log/discovery loop drives *which* operations to cover first.

**Credential-to-header mapping (v0.33.33):** the consuming client keeps using standard S3
credentials, but for the twin they carry routing/auth — the **AWS access-key → header name**,
**AWS secret → header value**. A standard S3 SDK stays happy (it just signs and sends), while
the twin reads the pair as its own auth header. This is transparent, out-of-band redirection:
no code cooperation from the consumer.

---

## 4. The `upstream-s3` mode — real S3 via in-instance credentials  ⭐ (this revision)

### 4.1 What it is
The twin runs **on the EC2 instance** and proxies (and optionally caches) to a **real upstream
S3 bucket**, authenticating to AWS with the **credentials already available inside the instance**
— i.e. the **EC2 instance role via IMDS** (no static keys, auto-refreshing), or forwarded
operator creds where present. Downstream clients talk plain S3 to the twin and supply **no AWS
credentials of their own** (or only the cred-as-header pair from §3).

### 4.2 How it works
```
downstream client ──S3(endpoint=twin)──▶ S3-Twin ──(instance role / IMDS)──▶ real AWS S3
   (no AWS creds)                          on EC2        boto3 default chain      (cache bucket)
```
- The twin builds its upstream S3 client via **boto3's default credential chain** — so the
  instance role (IMDS), or a task/exec role, or forwarded creds, all work and **auto-refresh**.
  (This is precisely the §5 guidance from the cp-mitm-service brief, but applied *once*, in the
  twin, instead of in every consuming service.)
- Operations are served from the upstream bucket; the v0.27.2 hybrid/cache modes let hot
  objects be backed by disk/memory in front of the upstream read.
- Region from `AWS_DEFAULT_REGION`/`AWS_REGION`; account derivable via STS at runtime.

### 4.3 Why this matters here — it dissolves the cp-mitm-service problem
The cp-mitm-service cache bucket is real upstream S3, and that service mishandles AWS creds
(it ignored the instance role and the session token — see the v0.2.64 cred brief). With this
mode:
- cp-mitm-service points `CACHE__SERVICE` S3 `endpoint_url` at the **twin** and supplies the
  cred-as-header pair (which it already requires as `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`).
- The **twin** reaches the real cache bucket using the **instance role** — the credential path
  we already proved works on the box.
- Net: **no AWS credentials on cp-mitm-service**, no static keys anywhere, the cred bug becomes
  irrelevant. The cred-modes brief drops to a fallback note.

### 4.4 IAM
The instance role needs read (and write, if the consumer writes) on the upstream bucket(s) —
the content_proxy `*-ec2-role` already has read on the cache bucket. No new principal; no static
secret. Same posture works from a **baked AMI** (each instance uses its own role).

## 5. How it slots into SG-Compute / content_proxy

- **As an SG-Compute spec** (mirrors `content_proxy` / `vault_app`): `manifest.py`
  (`spec_id='s3_twin'` or similar), `Type_Safe` schemas, a `Spec__CLI__Builder` CLI
  (`sg s3-twin …`), and a compose/user-data template. One Docker image, all deployment targets.
- **As a sidecar in the content_proxy stack**: add a `cp-s3-twin` service to the compose
  templates; set the consuming container's S3 `endpoint_url` to `http://cp-s3-twin:<port>` and
  its backend to `upstream-s3` (or `vault`). The `--backend` and upstream-bucket/endpoint become
  create options + `.env` keys (same single-source pattern as `CACHE__SERVICE__BUCKET_NAME`).
- **Backend selected at runtime** via env (`S3_TWIN__BACKEND=vault|disk|memory|upstream-s3`) +
  per-backend config (vault ref, disk path, upstream bucket/endpoint).

---

## 6. Acceptance criteria

1. A boto3 client / AWS CLI / osbot-aws against the twin's `endpoint_url` performs
   Put/Get/Head/List unmodified (the v0.27.2 acid test).
2. Backend is selectable at runtime: **vault | disk | memory | upstream-s3**.
3. **upstream-s3**: the twin reads/writes the real bucket using the **EC2 instance role
   (IMDS)** with **no static keys**, and **auto-refreshes** past the ~6h credential expiry.
4. A downstream consumer (e.g. cp-mitm-service) works against the twin with **no AWS
   credentials of its own**, supplying only the cred-as-header pair.
5. The vault backend serves vault files transparently as S3 objects.
6. Unimplemented operations return correct AWS XML error format (not a 500/HTML).
7. The consumer's code is unchanged; only `endpoint_url` (and the cred-as-header pair) differ.
8. Works identically from a baked AMI.
