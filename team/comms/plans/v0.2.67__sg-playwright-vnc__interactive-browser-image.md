## 1. Why we are stepping back

The v0.2.65 plan wired `jlesage/firefox` containers into the content_proxy stack
(`cp-firefox-{i}` at `/browser/firefox/{i}`). It worked — the browser proxied
through mitmproxy and rendered transformed content — but every integration point
fought us because **we do not control that image**:

| Pain (all hit in production testing) | Root cause |
|---|---|
| `SECURE_CONNECTION=1` 307 loop | jlesage's own TLS layer fighting our edge |
| noVNC breaks under `/browser/firefox/{i}` sub-path | jlesage's baseimage-gui emits root-absolute URLs; not ours to fix |
| certutil NSS-lock boot hang (`preparing Firefox 2 profile`) | CA trust had to be injected into a foreign profile DB from the host |
| user.js proxy config from the host | no API; file-poking a foreign layout |
| Firefox only | second image + second integration for Chrome |

Meanwhile **sg-playwright already solves the hard parts** in code we own:

- `Browser__Launcher.build_launch_kwargs()` already honours
  `SG_PLAYWRIGHT__DEFAULT_PROXY_URL` — every launched browser goes through
  mitmproxy-int with zero profile hacking.
- `Page__Factory` already honours `SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS` — the
  mitmproxy CA problem (the certutil hang) **does not exist** on this path.
- `Schema__Browser__Config.headless` already exists — headed launch is a flag,
  not a feature.
- The base image (`mcr.microsoft.com/playwright/python:v1.58.0-noble`) ships
  **Chromium, Firefox AND WebKit** with all system deps.

The only thing missing is a screen to draw on and a way to look at it.

## 2. Proposal

A new image variant, **`diniscruz/sg-playwright-vnc`**, built FROM the existing
sg-playwright Dockerfile output plus a thin desktop layer:

```
sg-playwright (FastAPI :8000, Browser__Launcher, Step__Executor)   ← unchanged
  + Xvfb        (virtual X display :99)
  + openbox     (minimal window manager — windows get borders/move/close)
  + x11vnc      (VNC server exposing :99, localhost-only)
  + noVNC + websockify  (browser-based VNC client on :6080)
  + supervisord (starts the four above + the FastAPI service)
```

Ports: `8000` (existing API), `6080` (noVNC web client). VNC `5900` stays
container-internal (only websockify talks to it).

One env flag drives the mode:

- `SG_PLAYWRIGHT__DISPLAY_MODE=headless` (default) → today's behaviour, X stack
  not started. The base image and existing deployments are untouched.
- `SG_PLAYWRIGHT__DISPLAY_MODE=vnc` → supervisord starts Xvfb/openbox/x11vnc/
  noVNC; `DISPLAY=:99` is exported; `Browser__Launcher` defaults `headless=False`.

### 2.1 The unlock nobody else offers

Because the API and the display share one container, the **same browser** is
reachable both ways:

1. **Interactive** — user opens noVNC, drives a headed browser by hand through
   the mitmproxy (the jlesage use case, minus the pain).
2. **Watched automation** — a `/sequence` or `/pw` API call launches headed;
   the user literally watches the steps execute live in noVNC.
3. **Hybrid / takeover** — automation navigates + logs in, human takes the
   mouse; or human navigates somewhere, automation continues. This is the
   feature path for "customise the browser UI, theme, bookmarks": all of it
   becomes API endpoints on a service we already own.

### 2.2 Browser start for the interactive case

A headed browser must exist before the user connects. Small addition to the
service (PROPOSED):

- `POST /desktop/browser` `{engine: chromium|firefox, start_url}` — launches a
  headed browser on `:99` via the existing `Browser__Launcher` (kept alive as a
  session, not per-request).
- `SG_PLAYWRIGHT__AUTOSTART_BROWSER=chromium|firefox` — boot-time convenience:
  container starts with a browser already open (content_proxy uses this).

Engine per container is an env choice, not an image choice — **one image serves
both the Chrome and Firefox requests** from the original ask.

## 3. content_proxy integration (replaces the jlesage fleet)

- Compose: `cp-browser-{i}` from `sg-playwright-vnc` with
  `SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy-int:8080`,
  `SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS=true`,
  `SG_PLAYWRIGHT__DISPLAY_MODE=vnc`, `SG_PLAYWRIGHT__AUTOSTART_BROWSER=…`.
  No host profile dir, no certutil boot block, no CA wait loop — the whole
  `_firefox_block` in the user-data builder collapses to nothing.
- Edge: `handle_path /browser/{i}/* → cp-browser-{i}:6080`. Vanilla noVNC uses
  relative asset paths and a configurable websockify path, so sub-path routing
  is solvable in config we control (test in P1 before wiring).
- CLI: `--firefox N` becomes `--browsers N` (`--browser-engine chromium|firefox`);
  old flag kept as an alias during transition.
- Diagnose: `cp-browser-{i}` in `expected_containers`; the boot-ok Firefox-prep
  tolerance becomes dead code once `_firefox_block` is gone.

## 4. Customization roadmap (the "next features" this unblocks)

All PROPOSED, all natural Type_Safe endpoints once the browser is ours:

| Feature | Mechanism |
|---|---|
| Bookmarks | launch persistent context with a prepared profile; or CDP/`places.sqlite` written by the service pre-launch |
| Theme / UI chrome | Chromium `--force-dark-mode`, managed policies JSON; Firefox `user.js` + `userChrome.css` written by the service (our profile, no lock race — browser not yet started) |
| Start page / kiosk | `--kiosk`, `--app=<url>` launch args (already supported via `launch_args`) |
| Locale / timezone / viewport | existing `Schema__Browser__Config` surface |
| Session save/restore | persistent context dir per user, S3 sync (ties into the vault/S3-twin work) |

## 5. Phases

**P1 — image spike (no service changes)**
Dockerfile.vnc + supervisord conf. Manual verify: `docker run`, open `:6080`,
see openbox; `docker exec` a headed `playwright open` on `:99`, drive it in
noVNC. Verify noVNC under a path-stripping reverse proxy (the sub-path
question) with a throwaway Caddy. Exit criteria: image < ~2.5 GB, cold start
< 10 s, noVNC usable behind a sub-path.

**P2 — service awareness**
`SG_PLAYWRIGHT__DISPLAY_MODE`, `DISPLAY` export, `headless` default flip in vnc
mode, `POST /desktop/browser` + autostart. Tests: in-memory for the config
plumbing; gated real-Chromium test that a headed launch succeeds under Xvfb
(CI runner has no display → the Xvfb in the image provides it).

**P3 — content_proxy switch**
Compose/user-data/edge/CLI/diagnose changes from §3. Delete `_firefox_block`.
EC2 validation: `sg content-proxy create --browsers 2 --with-aws-dns --wait`.

**P4 — customization endpoints** (bookmarks/theme/profile — separate brief once
P3 is live and the exact asks are prioritised).

## 6. Risks / open questions

- **Image size**: base is already ~2 GB; X stack adds ~150–300 MB. Acceptable —
  same EC2 pulls it once.
- **Memory**: a headed Chromium ≈ 300–500 MB/user. `t3.large` (8 GB) fits ~4–6
  interactive browsers + stack. Document per-count instance-type guidance.
- **`--single-process` / `--disable-gpu` defaults** were tuned for Lambda;
  headed mode needs its own default arg set (drop `--single-process`, likely
  keep `--no-sandbox` as root-in-container, add `--start-maximized`).
- **noVNC auth**: :6080 is unauthenticated inside the docker network; the edge
  gate (`--edge-auth`, already built) is the auth story — must be default-ON
  for browser routes when this ships.
- **WebSocket through the edge**: Caddy proxies WebSockets natively; needs an
  explicit P1 test through the sub-path.
- **Keep vs kill the jlesage path**: proposal — keep `--firefox` working until
  P3 lands, then remove in one commit (fleet is ephemeral, nothing persists).
- **TLS-by-IP at the edge** is orthogonal and still open (browsers send no SNI
  for IPs). Tracked separately: cert-init letsencrypt-ip certs mounted into
  Caddy, or auto-`sslip.io` hostname. Not this plan's problem.
