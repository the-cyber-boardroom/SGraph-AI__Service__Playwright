# Proposal — interactive remote-browser sidecar (`/browser`) for content_proxy

> **One line.** Add a real Firefox/Chrome running in the stack, viewed over **noVNC through the
> existing edge**, browsing through the **existing `mitmproxy-int`** — the *interactive human twin*
> of `/pw` (which is the *automated* Playwright twin). Same network position, same proxy, same CA.

---

## 0. Decisions locked (2026-07-03)

| # | Decision | Consequence |
|---|----------|-------------|
| Route | **`/browser`**, and a **fleet** — one container per user (a browser serves one session). Path is **`/browser/{engine}/{n}`** — `engine ∈ {chrome, firefox}`, `n = 1..N`. | The compose renders N firefox + M chrome services; the edge generates one route per container. |
| Engines | **Both** — Chrome *and* Firefox, per-index. `/browser/firefox/1`, `/browser/chrome/1`, `/browser/firefox/2`, … | Counts per engine (`--firefox N --chrome M`); container `cp-{engine}-{n}`. |
| CA | **mitmproxy's own self-generated CA** (from `/opt/content-proxy/certs`) — the one the local mitmproxy is already using. | No `--ca-from-local`; the browser installs the box's `mitmproxy-ca-cert.pem`. |
| Auth | **Same gate as `/pw`** — if a user can reach `/pw`, they can reach `/browser/*`. | Reuse the access-token set-cookie gate at the edge over the whole `/browser/*` tree. |
| Persistence | **Fully ephemeral** — no profile volumes; wiped on stop; every new instance is fresh. | No volumes on the browser services; matches `vnc`/`neko` behaviour. |

## 1. Why this drops in cleanly

`/pw` and the new `/browser` are the same shape — a client on `cp-net` that routes through
`mitmproxy-int` and is reached remotely through the edge:

| | client | how it browses | reached via |
|---|--------|----------------|-------------|
| **`/pw`** (today) | sg-playwright (headless, programmatic) | `SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy-int:8080` | edge → `sg-playwright:8000` |
| **`/browser`** (new) | real Firefox/Chrome (interactive, human) | `HTTP(S)_PROXY=http://mitmproxy-int:8080` | edge → noVNC (`:5800`/`:3000`) |

`mitmproxy-int` is **no-auth, internal** (`proxy_command(..., with_proxyauth=False)`), so the browser
sidecar points at it with no credentials — identical to sg-playwright. The mitmproxy CA already lives
at `/opt/content-proxy/certs`. So the user browses in the remote window, traffic flows through
mitmproxy, the mitm-service injects its transform, and the human sees the proxied/transformed content
live — the interactive version of the `/pw` workflow.

## 2. Chrome vs Firefox — which is easier (the headline)

**Firefox is materially easier, and the in-repo evidence proves it.** The two halves of the job are
*proxy injection* (easy for both) and *CA trust* (the hard part — the browser must trust mitmproxy's
self-signed CA or every HTTPS page throws a warning).

| | **Firefox** (jlesage / LinuxServer) | **Chrome/Chromium** (LinuxServer) |
|---|---|---|
| Proxy | `user.js` → `network.proxy.*` (simple) | `HTTP(S)_PROXY` env / `--proxy-server` (simple) |
| **CA trust** | ✅ **already solved in-repo** — `firefox` spec installs `nss-tools`, waits for `mitmproxy-ca-cert.pem`, `certutil -A -n "mitmproxy CA" -t "TCu,,"` into the profile NSS DB. Copy-paste. | ⚠️ **not wired anywhere** — Chromium uses the OS/NSS *system* store; needs `update-ca-certificates` or a managed-policy JSON. The `vnc` spec never did this and falls back to ignore-cert-errors, which is unreliable/insecure for an interactive session. |
| noVNC port | `5800` | `3000` |
| Interactive UX with HTTPS interception | ✅ warning-free | ⚠️ cert warnings unless the system-store install is added |
| Verdict | **MVP** | **Phase 2** |

**Recommendation: ship Firefox first** (clean, warning-free CA trust via the existing `certutil`
recipe), then add Chrome once the container installs the mitmproxy CA into its system trust store.
Both are the *same wiring* into content_proxy — only the container image + CA-install step differ.

**Why not Neko (WebRTC)?** The `neko` spec is WebRTC over **UDP 52000-52100 open to the world**, with
**no proxy and no CA** story — it doesn't fit a single-edge sidecar and would need proxy/CA built from
scratch. noVNC (all traffic over the `:443` WebSocket) fits the content_proxy edge model. Skip Neko.

## 3. Architecture / wiring — a browser fleet

The compose renders **one service per (engine, index)**; the edge renders **one route per service**.
Both are generated from the per-engine counts (`--firefox N --chrome M`).

**(a) Compose services** — a `browser_block(firefox_count, chrome_count)` injector (mirrors
`edge_block()`/`cert_init_block()`, wired through `render()` + the test-locked `PLACEHOLDERS`) emits, for
each engine `e` and index `i`:
```yaml
  cp-firefox-1:                       # cp-{engine}-{i}
    image: jlesage/firefox            # firefox → jlesage/firefox (noVNC :5800); chrome → lscr.io/linuxserver/chromium (:3000)
    container_name: cp-firefox-1
    environment:
      - HTTP_PROXY=http://mitmproxy-int:8080          # the no-auth internal proxy sg-playwright already uses
      - HTTPS_PROXY=http://mitmproxy-int:8080
    volumes:
      - ${CONTENT_PROXY__CA_DIR:-./certs}:/certs:ro    # mitmproxy's own self-generated CA
    networks: [cp-net]
    depends_on: [mitmproxy-int]
    restart: unless-stopped           # NO volume for profile state → fully ephemeral
```
plus a per-container init that installs **mitmproxy's self-generated CA** (`certutil -A` for Firefox;
system-store for Chrome) after a short wait for `/certs/mitmproxy-ca-cert.pem` — the `firefox` spec's
exact recipe. (Decision: use the box's own mitmproxy CA, not `--ca-from-local`.)

**(b) Edge routes** — `Content_Proxy__Edge__Template.ROUTE_BODY` gains one generated block per container,
above the catch-all `handle`:
```
handle_path /browser/firefox/1/* { reverse_proxy cp-firefox-1:5800 }
handle_path /browser/chrome/1/*  { reverse_proxy cp-chrome-1:3000 }
handle_path /browser/firefox/2/* { reverse_proxy cp-firefox-2:5800 }
...
```
Non-caddy path: append each to the vault override's route var
(`…,browser/firefox/1=http://cp-firefox-1:5800,…`) — verify N-route parsing in `Fast_API__Reverse_Proxy`.
The whole `/browser/*` tree sits behind the **same access-token gate as `/pw`** (decision 4).

**(c) ⚠️ The one real technical wrinkle — noVNC under a sub-path.** `handle_path` strips
`/browser/firefox/1`, so the container receives `/`. But a noVNC page loaded at
`https://host/browser/firefox/1/` requests its assets and its **WebSocket** at absolute paths
(`/websockify`, `/app/…`) — which hit the host root and miss the container. Serving *many* noVNC
instances under distinct sub-paths therefore needs the browser image to emit **relative** URLs / honour a
base-path. **This is another point in Firefox's favour:** jlesage's `baseimage-gui` (v4+) documents
reverse-proxy-under-a-subfolder and uses relative paths + `X-Forwarded-*`, so `/browser/firefox/{n}/`
works with a `header_up X-Forwarded-*` on the reverse_proxy. LinuxServer/Selkies Chromium subpath support
is more finicky. If sub-path proves painful for an engine, the fallback is a **sub-domain per container**
(`firefox-1.<stack>.sg-compute.sgraph.ai`) — clean for noVNC but needs a **wildcard cert** (DNS-01), i.e.
more infra. Recommendation: prove the sub-path model with Firefox first; treat Chrome sub-path (or the
wildcard-subdomain fallback) as phase 2.

**(d) Resource sizing.** Each container is a full browser + Xvfb + noVNC (~0.5–1 GB RAM, real CPU under
use). A `t3.large` (2 vCPU / 8 GB) realistically hosts ~2–4 concurrent browsers. The create banner /
`info` should surface the per-engine counts, and `create` should sanity-check counts against
`instance_type` (or at least warn). Bigger fleets → bigger box.

## 4. Auth / security

The noVNC surface is a **full interactive browser** — it must be gated (more than `/pw`, which is an
API). Layers, cheapest first:
- **Edge auth** — put `/browser/*` behind the same access-token gate as the vault (Caddy `forward_auth`
  or the set-cookie token), so only an authed operator reaches the noVNC page.
- **Image auth** — the jlesage/LinuxServer images support `WEB_AUTHENTICATION` basic-auth; the standalone
  `vnc` spec uses a full caddy-security portal. Reuse one.
- Internal only otherwise — the browser uses `mitmproxy-int` (no-auth, net-local); `block_global` and
  proxyauth are irrelevant here. Browser state is wiped on stop (no host volume), like the `vnc` spec.

## 5. Recommended MVP (one PR)

1. **Firefox fleet, Caddy-edge only** (simplest, cleanest CA trust + the only engine with proven
   subpath-noVNC).
2. **`--firefox N`** create option (default `0`) → renders `cp-firefox-1..N` + a
   `/browser/firefox/{i}/*` Caddy route each, via a `browser_block()` injector.
3. Per-container CA-trust init (`certutil`, mitmproxy self-gen CA) copied from
   `Firefox__User_Data__Builder`; browsers point at `mitmproxy-int:8080`; **no volumes** (ephemeral).
4. `/browser/*` behind the **same access-token gate as `/pw`**.
5. `info` / banner surface the count + the per-browser URLs; a soft warn if `N` looks big for the
   `instance_type`.
6. Pure-render templates + regenerate the committed compose/Caddyfile + drift guards + unit tests
   (assert N services + N routes render, proxy env + CA mount present, ext/int proxy unaffected, counts
   drive the fleet).

**Phase 2:** **`--chrome M`** (Chrome fleet — add the system-store CA install, and prove Selkies subpath
or fall back to a wildcard-subdomain), the non-caddy `edge=none` routes, and an admin-UI iframe pane per
browser (reuse the `IFRAME_EMBED` precedent from the `vnc`/`firefox` UI detail views).

MVP (Firefox + Caddy) is a small, well-bounded PR — nearly all of it is lifting existing recipes.

## 7. Open questions

**Resolved (§0):** route = `/browser/{engine}/{n}` fleet · both engines · mitmproxy self-gen CA ·
`/pw`-equivalent auth · fully ephemeral.

**Remaining (technical, to settle during MVP):**
1. **noVNC sub-path** (§3c) — confirm jlesage Firefox serves cleanly under `/browser/firefox/{n}/` via
   Caddy `handle_path` + `X-Forwarded-*`. If an engine won't, decide sub-path-with-rewrites vs
   wildcard-subdomain (needs DNS-01 wildcard cert).
2. **Count option shape** — `--firefox N --chrome M` (proposed) vs a single `--browsers firefox:2,chrome:1`.
3. **Fleet vs `instance_type`** — hard cap, or soft warn only? What default box for N>2?
4. **WebSocket + auth interplay** — the access-token set-cookie gate must also cover the noVNC
   **WebSocket** upgrade (`/websockify`), not just the HTML — verify the cookie rides the WS handshake.
5. **Lifecycle** — can browsers be added/removed without recreating the stack (scale the fleet), or is the
   count fixed at `create`? (MVP: fixed at create; dynamic scaling is a later nicety.)
