# SG/Sentinel — adding LLM chat to the TUIs

## The principle (from the mockups brief)

> The TUI is the visual surface; the chat is the conversational surface; **both are
> views of the same API.** Chat must be grounded in the real, current state.

So we do not bolt an LLM onto each screen. We expose each Sentinel surface as a
**TUI API** (structured, addressable actions) and let an LLM drive that API. The
visual screen and the chat are then two clients of one provider.

## What already exists (we reuse, not rebuild)

| Piece | Where | Role |
|-------|-------|------|
| Tool-API framework | `cli/tui/tool_api/` | `Tui_Api__Provider` (manifest of `Schema__Tui_Api__Action` + `dispatch`), `Tui_Api__Registry`, `Tui_Api__Execution_Center` (gates + change-log + dry-run + cost), `Tui_Api__Schema__Builder` (Type_Safe params → JSON Schema), `Tui_Api__Privilege__Resolver`, `make_tui_api_app` (`… tui api` CLI), `Tui_Api__Explorer` screen, `Tui_Api__Contract__Asserts` |
| Chat engine | `cli/tui/chat/` | `Chat__Engine.send_turn_agentic(session, text, center)` — **already does agentic tool-calling against an execution center**; `Chat__Tool__Builder`; session/turn/usage schemas; `Chat__Backend__In_Memory` (scripted, for tests) |
| Real LLM backend | `aws/bedrock/chat/Chat__Backend__Bedrock.py` | Nova via Bedrock Converse (+ streaming usage/cost) — the production chat backend |
| Chat widgets | bedrock chat TUI | `Chat__Bubble / Composer / Cost__Meter` — reusable chat pane widgets |
| Working precedent | `sg_compute_specs/sg_edge/tui/tui_api/SG_Edge__Tui_Api__Provider.py` | A full provider: read actions READ_ONLY, mutations WRITE/DESTRUCTIVE gated by preconditions + the center; registered + exposed as `sg edge tui api`. **We mirror this exactly.** |
| Sentinel data layer | `sentinel/tui/source/Sentinel__TUI__Source.py` | Already the read seam the screens use — the provider delegates to it (owns no logic) |

## The plan — four phases

### Phase A — `Sentinel__Tui_Api__Provider` (programmatic, no LLM)
Mirror `SG_Edge__Tui_Api__Provider`. New `sentinel/tui/tui_api/`:
- `Sentinel__Tui_Api__Provider(Tui_Api__Provider)` — `manifest()` lists the actions
  (below); `dispatch(action, params)` delegates to `Sentinel__TUI__Source` (reads) and
  the deploy/local services (mutations); `state()` exposes `node_available`,
  `has_deployment`, counts (drives preconditions); `skills()` returns the
  human/api/driver markdown.
- One `Schema__…__Params__*` Type_Safe class per action that takes args (rule id,
  request id, ip, url, repeat) → `Tui_Api__Schema__Builder` turns it into JSON Schema.
- Register in `Cli__Sentinel__Tui` via `Tui_Api__Registry().register(provider)` and
  mount `make_tui_api_app(registry)` as `sg sentinel tui api`.
- Tests: `Tui_Api__Contract__Asserts` + dispatch over an in-memory sink (no mocks).

**Action catalogue** (tier in brackets):

| Surface | Action | Tier | Delegates to |
|---------|--------|------|--------------|
| rules   | `rules_list`, `rule_show {rule_id}`, `rules_test` | READ_ONLY | registry / L1 source |
| logs    | `logs_list {limit}`, `logs_trace {request_id}` | READ_ONLY | sink |
| blocks  | `blocks_list`, `blocks_why {needle}` | READ_ONLY | sink |
| status  | `status`, `engine_code` | READ_ONLY | source + L1 materialiser |
| traffic | `traffic_cases`, `traffic_gen {repeat}` | READ_ONLY (no AWS side-effects) | generator (local) |
| traffic | `traffic_send {url, repeat}` | WRITE (egress) | generator (http) |
| deploy  | `deploy_status` | READ_ONLY | deployer.status() |
| deploy  | `deploy_create {region}`, `deploy_destroy {id}`, `deploy_teardown {id}` | DESTRUCTIVE | deployer (mutation-gated) |

Mutations carry a `precondition` (`SG_AWS__SENTINEL__ALLOW_MUTATIONS=1` / `node_available`)
and `supports_dry_run=True`; the execution center enforces scope + confirm + records a
change-log entry, exactly as for `sg edge`.

### Phase B — chat backend wiring (no UI yet)
- A thin `Sentinel__Chat` helper: `Chat__Engine` + `Tui_Api__Execution_Center` over the
  registered provider. Default backend `Chat__Backend__Bedrock` (Nova); inject
  `Chat__Backend__In_Memory` in tests.
- `engine.send_turn_agentic(session, text, center)` already loops tool-calls → the LLM
  can answer "why was 185.x.x.x blocked?" by calling `blocks_why`, or "show rule 0012"
  by calling `rule_show`. Grounded by construction (tools read live state).
- CLI: `sg sentinel tui chat "<question>"` (one-shot, pipe-friendly) for headless use.
- Tests: scripted in-memory backend asserts the right tool was called + the answer
  contains the real value — no network, no mocks.

### Phase C — chat pane in the screens
- Add a `Sentinel__TUI__Chat__Pane` (reuse the bedrock `Chat__Composer/Bubble` widgets):
  a `:` / `c` keybinding toggles a docked input + transcript on any Sentinel screen.
- The pane shares the screen's source/provider, so a question is answered against the
  exact data on screen; tool results can also re-drive the screen (e.g. chat "trace
  sn-abc" focuses that record).
- No-TTY: chat is a TTY-only affordance; piped use goes through `tui chat` / `tui api`.

### Phase D — actions that mutate, behind the gates
- Wire `deploy_create/destroy/teardown` + `traffic_send` as WRITE/DESTRUCTIVE actions so
  "tear down the test distribution" works from chat — but only through the execution
  center's confirm + mutation gate + change-log (never a raw call). Cost (Bedrock
  tokens + any AWS spend) is surfaced via the existing `Cost__Meter`.

## Safety model (inherited from tool_api)
- **Read vs mutate is explicit** (action `tier`); the chat can read freely, but every
  mutation goes through `Tui_Api__Execution_Center` → scope check → precondition
  (`node`/mutation-gate) → confirm → `Tui_Api__Change_Log`. Same gate as the CLI.
- **Grounding, not guessing**: the LLM only sees tool outputs (real state), never
  fabricates rule/verdict data — consistent with the reality-doc principle.
- **Least privilege**: load only the actions a session needs (`Tui_Api__Loadout`).

## Effort / sequencing
A (provider + `tui api`) is the keystone and is self-contained — do it first (≈ the
size of the sg_edge provider slice). B + C are small once A exists (the engine + widgets
are done). D is gated and last. A can ship and be tested with zero LLM/network.
