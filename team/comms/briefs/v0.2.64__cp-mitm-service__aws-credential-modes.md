# Brief — cp-mitm-service: support the 3 AWS credential modes

> **Ask in one line:** make the MITM service resolve AWS credentials through boto3's
> **default provider chain** so it works with an **instance/task role (no keys)**, with
> **static long-lived keys**, and with **temporary STS credentials (with session token)** —
> instead of only working when explicit long-lived `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`
> are present.

---

## 1. TL;DR

The MITM service reads its S3 cache bucket (`CACHE__SERVICE__BUCKET_NAME`) using AWS
credentials. Today it **only** works when the container is given explicit
**long-lived** static keys (`AKIA…`). It does **not** work via the EC2 instance role
(IMDS), and it does **not** work with temporary credentials that carry an
`AWS_SESSION_TOKEN`. That forces operators to forward long-lived secrets onto every
box — the exact anti-pattern the instance-role design exists to avoid.

We proved the instance role is fully capable (see §3). The fix is to let boto3 resolve
credentials normally rather than reading specific env vars and constructing clients with
them.

---

## 2. Context — where this bites

- `cp-mitm-service` (image `diniscruz/mgraph-ai-service-mitmproxy`) runs as one container
  in the content_proxy stack and uses S3 for its content cache
  (`CACHE__SERVICE__BUCKET_NAME`, e.g. `akeia--mgraph-ai-cache`).
- In production the container runs on an **EC2 instance with an instance profile**
  (`playwright-ec2`) that already has read access to that bucket. The same image is meant
  to run on a laptop, in CI, on Fargate, and on Lambda — each with a *different* credential
  source. That portability only works if the service uses the standard credential chain.

---

## 3. The problem — current behaviour + evidence

Inside a running `cp-mitm-service` container on EC2 (instance profile `playwright-ec2`):

**The instance role works — proven with boto3's default chain (no env keys):**
```python
# run inside the container, with AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY EMPTY:
import boto3
boto3.client('sts').get_caller_identity()
# -> Arn: arn:aws:sts::504558652080:assumed-role/playwright-ec2/i-0c9f04...
boto3.client('s3').head_bucket(Bucket='akeia--mgraph-ai-cache')   # -> 200 OK
boto3.client('s3').list_objects_v2(Bucket='akeia--mgraph-ai-cache', MaxKeys=5)  # -> objects listed
```
So: the container **can** reach IMDS, the role **is** assumable, and it **has** S3 access.

**But the MITM service itself only works when given explicit long-lived keys:**
```
AWS_ACCESS_KEY_ID=AKIA...            # long-lived IAM user key
AWS_SECRET_ACCESS_KEY=...
```
- With `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` **empty/unset** (the default — the
  container would then resolve the role via IMDS, as shown above) → the service's S3 access
  fails.
- With **temporary** credentials injected (`AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` +
  `AWS_SESSION_TOKEN` from the instance role) → still fails.

**Conclusion:** the service is not using boto3's default credential chain. It is most likely
reading specific env vars and building its S3 client from them explicitly — which (a) ignores
IMDS/role credentials, (b) ignores `AWS_SESSION_TOKEN`, and (c) can be broken outright by the
empty-string values that the orchestration injects (see §5).

---

## 4. Required behaviour — the 3 modes

The service must work, unchanged, in all three of these, selected purely by which env vars
are present:

| # | Mode | Env provided | Primary use |
|---|------|--------------|-------------|
| **1** | **Ambient role** (default) | *No* `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | EC2 instance role, Fargate task role, Lambda exec role — **the production default**. Credentials come from IMDS / container creds and **auto-refresh**. |
| **2** | **Static long-lived keys** | `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` | Laptop / CI with an IAM user key. |
| **3** | **Temporary STS creds** | `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` + **`AWS_SESSION_TOKEN`** | Forwarded `sts assume-role` / SSO / instance-role creds. |

Region comes from `AWS_DEFAULT_REGION` / `AWS_REGION` (already provided).

---

## 5. Root cause & implementation guidance

**The fix is almost always "stop being clever about credentials".**

1. **Build clients from a default session, not from explicit env reads.** Prefer:
   ```python
   import boto3
   s3 = boto3.client("s3")          # botocore resolves: env -> shared config -> container -> IMDS
   ```
   or a shared `boto3.session.Session()`. This single change gives you all three modes for
   free, **and** auto-refreshes role/temporary credentials (no expiry handling needed).

2. **If you must read env explicitly, do it correctly:**
   - Treat **empty strings as unset** — `os.environ.get("AWS_ACCESS_KEY_ID") or None`. The
     orchestration injects `AWS_ACCESS_KEY_ID=${AWS_ACCESS_KEY_ID:-}`, which becomes an
     **empty string** in the container; passing an empty access key to
     `boto3.client(..., aws_access_key_id="")` breaks credential resolution instead of
     falling through to the role.
   - **Always pass `aws_session_token`** too (`AWS_SESSION_TOKEN`), or temporary creds (mode 3)
     can't work.
   - Better: don't pass any of them — see (1).

3. **Don't hard-require `AWS_ACCOUNT_ID`.** If the service needs the account number, derive it
   at runtime (`boto3.client("sts").get_caller_identity()["Account"]`) or make it optional.
   content_proxy now sets `AWS_ACCOUNT_ID` for convenience, but the service must not fail when
   it is absent.

4. **Add a one-line startup log of the resolved credential source** (without leaking secrets) —
   e.g. `creds: resolved via <provider> (arn=arn:aws:sts::…:assumed-role/playwright-ec2/…)`.
   The absence of this is what turned a 1-line config issue into a multi-hour live debug.

## 6. Acceptance criteria

A test matrix (the bucket must be readable in ✅ rows; ❌ row must fail *clearly*):

| Env in container | Expected |
|------------------|----------|
| no `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, IMDS/role available | ✅ works (mode 1) |
| `AWS_ACCESS_KEY_ID=""` + `AWS_SECRET_ACCESS_KEY=""` (empty strings), IMDS available | ✅ works — empty treated as unset (mode 1) |
| long-lived `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` | ✅ works (mode 2) |
| `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` + `AWS_SESSION_TOKEN` (temp) | ✅ works (mode 3) |
| no credentials resolvable anywhere | ❌ fails with a clear error naming the bucket and "no AWS credentials resolved" |
| `AWS_ACCOUNT_ID` absent | ✅ still works (account derived or unused) |

Plus: with mode 1, a long-running service must keep working **past the ~6h credential
expiry** (botocore's default-chain providers auto-refresh; explicitly-passed static creds do
not — another reason to prefer (1)).

---

## 7. What content_proxy has already done on its side (the integration contract)

So the two sides meet in the middle — already shipped on `claude/trusting-franklin-fza33n`:

- The EC2 instance runs with the **`playwright-ec2` instance profile** (S3 read on the cache
  bucket — verified).
- The box `.env` now always sets **`AWS_ACCOUNT_ID`** (derived from the deploying account) and
  **`AWS_DEFAULT_REGION`**, and inherits **`CACHE__SERVICE__BUCKET_NAME`** from the operator's
  local `.env`.
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` are **left unset by default** (only populated
  by the explicit `--forward-aws-creds` path). Once mode 1 works, that path becomes optional.

Open follow-up on our side once mode 1 lands: stop injecting the empty
`AWS_ACCESS_KEY_ID=${AWS_ACCESS_KEY_ID:-}` / `AWS_SECRET_ACCESS_KEY=${…:-}` lines into the
mitm-service container env entirely (cleaner than relying on "treat empty as unset"). We'll
keep the empty-string passthrough until you confirm the service tolerates it.

---

## 8. Out of scope

- No change to *what* the cache does or its bucket layout — only **how credentials are
  obtained**.
- content_proxy will not forward long-lived keys as the default once mode 1 works.
