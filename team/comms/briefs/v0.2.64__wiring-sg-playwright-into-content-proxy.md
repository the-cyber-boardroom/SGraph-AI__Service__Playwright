# Wiring sg-playwright into content_proxy — what to change and verify

## 0. TL;DR

sg-playwright is **already** the 4th service in the content_proxy compose
(`Content_Proxy__Compose__Template.py:269-281`), reached through the internal no-auth
mitmproxy and fronted by `/pw`. You are **not** adding it — you are **re-pinning it to the
v0.2.64 image and threading through the new capabilities**. Four concrete changes + a
verification pass. Nothing here needs sg-playwright source edits; it's all content_proxy-side
config plus one `/pw`-edge decision that fixes a live bug the onboarding team hit.

## 1. What sg-playwright now provides (v0.2.64) that the stack should light up

| Capability | How the stack uses it |
|---|---|
| **`set_cookie` step verb** (stateless per-request context cookie) | The onboarding pipeline's `mitm-mode=inject` cookie becomes a step in `/pw/sequence/execute`: `set_cookie → navigate → screenshot`. Answers the handoff Q8/Q9 without always-on injection. |
| **`js_evaluate_enabled` capability + `SG_PLAYWRIGHT__JS_ALLOW_ALL` / `SG_PLAYWRIGHT__JS_ALLOWLIST_FILE`** | Lets an **internal** content_proxy stack open `evaluate` for recon (`FilterDebug`, mutation counter) while the customer stack stays deny-all. See §3. |
| **Health fix** (`healthy` no longer vault-gated; real `chromium_version`) | `/pw/health/status` and the console badge now read `healthy` + `chromium 148.x` instead of `degraded · 0.0.0`. |
| **`/test-pages/*` fixtures + the console** | Self-contained smoke targets reachable through `/pw` for the stack's own health checks. |

## 2. Change 1 — pin the image tag (do NOT ship `:latest`)

`Content_Proxy__Compose__Template.PLAYWRIGHT_IMAGE = 'diniscruz/sg-playwright'` and
`Schema__Content_Proxy__Create__Request.playwright_image` default to the untagged ref → Docker
pulls `:latest`, which is whatever was last published — non-reproducible, and today predates
every v0.2.64 feature above.

- **Pin to the published v0.2.64 tag** (`diniscruz/sg-playwright:v0.2.64`) in the Create__Request
  default and the compose default, once the sg-playwright branch is merged and the
  `push-playwright-manifest` CI job has published that tag. (The image only carries these
  features **after** that publish — `sp docker`/content_proxy pull the Hub tag, not this branch.)
- Keep it a `--playwright-image` override so an internal stack can point at a newer tag.

## 3. Change 2 — thread the script-exec env through (internal variant only)

The sg-playwright compose block hardcodes four env vars (`Compose__Template.py:272-276`). Add
**optional** passthrough for the two script toggles so an internal onboarding stack can enable
`evaluate` via its `.env`, while the customer stack (vars unset) stays deny-all:

```yaml
  sg-playwright:
    environment:
      - SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy-int:8080
      - SG_PLAYWRIGHT__IGNORE_HTTPS_ERRORS=true
      - FAST_API__AUTH__API_KEY__NAME=${{FAST_API__AUTH__API_KEY__NAME:-x-api-key}}
      - FAST_API__AUTH__API_KEY__VALUE=${{FAST_API__AUTH__API_KEY__VALUE}}
      - SG_PLAYWRIGHT__JS_ALLOW_ALL=${{SG_PLAYWRIGHT__JS_ALLOW_ALL:-}}          # add — empty = deny-all
      - SG_PLAYWRIGHT__JS_ALLOWLIST_FILE=${{SG_PLAYWRIGHT__JS_ALLOWLIST_FILE:-}} # add — empty = deny-all
```

- Add both to `.env.example` commented-out with a security note (they default OFF; only set on a
  trusted internal stack). Full operator guide: `library/guides/v0.2.64__enabling-script-execution.md`.
- If you wire the allowlist-file option, remember it needs a bind-mount into the container — the
  simplest internal path is `SG_PLAYWRIGHT__JS_ALLOW_ALL=true` (no mount) on an isolated EC2.
- **Do not** default either on. This is a deliberate CLAUDE.md rule-11 exception, opt-in per stack.

## 4. Change 3 — route `/pw` through the Caddy edge, not the vault HTML-injection proxy (fixes review Q5)

The onboarding team saw **inline screenshots return 7 bytes through `/pw`** (review Q5) and
questioned cookie/body passthrough (Q9). Root cause is almost certainly the **vault-as-edge**
`serve_with_proxy` path: it's built to inject a transformation `<script>` into **HTML**
responses and mangles/undersizes non-HTML bodies (a multi-hundred-KB JSON with `screenshot_b64`).
The service itself returns the full base64 on direct access (verified this session).

- **The Caddy edge already does the right thing.** `Content_Proxy__Edge__Template` routes
  `handle_path /pw/* { reverse_proxy sg-playwright:8000 { header_up X-API-Key …; header_up
  X-Forwarded-Prefix /pw } }` — a **plain reverse proxy**, no body rewriting. Large JSON and POST
  bodies pass through untouched, and `X-Forwarded-Prefix: /pw` is exactly what the console's
  `window.API_BASE` expects.
- **Guidance:** the sg-playwright `/pw` route should go through the **Caddy edge** (`--edge caddy`
  / hostname mode), and the vault's `FAST_API__REVERSE_PROXY__ROUTES=pw=…` HTML-injection path
  should **not** front sg-playwright's binary/JSON responses. If a deployment must keep the
  vault-as-edge, treat the 7-byte screenshot as a **vault serve_with_proxy bug** to fix in that
  repo (it needs to pass non-HTML bodies verbatim) — it is *not* an sg-playwright issue.

## 5. Change 4 — confirm the auth contract still lines up

`/pw` (Caddy or vault) injects `X-API-Key = SGRAPH_SEND__ACCESS_TOKEN` toward sg-playwright,
and sg-playwright's `FAST_API__AUTH__API_KEY__NAME` defaults to `x-api-key`
(`.env.example:8,23`). These must match (header name **and** value):

- `FAST_API__AUTH__API_KEY__NAME` (sg-playwright) == the header the edge injects (`x-api-key`). ✔ today.
- `FAST_API__AUTH__API_KEY__VALUE` (sg-playwright) == `SGRAPH_SEND__ACCESS_TOKEN` (the token the
  edge forwards). The reality doc calls this out — `local up`'s `realize_secrets` already writes
  one shared GUID into both; keep that invariant. If you change the header name, change it in
  both places.
- Nothing to build here — just a review item that a re-pin or edge change must not break.

## 6. Verification pass (order matters)

After the changes, on a local or internal stack:

```bash
sg content-proxy local up --edge caddy        # or: sg cp create … --edge caddy --hostname <fqdn>
sg content-proxy local smoke                    # existing /mitm-proxy chain check
```
Then, through `/pw` (use the stack's access token as x-sgraph-access-token / basic-auth per your edge):

1. **Health + discovery** — `GET /pw/health/capabilities` → `js_evaluate_enabled` present
   (`true` only if you enabled §3), `GET /pw/health/status` → `healthy: true`,
   `/pw/health/info` → `chromium_version` a real dotted version (not `0.0.0`).
2. **Full screenshot not truncated (Q5)** — `POST /pw/screenshot {"url":"https://bbc.co.uk","full_page":true}`
   → `screenshot_b64` is hundreds of KB, **not** 7 bytes. If it's tiny, you're still on the vault
   HTML-injection path (see §4).
3. **Cookie inject → reload → screenshot (Q8/Q9)** — run the console's **S6** example body
   through `/pw/sequence/execute`: `set_cookie{name,value,url} → navigate → screenshot`, or target
   `/pw/test-pages/cookies` and assert the second screenshot shows the cookie. Confirms the POST
   body (with the `set_cookie` step) survived the proxy.
4. **Console** — open `/pw/` in a browser: the light console renders under `/pw` (prefix-aware),
   panels populated. This is also what the sg-playwright CI image gate (`test_99` test_6) asserts
   in-image.

## 7. Explicitly NOT in scope here (flag, don't silently do)

- **Xvfb / stealth launch args** (review Q7 — Daily Mail/Akamai). That's an sg-playwright *image*
  change (a separate internal-image profile), not content_proxy wiring. Track separately.
- **Screenshot `return_value`** (review Q6) and **`skip_selectors` / `max_nodes`** (Q1/Q3) are
  proposed sg-playwright features, not wiring. Don't stub them here.
- **Editing sg-playwright source.** Everything above is content_proxy-side config + one edge
  decision. If you find you need an sg-playwright code change, stop and raise it — it belongs in
  the sg-playwright repo with its own tests, not smuggled into the wiring.
