# `sg aws alb stack perf-test`

An end-to-end smoke / round-trip command that proves a live ALB stack can
reach an existing target IP. Mirrors the UX of `sg vault-app fargate setup
check` and `sg aws ec2 vpc create-stack`: phased orchestrator, Rich progress
renderer, single report schema with phase timings.

## One-paragraph summary

`sg aws alb stack perf-test` accepts a VPC, two subnets, and an IP that's
already serving HTTP somewhere reachable from the VPC. It provisions a
throw-away ALB stack (SGs → LB → TG → listener), waits for `active`,
registers the IP into the TG, waits for `healthy`, sends one or more HTTP
probes through the ALB DNS, asserts a 2xx, then tears the entire stack down
(unless `--keep`). Every phase is timed; the report is the standard
`Schema__AWS__Phase__Result` shape so the existing `Phase__Progress__Renderer`
just works.

This is the missing acceptance gate for v0.2.36: today the unit tests prove
the wiring compiles, but nothing exercises a real round-trip against AWS.

## Why this and not "just" run the manual steps

The end-to-end walk-through in
[`v0.2.36__sg-aws-alb-howto.md` §3](../../../library/docs/ops/v0.2.36__sg-aws-alb-howto.md#3-end-to-end-walkthrough-ec2-backend)
is 6 shell commands plus `jq` plumbing. That's:

- Easy to mis-type (forgetting `--yes` / leaving an LB running and being
  billed)
- Impossible to assert from CI (no exit code on the curl part)
- Not measured — operators ask "did it work?" not "how long did each phase
  take?"

A phased command bakes the assertions in, prints timings the same way every
other stack command does, and leaves nothing behind by default.

## UX

### Command surface

```
sg aws alb stack perf-test \
    --vpc          <vpc-id>                       # required
    --subnets      <sn1,sn2>                      # required, ≥ 2 in distinct AZs
    --target-ip    <ipv4>                         # required
    [--target-port 8080]                          # default 8080
    [--http-path   /info/health]                  # default /info/health
    [--expected-status 200]                       # default 200
    [--http-probes 3]                             # default 3 sequential GETs
    [--name        perf-<random>]                 # default auto-generated
    [--keep]                                      # don't tear down on success
    [--lb-active-timeout 360]                     # default 360s (3-5 min realistic)
    [--healthy-timeout   90]                      # default 90s
    [--http-timeout      30]                      # per-probe timeout, default 30s
    [--yes]                                       # skip confirmation
    [--time]                                      # show phase-timing table
    [--json]                                      # machine-readable output
```

**Mutation gate:** `SG_AWS__ALB__ALLOW_MUTATIONS=1` — same as the rest of
`sg aws alb`.

### Phases

| # | Phase | What it does | Typical duration |
|---|-------|--------------|------------------|
| 1 | `PROVISION` | Calls `ALB__Stack__Provisioner.create_stack(target_type=ip)` | 5–10 s |
| 2 | `WAIT_LB_ACTIVE` | Polls `describe_load_balancer` until `state == active` | **3–5 min** |
| 3 | `REGISTER_TARGET` | `alb_client.register_targets(tg_arn, [{Id: target_ip, Port: target_port}])` | <1 s |
| 4 | `WAIT_HEALTHY` | Polls `describe_target_health` until `state == healthy` | 30–60 s |
| 5 | `HTTP_PROBE` | `--http-probes` sequential GETs to `http://<lb-dns><path>` | <5 s |
| 6 | `TEARDOWN` | `ALB__Stack__Provisioner.delete_stack(name)` — skipped if `--keep` | 2–5 s |

Each phase enters `RUNNING` → exits `OK | ERROR | SKIPPED`, just like
`VPC__Stack__Phase`. On `ERROR` in phases 2–5 the runner still attempts
`TEARDOWN` so we don't leave a $0.025/hr LB behind on test failures (this
is the analogue of the existing rollback in `create_stack`, but extended to
the post-provision phases).

### Output (text mode)

```
╭─ perf-test — perf-7f3a ───────────────────────────────────────╮
│  PROVISION         ok      [4.2 s]   lb=perf-7f3a-alb tg=perf-7f3a-tg  │
│  WAIT_LB_ACTIVE    ok      [184.1 s] state=active                       │
│  REGISTER_TARGET   ok      [0.4 s]   target=10.0.1.42:8080              │
│  WAIT_HEALTHY      ok      [41.7 s]  healthy after 7 polls              │
│  HTTP_PROBE        ok      [1.8 s]   3/3 probes 200 OK (mean 412ms)     │
│  TEARDOWN          ok      [3.1 s]   destroyed                          │
╰────────────────────────────────────────────────────────────────╯

  Total: 235.3 s   reach: http://perf-7f3a-alb.eu-west-2.elb.amazonaws.com  ok
```

JSON mode emits the same shape as the other stack commands plus a
`probes: [{status, duration_ms, body_size}, …]` array on the `HTTP_PROBE`
phase detail.

### Exit codes

- `0` — all probes returned the expected status; teardown succeeded
- `1` — any phase reported `ERROR`, or any probe failed to match
  `--expected-status`
- `2` — teardown left orphaned resources (rare — populated from
  `report.rollback_errors`)

## Service

```
service/ALB__Perf_Test__Runner.py
```

Constructor injects `alb_client`, `ec2_client`, `http_client` (the last
defaulting to a thin `urllib`-backed seam so tests can swap a fake without
hitting the network). The runner composes:

- `ALB__Stack__Provisioner` for `PROVISION` and `TEARDOWN`
- A small `ALB__LB__Wait__Active` helper (poll loop with backoff)
- A small `ALB__Target__Wait__Healthy` helper
- `ALB__HTTP__Probe` (the HTTP seam)

Each polling helper hits its specific phase timeout and adds `attempts=` /
`elapsed_ms=` detail to its phase result. **No phase blocks indefinitely** —
all timeouts come from the request schema.

## CLI

Lives in `aws/alb/cli/Cli__ALB__Stack.py` (existing file gets a new
`@app.command('perf-test')` block). Same `@spec_cli_errors` +
`@require_mutation_gate` stack as `provision`/`destroy`. The factory uses
`ctx.obj['alb_client']` (already wired by `_setup_ctx`) and lazy-creates an
`EC2__AWS__Client` and the HTTP-probe seam.

## Tests

| Test | Coverage |
|------|----------|
| `test_perf_test__happy_path` | All 6 phases succeed; report.ok=True; probes=3 OK |
| `test_perf_test__lb_active_timeout` | `WAIT_LB_ACTIVE` exceeds timeout; TEARDOWN still runs |
| `test_perf_test__target_unhealthy` | `WAIT_HEALTHY` times out; TEARDOWN runs; report.ok=False |
| `test_perf_test__http_status_mismatch` | Probe returns 503 vs expected 200; report.ok=False; TEARDOWN runs |
| `test_perf_test__http_timeout` | Probe times out (fake HTTP raises); report.ok=False |
| `test_perf_test__keep_flag` | `--keep` set; TEARDOWN phase = SKIPPED; stack still exists post-run |
| `test_perf_test__teardown_failure_recorded` | TEARDOWN partial fail → rollback_errors populated, exit=2 |
| `test_perf_test__probes_aggregate_timings` | 3 probes; report aggregates mean/p50/p99 |
| `test_perf_test__ip_target_type` | TG is created with `TargetType=ip` not `instance` |
| `test_perf_test__schema_round_trip` | JSON output deserialises back to `Schema__ALB__Perf_Test__Report` |

All tests use the existing `ALB__AWS__Client__In_Memory` plus a new
`Fake_HTTP__Probe` (deterministic `(status, latency, body)` lookup keyed by
URL). Real-network smoke test stays optional, gated on
`SG_AWS__ALB__PERF_TEST__LIVE=1` and a known healthy IP — runs under the
deploy-via-pytest convention if/when we have a long-running target IP for
CI.

## Decisions for sign-off

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Sequential HTTP probes, not concurrent** | Smoke test, not load test. Concurrent probes need rate-limit awareness + per-probe LCU accounting. Out of scope for v1; add when we want load-style runs. |
| 2 | **Default `--http-probes 3`** | One probe is too noisy on cold-start DNS. Three sequential gives a stable mean without dragging the wall-clock over 10s. |
| 3 | **TEARDOWN runs even on failure** | Avoid leaving idle ALBs ($18/mo). Operator can opt out with `--keep` if they want to triage. |
| 4 | **`target-type=ip` only** | The whole point is to point at an existing IP. If you have an instance-id, use `tg register` directly — no need for a perf-test wrapper. |
| 5 | **HTTP only, no HTTPS probe** | Mirrors the v0.2.36 listener decision. HTTPS probing waits for ACM/cert work. |
| 6 | **Auto-generated stack name** when `--name` omitted | Default `perf-<8-hex>` so re-runs in parallel don't collide. Operator passes `--name` for stable CI artifacts. |
| 7 | **No retries on `WAIT_LB_ACTIVE` failure** | If the LB never reaches active in 6 min, retrying won't help — fail fast, run TEARDOWN. |

## Acceptance criteria

1. `sg aws alb stack perf-test --vpc V --subnets S1,S2 --target-ip IP --yes`
   returns exit 0 against a target that's actually serving 200 on
   `/info/health:8080`.
2. The Rich progress renderer shows the 6 phases live (same widget as
   `vpc create-stack`).
3. On any phase failure, the LB / TG / SGs are deleted before the command
   exits (verify with `sg aws alb lb list` post-run).
4. `--keep` leaves the stack in place; `sg aws alb stack describe <name>`
   confirms it.
5. `--json` output round-trips through `Schema__ALB__Perf_Test__Report`.
6. 10 unit tests pass under `pytest tests/unit/sgraph_ai_service_playwright__cli/aws/alb/`.

## Out of scope (for v1 of this brief)

- **Load generation** — no concurrency, no RPS knob, no LCU correlation.
  Sequential 3-probe smoke only.
- **TLS / HTTPS** — HTTP only; matches the listener decision in v0.2.36.
- **Path / host routing** — probe hits the single forward-to-TG default
  action; no rule creation.
- **Cross-region** — runs in whatever region `Sg__Aws__Session` is pointing
  at. No `--region` override.
- **Reusing an existing ALB** — always creates and destroys its own stack.
  A future `perf-test --reuse-stack <name>` could skip PROVISION/TEARDOWN
  and just register/probe/deregister.

## Cost guard

A single full perf-test run holds an ALB for ~4 min — that's
`4/60 × $0.02475 ≈ $0.0017`. Even 100 runs/day is ~$0.17. Safe to wire
into CI on a smoke-gate cron without budget alarms.
