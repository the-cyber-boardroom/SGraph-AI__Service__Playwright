# Native SSH remote-control for `sg aws ec2`

Add a first-class SSH surface to `sg aws ec2` — key-pair lifecycle plus
`exec / install / upload / service / info` against a running instance — built
on the OSBot SSH foundation documented in
[`library/docs/reference/osbot-ssh__remote-ec2-control-pattern.md`][ref].
This is an **additive alternative to the existing SSM path**, not a
replacement.

[ref]: ../../library/docs/reference/osbot-ssh__remote-ec2-control-pattern.md

## One-paragraph summary

Today this repo can *print* an SSH command (`sg aws ec2 ssh-info`) but cannot
*use* SSH — all remote control goes through SSM `send_command`
(`EC2__Instance__Helper`, `Firefox__SSM__Helper`, …). The OSBot SSH helper
classes (`SSH`, `SSH__Execute`, `SSH__Linux`, `SSH__Python`, `SCP`) already
give us a complete remote-control toolkit; osbot-aws already gives us
key-pair CRUD and `EC2_Instance.ssh()`. This brief wraps those behind a
Type_Safe `EC2__SSH__Client` seam (with an in-memory twin for tests), exposes
them as `sg aws ec2 key-pair *` and `sg aws ec2 ssh *` commands, and adds the
strategic pieces: vault-backed key storage, a key-pair-at-boot helper, an SG
ingress helper for :22, and an optional FastAPI route surface mirroring the
prior-art `Routes__EC2_SSH`.

## Why now

- **VPC scaffolding is friction.** We can't always stand up private subnets +
  bastions to gate access. Key-only SSH on an open :22 is an acceptable
  posture (no passwords ⇒ no brute force) and unblocks "log into the box and
  fix it / install something" workflows immediately.
- **SSM has prerequisites** (agent + IAM instance profile + SSM reachability)
  that aren't always present on the instances we spin up.
- **We already do this elsewhere.** The attached prior art
  (`CBR__Athena__Deploy__EC2`, `Create_EC2_Instance__CBR_Website_Beta`,
  `Mitmproxy__Create__EC2_Instance`, `Service__EC2_SSH`, `Routes__EC2_SSH`)
  proves the pattern end-to-end — create spot instance with a key-pair,
  `wait_for_ssh`, install packages, scp files, register systemd, snapshot AMI.
  This brief brings that into `sg` with our conventions (Type_Safe, one class
  per file, in-memory test seam, mutation gate).

## Relationship to the existing SSM path

Both coexist. SSM stays the default for hardened/agent-equipped hosts; SSH is
for the "I have a key-pair and :22 is open" case. They share nothing except
the `EC2__AWS__Client` for instance metadata. No change to any SSM helper.

## Command surface

```
# ── key-pair lifecycle ──────────────────────────────────────────────────────
sg aws ec2 key-pair list                                   [--json]
sg aws ec2 key-pair show     <name>                        [--json]
sg aws ec2 key-pair create   <name> [--vault] [--out PATH] [--tag k=v] [--yes] [--json]
sg aws ec2 key-pair delete   <name>                        [--yes] [--json]
sg aws ec2 key-pair import   <name> --public-key PATH      [--yes] [--json]

# ── ssh against a running instance (id or Name tag) ─────────────────────────
sg aws ec2 ssh connect  <id-or-name>                        # prints ready-to-paste ssh cmd (today's ssh-info, upgraded)
sg aws ec2 ssh check    <id-or-name> --key KEY [--user U]   # SSH__Health_Check round-trip [--json]
sg aws ec2 ssh exec     <id-or-name> --key KEY [--user U] -- <command…>     [--json]
sg aws ec2 ssh run      <id-or-name> --key KEY --script FILE                [--json]   # multi-line script
sg aws ec2 ssh install  <id-or-name> --key KEY [--apt PKG] [--pip PKG] [--yum PKG]     [--json]
sg aws ec2 ssh upload   <id-or-name> --key KEY --local PATH --remote PATH   [--json]
sg aws ec2 ssh download <id-or-name> --key KEY --remote PATH --local PATH   [--json]
sg aws ec2 ssh service  <id-or-name> --key KEY --action {start|stop|restart|status|logs} --name SVC  [--json]
sg aws ec2 ssh info     <id-or-name> --key KEY [--user U]   [--json]   # whoami/uname/disk/mem/uptime
```

Conventions, matching the rest of `sg aws`:

- `<id-or-name>` resolved via the existing `EC2__Name__Resolver`.
- `--user` defaults are auto-detected from the AMI (ubuntu → `ubuntu`,
  AL2023 → `ec2-user`) — same heuristic `ssh-info` already uses.
- `--key` accepts a path OR a vault key reference (`vault:<name>`) when
  `--vault` storage is in play (see decisions).
- **Mutation gate** `SG_AWS__EC2__ALLOW_MUTATIONS=1` on everything that
  changes remote/AWS state: `key-pair create/delete/import`, `ssh
  exec/run/install/upload/service`. Read-only (`key-pair list/show`, `ssh
  check/info/connect`, `download`) needs no gate.
- `--json` everywhere; text mode uses Rich tables/panels like `ec2 describe`.

### `EC2__SSH__Client` — the seam

The single boundary to OSBot SSH, mirroring how `ALB__AWS__Client` /
`EC2__AWS__Client` wrap boto3. One method per remote capability; everything
returns a `Schema__EC2__SSH__Result` (or a list). The in-memory subclass
overrides the transport so tests assert on *commands that would run*.

```python
class EC2__SSH__Client(Type_Safe):
    ec2_client : object = None                    # EC2__AWS__Client — for instance metadata
    config     : Schema__EC2__SSH__Config = None

    def ssh(self):                                # single seam — subclass overrides for tests
        from osbot_utils.helpers.ssh.SSH__Execute import SSH__Execute
        s = SSH__Execute(ssh_host          = str(self.config.host),
                         ssh_port          = int(self.config.port),
                         ssh_key_file      = str(self.config.key_file),
                         ssh_key_user      = str(self.config.key_user),
                         strict_host_check = bool(self.config.strict_host_check))
        return s

    def configure_for_instance(self, id_or_name, key_file, user='') -> Schema__EC2__SSH__Config: ...
    def check(self)                                  -> Schema__EC2__SSH__Result        # health echo
    def exec(self, command: str)                     -> Schema__EC2__SSH__Result
    def run_script(self, script: str)                -> List__Schema__EC2__SSH__Result
    def install(self, request)                       -> List__Schema__EC2__SSH__Result  # apt/pip/yum
    def upload(self, local: str, remote: str)        -> Schema__EC2__SSH__Result        # via SCP
    def download(self, remote: str, local: str)      -> Schema__EC2__SSH__Result
    def service(self, action, name: str)             -> Schema__EC2__SSH__Result        # systemctl
    def info(self)                                   -> dict                            # whoami/uname/disk/mem
```

`configure_for_instance` resolves the public IP via `EC2__AWS__Client`,
auto-detects the SSH user from the AMI, and (when `key_file` is a
`vault:` reference) materialises the `.pem` to a `chmod 0400` temp file for
the duration of the call.

## Strategic extensions (the "much more native" part)

These are what make this strategic rather than a thin CLI wrapper. Each is
independently shippable after the core lands.

### A. Vault-backed key storage
`key-pair create --vault` stores the private key in the vault (sgit) under a
known path, never on local disk beyond a transient `chmod 0400` temp file.
`--key vault:<name>` resolves from there. **Hard rule (CLAUDE.md #12/#13):**
no key material in git, ever; block any commit that would include a `.pem`.

### B. Key-pair-at-boot helper
A small helper that, given a stack/instance request, ensures the key-pair
exists (create-if-missing) and threads `KeyName` into the launch kwargs of
`EC2__AWS__Client.create_instance` — so "launch a box I can SSH into" is one
flag (`ec2 create … --ssh-key <name>`), not a two-step dance.

### C. Security-group ingress helper for :22
`EC2__AWS__Client.authorize_security_group_ingress` already exists. Add a
convenience that opens :22 (default `0.0.0.0/0`, overridable to a CIDR/your
egress IP) on a named SG, respecting naming rule #14. Surfaced as
`--open-ssh [CIDR]` on `ec2 create`.

### D. Deployer recipe orchestrator
`EC2__SSH__Deployer` — a phased orchestrator (mirrors `ALB__Stack__Provisioner`
+ the prior-art `CBR__Athena__Deploy__SSH`): `WAIT_SSH → INSTALL_DEPS →
UPLOAD_FILES → REGISTER_SERVICE → START → (optional) SNAPSHOT_AMI`, with the
standard `Phase__Timer` + `Phase__Progress__Renderer` UX. Lets us script
"provision a box and deploy X" as `sg aws ec2 ssh deploy <id> --recipe FILE`.

### E. FastAPI route surface (optional, later)
Mirror the prior-art `Routes__EC2_SSH` → `Service__EC2_SSH`: expose
configure/exec/install/upload/service over HTTP for an admin console. **Gate
hard** — a raw `exec` endpoint is RCE; require auth + an allow-list before it
leaves a trusted boundary. Out of scope for v1; noted so the seam is built
with it in mind.

### F. Readiness loop
Bake the "port-open ≠ shell-ready" loop (from the reference doc §6) into
`configure_for_instance` so `ssh exec` doesn't fail on a still-booting host.

## Testing — the twin

`EC2__SSH__Client__In_Memory` overrides `ssh()` to return a fake transport
that records commands and returns canned results — no network, no mocks/
patches (CLAUDE.md testing rule). Same philosophy as the prior-art
`Service__EC2_SSH` "twin mode".

| Test | Coverage |
|---|---|
| `test_exec__records_command` | `exec('uname -a')` → recorded verbatim, result schema populated |
| `test_install__apt_pip_yum` | install request fans out to the right `apt-get`/`pip3`/`yum` lines |
| `test_upload__builds_scp` | upload routes through SCP with correct args |
| `test_service__systemctl` | `service(restart, app)` → `sudo systemctl restart app` |
| `test_check__health_echo` | health check parses the echo round-trip |
| `test_configure__resolves_ip_and_user` | IP from EC2 client, user auto-detected from AMI |
| `test_run_script__multiline` | each line becomes a separate recorded command |
| `test_readiness_loop__waits_then_proceeds` | "System is booting up" stderr retries, then succeeds |
| `test_result_schema_round_trip` | `.json()` ↔ `from_json()` on `Schema__EC2__SSH__Result` |
| `test_exec__not_configured_errors` | unconfigured client returns error result, no crash |
| `test_key_pair_create__writes_and_tags` (key-pair) | create returns name/id/fingerprint; vault path used when `--vault` |
| `test_key_pair_delete__revokes` (key-pair) | delete → `key_pair_exists` False |
| `test_command_injection_guarded` | untrusted target in `service`/`install` is quoted/validated |

A single live round-trip smoke test stays env-gated
(`SG_AWS__EC2__SSH__LIVE=1` + a known instance/key) under the
deploy-via-pytest convention.

## Decisions for sign-off

| # | Question | Recommended default | Notes |
|---|----------|---------------------|-------|
| 1 | **Key storage** — vault, local file, or both? | **Both; default `--vault`** | Vault is the safe default per CLAUDE.md #12/#13; `--out PATH` for local when explicitly asked. |
| 2 | **Default SSH ingress CIDR** when `--open-ssh` used with no arg | `0.0.0.0/0` | Key-only auth makes this acceptable; warn in output + suggest tightening. |
| 3 | **`strict_host_check` default** | `False` (matches OSBot) | First-connect ergonomics; offer `--strict` for long-lived hosts. |
| 4 | **Expose the FastAPI route surface in v1?** | **No** | RCE risk; ship the client + CLI first, add routes behind auth later (extension E). |
| 5 | **Auto-open :22 on `ec2 create`?** | **No, opt-in** via `--open-ssh` | Don't widen exposure implicitly. |
| 6 | **`exec` arg style** | `-- <command…>` passthrough | Avoids quoting hell; everything after `--` is the remote command. |

(These mirror the "decisions resolved" style of the ALB plan — I've pre-filled
recommendations; flag any you want changed before Dev picks this up.)

## Acceptance criteria

1. `sg aws ec2 key-pair create my-key --vault --yes` creates the AWS key-pair
   and stores the private key in the vault (never touches git).
2. `sg aws ec2 ssh check <id> --key vault:my-key` returns a healthy
   round-trip against a real instance.
3. `sg aws ec2 ssh install <id> --key vault:my-key --apt nginx` installs the
   package and reports per-command results.
4. `sg aws ec2 ssh upload <id> --key … --local app.service --remote app.service`
   then `ssh service <id> --action start --name app` brings a service up.
5. All mutating commands refuse without `SG_AWS__EC2__ALLOW_MUTATIONS=1`.
6. 21 unit tests pass via the in-memory twin (no network, no mocks).
7. No regressions in the existing SSM helpers or `ec2` commands.

## Out of scope (v1)

- **FastAPI route surface** (extension E) — design the seam for it, don't ship it.
- **Windows / non-Linux targets.**
- **Port forwarding / tunnels** (OSBot has TODOs here; not needed yet).
- **Connection pooling / persistent sessions** — each command is a fresh ssh
  invocation (fine for ops; revisit if we do high-frequency control).
- **Replacing SSM** — explicitly additive.

## Implementation order (one slice, extensions follow)

1. Primitives + enums + schemas + collections (~20 min)
2. `EC2__Key_Pair__Client` + tests (~30 min)
3. `EC2__SSH__Client` + in-memory twin + tests (~60 min)
4. `Cli__EC2__Key_Pair` + `Cli__EC2__SSH` + Rich rendering (~45 min)
5. Vault storage hook (extension A) + readiness loop (extension F) (~30 min)
6. Docs: add a `sg aws ec2 ssh` how-to under `library/docs/ops/` and link the
   reference doc.

Extensions B (boot helper), C (SG :22 helper), D (deployer), E (routes) each
land as their own follow-on slice once the core seam is in.
