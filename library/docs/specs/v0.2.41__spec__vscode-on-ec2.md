# Spec (PROPOSED) — `sg vscode`: VS Code on EC2

> **PROPOSED — does not exist yet.** No `sg_compute_specs/vscode/` package exists today, and VS Code is not in the `sg-compute/proposed/` list prior to P-8 (added alongside this doc). Everything below is an aspiration to be ratified, not a description of shipped behaviour. Cross-check against `team/roles/librarian/reality/sg-compute/index.md` before relying on any claim.

A new top-level compute spec that launches an ephemeral EC2 node running **VS Code server**, so VS-Code-dependent tooling (agentic coding extensions, language servers, app builders) runs on remote compute instead of the laptop. It reuses the existing spec scaffold almost wholesale: the EC2 skeleton from `local_claude`, the SSM port-forward "tunnel" pattern from `vault_app`, and the browser-front + auth machinery from `vnc`.

---

## 1. Goal

Run apps and solutions that need a real VS Code engine — the extension host, language servers, and agentic/AI coding extensions — on an EC2 box rather than the local laptop. Two access shapes are required:

1. **Remote tunnel** — reach the editor over an **SSM port-forwarding** session (`AWS-StartPortForwardingSession`). No inbound ports; the editor binds to loopback on the instance and is forwarded to `https://localhost:<port>` on the operator's machine.
2. **Browser app (public)** — reach the editor over HTTPS `:443` fronted by Caddy with an auth portal, optionally on a real DNS hostname.

Plus the always-available **terminal path**: an interactive SSM shell into the box (for neovim/CLI workflows, container management, `git`), which every spec gets free from `Spec__Service__Base.connect_target`.

---

## 2. VS Code on a server — the options, and what we pick

Settled questions about how VS Code runs server-side, since this drives the build:

| Approach | UX | Extension marketplace | Fit here |
|----------|-----|----------------------|----------|
| **code-server** (Coder) | VS Code in a browser tab | **Open VSX** only — Pylance, MS C#, official Remote, and some proprietary AI extensions are absent/unlicensed | Simplest container; v1 **default** |
| **openvscode-server** (Gitpod) | Browser tab, closer to upstream build | Open VSX | Alternative to code-server |
| **`code serve-web`** (official MS) | Browser tab, official build | **Full MS marketplace** | Best extension compat; v1 alt behind a flag |
| **`code tunnel`** (official MS) | Local desktop VS Code attaches via MS relay | Full MS marketplace | Outbound MS relay — overlaps with, and is arguably redundant given, our SSM-forward tunnel. Deferred. |
| Full Linux desktop + VNC/DCV running desktop VS Code | Remote desktop | Full (desktop app) | Heaviest; out of scope — reuse `vnc`/`neko` later if a workload truly needs a GUI desktop |

**Is there a TUI for VS Code?** No. VS Code is an Electron/web app with no ncurses build, so there is no true terminal-UI port. "Pure terminal" here means the SSM shell (`connect` verb) into the box for terminal editors (neovim/helix) and CLI tools — which loses the VS Code extension host, the very thing VS-Code-dependent tools need. So the editor itself is always served (code-server / serve-web); the terminal path is for box access, not for editing in a TUI.

**Ratified (2026-05-25, see §11):** confirmed **web/browser VS Code, not remote desktop**. v1 defaults to **code-server** ("ok to start with"); **`code serve-web`** is the genuinely feature-equivalent path (full MS marketplace) available behind `Enum__Vscode__Distribution` — flip to it the moment a required tool needs an MS-marketplace-only extension. It is a config flip, not a rebuild.

## 3. Reuse map — what we clone vs build

The point of this spec is **maximum reuse**. Almost nothing is net-new.

| Need | Reuse from | Concrete artefact |
|------|-----------|-------------------|
| EC2 spec skeleton (SSM-only, no public port) | `sg_compute_specs/local_claude/` | `Local_Claude__{Service,AWS__Client,User_Data__Builder,Stack__Mapper,AMI__Helper}.py` — clone the directory shape |
| SSM port-forward "tunnel" | `sg_compute_specs/vault_app/` | `Schema__Vault_App__Info.ssm_forward`, `Vault_App__Stack__Mapper.py:76` (builds `aws ssm start-session --document-name AWS-StartPortForwardingSession`), `Cli__Vault_App.py:974` (the `forward`/`tunnel` command) |
| Browser front + TLS + auth (public mode) | `sg_compute_specs/vnc/service/` | `Vnc__Caddy__Template.py` (Caddyfile + caddy-security portal + bcrypt `users.json`), `Vnc__Compose__Template.py`, `Vnc__SG__Helper.py` (`:443` locked to caller `/32`, or `--public` 0.0.0.0/0 auth-gated) |
| Free health / exec / connect (terminal) | `sg_compute/core/spec/Spec__Service__Base.py` | inherited `health`, `exec`, `connect_target` (returns instance-id for `aws ssm start-session`) |
| Free `list/info/create/delete/connect` CLI verbs | `sg_compute/cli/base/Spec__CLI__Builder.py` | `Spec__CLI__Builder.py:330` already execs `aws ssm start-session` for the `connect` verb |
| EC2 launch primitives | `sg_compute/platforms/ec2/helpers/` | `EC2__{AMI,Instance,Launch,SG,Tags__Builder}__Helper.py`, `Stack__Naming.py` (rule-14/15-safe) |
| Caller IP + stack-name generation | `sg_compute/platforms/ec2/networking/` | `Caller__IP__Detector.py`, `Stack__Name__Generator.py` |
| User-data boot fragments | `sg_compute/platforms/ec2/user_data/` | `Section__Base` (SSM agent, auto-terminate timer, `ssm-user`), `Section__Docker`, `Section__Nginx`, `Section__Env__File` (tmpfs secrets), `Section__Sidecar` |

**Net-new (small):** the `vscode/` package files themselves, a `Vscode__Compose__Template` that runs the code-server (or serve-web) container bound to `127.0.0.1:<port>`, two per-spec enums (`Enum__Vscode__Distribution`, `Enum__Vscode__Ingress`), a per-spec stack-name primitive, and the schemas. Everything structural already exists.

## 8. CLI surface

```
sg vscode
  list     [--region X] [--json]
  info     <stack-name> [--region X] [--json]
  create   [--region X] [--instance-type T] [--disk-gb N] [--max-hours N]
           [--distribution code-server|openvscode|serve-web]
           [--ingress ssm-forward|public-https]
           [--name X] [--password P]
           [--public] [--with-aws-dns] [--fqdn F] [--yes]
  delete   <stack-name> [--region X] [--yes]
  connect  <stack-name>           # FREE from Spec__CLI__Builder — interactive SSM shell (terminal path)
  forward  <stack-name> [--local-port 8443]   # SSM port-forward tunnel (clone Cli__Vault_App forward)
  url      <stack-name>           # print vscode_url
  open     <stack-name>           # open vscode_url in a browser (after forward for SSM mode)
  health   <stack-name> [--timeout 120]
```

`list/info/create/delete/connect` come from `Spec__CLI__Builder`. Only `forward`/`url`/`open` are spec-specific additions (and `forward` is a near-verbatim clone of vault_app's).

## 9. Boot / user-data composition

`Vscode__User_Data__Builder.render()` joins shared `Section__*` fragments (mirrors `Local_Claude__User_Data__Builder`):

```
Section__Base(stack_name, max_hours)        # SSM agent, auto-terminate timer, ssm-user, logging
Section__Docker()                           # docker + compose plugin
Section__Env__File(secrets)                 # tmpfs .env: PASSWORD, optional API keys
<Vscode__Compose__Template>                 # code-server / serve-web container, bind 127.0.0.1:<port>
[Section__Nginx OR Vscode__Caddy__Template] # ONLY when ingress == PUBLIC_HTTPS (TLS :443 + auth portal)
Section__Sidecar()                          # optional host-control sidecar
FOOTER                                       # /var/lib/sg-compute-boot-ok
```

- **SSM_FORWARD mode (default):** editor binds to loopback; **SG opens nothing** (clone local_claude's `inbound_ports=[]`). Reached only via `sg vscode forward`. No Caddy.
- **PUBLIC_HTTPS mode:** Caddy terminates TLS on `:443` with a bcrypt/JWT auth portal in front of the editor port; SG opens `:443` locked to caller `/32` (or `0.0.0.0/0` with `--public`, still auth-gated). Optional `Vscode__Auto_DNS` (reuse `Vault_App__Auto_DNS`) upserts an A record so Caddy can serve a real Let's Encrypt cert instead of `tls internal`.

## 10. Security model

- **Default is closed.** SSM_FORWARD opens zero inbound ports; all access is IAM-gated through SSM (`playwright-ec2` instance profile, `AmazonSSMManagedInstanceCore`). This is the recommended posture and aligns with rule-10/11 (deny-by-default, no arbitrary exec surface).
- **No SSH, no key pairs** — consistent with the rest of `sg_compute`.
- **Auth on the editor:** code-server password (SSM_FORWARD) or Caddy auth portal + bcrypt password (PUBLIC_HTTPS). Password generated server-side, surfaced once in `Create__Response`, stored only in tmpfs (`Section__Env__File`).
- **SG naming:** `Vscode__SG__Helper` uses `Stack__Naming(section_prefix='vscode')` → `vscode-<name>-sg` (never `sg-*`, rule 14; never double-prefixed, rule 15).
- **Auto-terminate** via `Section__Base` systemd timer + `InstanceInitiatedShutdownBehavior=terminate` — a dev box left running won't bill indefinitely.

## 11. Ratified decisions (2026-05-25)

1. **Web, not desktop.** Editor is **web/browser VS Code** served from the box (code-server / serve-web) — no VNC/RDP/desktop streaming. Feature-equivalence is the priority (see §2).
2. **Distribution default.** Start with **code-server** (Open VSX). `code serve-web` (official build, full MS marketplace) is the feature-equivalent alternative behind `Enum__Vscode__Distribution`; switch to it when a required tool needs an MS-marketplace-only extension.
3. **Fully ephemeral.** No persistence in v1 — no AMI bake, no EBS snapshot, no EFS. Data survival comes later via **vault-managed data** (a separate follow-on, not v1).
4. **No workspace seeding.** `create` does **not** take `--git-repo`; cloning/setup is done post-connect by the operator.
5. **No `code tunnel`.** SSM port-forward is the only tunnel ingress — no MS relay, no Microsoft/GitHub login dependency.

## 12. What is NOT in v1

| Excluded | Reason |
|----------|--------|
| Persistent storage (EBS snapshot / EFS) | Ephemeral-first; revisit per §11.2 |
| Full Linux desktop (VNC/DCV) + desktop VS Code | Heavy; reuse `vnc`/`neko` later only if a GUI desktop is genuinely required |
| `code tunnel` MS-relay ingress | SSM-forward covers the no-inbound tunnel need (§11.4) |
| Dashboard UI card/detail | Optional per authoring-guide §4.3; add after the service lands |
| Multi-user / shared workspaces | One box, one operator for v1 |

## 13. Implementation slices (suggested)

1. **Skeleton + manifest + contract test** — package, `manifest.py`, `tests/test_manifest.py`, pyproject entry point, one line in `Cli__SG.py`. Spec appears in `sg vscode --help` and `/api/specs`.
2. **SSM_FORWARD mode end-to-end** — schemas, `Vscode__Service` (clone local_claude), `Vscode__Compose__Template` (code-server loopback), `Vscode__Stack__Mapper` (ssm_forward string), CLI `create/info/forward/connect/delete`. This is the primary user-requested mode.
3. **PUBLIC_HTTPS mode** — `Vscode__Caddy__Template` + `Vscode__SG__Helper` :443 + auth portal (clone vnc), `--public`.
4. **Auto-DNS + real cert** — reuse `Vault_App__Auto_DNS` for `--with-aws-dns`.
5. **(Optional) `serve-web` distribution** — second `Enum__Vscode__Distribution` branch for full MS marketplace.
