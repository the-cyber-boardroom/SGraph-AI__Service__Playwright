# Spec — content-transformation proxy stack

> **Framing note (supersedes the earlier `pw_capture` draft).** mitmproxy here is a
> **content-transformation proxy**, not an egress/flow-capture proxy. It fetches the
> origin page and hands it to the FastAPI MITM service, which **injects a client-side
> transformation script** that blurs/removes content before the user sees it. Durable
> data movement (scripts in, logs out) is the **vault's** job, not a flow store.

A self-contained EC2 image runs **four components** that together turn a request into a
policy-transformed page: the user browses through **mitmproxy**, which hands the fetched
page to the **FastAPI MITM service**, which injects a transformation **script** (the
"formula"); **sg-playwright** drives/tests the result; the **vault app** ships the
scripts in, streams the logs out to S3, and serves the UX. The VNC remote-browser is
**out of scope** here (it needs a container per user — separate scaling/isolation).

The roles below are the correction the project lead asked for: each piece does one job.

---

## 1. The premise

Website transformation via a proxy of content: based on criteria, change parts of the
page so the user sees only the content their policy ("formula") allows. Lead use case is
content filtering (blur/remove), but the mechanism is general — any criteria-driven page
transform. The **decision** to transform happens server-side (currently keyed on a
cookie); the **transformation** happens client-side, in an injected script, before render.

---

## 2. The request-and-transform flow

```
  Browser (configured to use the proxy)
        │  (1) request
        ▼
  mitmproxy ──(2) fetch──▶ Origin website
   (on EC2) ◀─(3) page────┘
        │  (4) hand the page to the MITM service
        ▼
  FastAPI MITM service  (same EC2 instance, :10011, x-api-key)
        │   • decide: activate?  (currently via cookie)
        │   • if active: inject the transformation <script> (latest, from a vault)
        │  (5) return page + injected script
        ▼
  mitmproxy ──(6) deliver transformed page──▶ Browser
                                                  │  (7) injected script runs CLIENT-SIDE
                                                  ▼   blurs / removes before the user sees it
                                          User sees only policy-allowed content
```

Keeping the transform client-side keeps the proxy light (it injects, it does not rewrite
the whole page) and puts the logic where the rendered DOM actually exists.

---

## 3. The four components and their roles

This is the heart of the correction — what each piece is *for*:

| Component | Role (one job) | Where it lives | Status (per sg-send briefs) |
|-----------|----------------|----------------|------------------------------|
| **mitmproxy** | **The proxy.** Fetches the origin page and hands it to the MITM service; delivers the injected result back to the browser. Does *not* decide or transform. | OSS `mitmproxy` on the image | Built |
| **FastAPI MITM service** | **The decision + injection engine.** Decides activation (cookie today) and **injects the latest transformation script**. Python 3.12 on OSBot-Utils / OSBot-Fast-API / OSBot-AWS; `x-api-key`; port **10011**; admin UI + console + **mitm-scripts CLI**; Lambda-deployable, multi-stage dev/QA/prod. | `MGraph-AI__Service__Mitmproxy` (external) | Built |
| **sg-playwright** | **Browser automation over HTTP.** navigate · screenshot · PDF · extract DOM/text · run sequences · hold sessions. Used to **drive and test** the transformation (QA the policy) and to render in automation contexts. Auth via `x-sgraph-access-token` through the vault `/pw` proxy, or `X-API-Key` direct. | **this repo** (`diniscruz/sg-playwright`) | Built |
| **Vault app** | **The data-communication backbone + UX.** SG API + vault + vault UI (build-to-render vaults). Ships scripts in, streams logs out to S3, serves the UX launcher and testing tools. Lets vaults be deployed to and served from the server. | `SGraph-AI__App__Send` (external) | Built |

So the instance is self-contained: it **proxies** (mitmproxy), **transforms** (MITM
service), **drives a browser** (sg-playwright), and **serves vaults** (vault app). The
MITM service and sg-playwright are the two externally-referenced compute components; the
vault app is the SGraph stack delivering script-management, logging, and UX.

---

## 4. The script is the formula

The injected script carries all the detail — the rules for what to blur/remove on a page.
Changing behaviour = shipping a new script (not a redeploy). Today the script is a
**regex-and-graph** structure built **offline with LLMs** (separate from the request path,
which keeps runtime deterministic); the direction of travel is **semantic-graph and more
dynamic**. The script is the unit of policy, and it is **version-controlled in a vault**
(§5 role one) — the MITM service injects the latest from that vault.

---

## 5. The vault's three roles (the data-communication backbone)

The vault is not an add-on; it is *how* scripts reach the server, *how* logs leave it, and
*how* the experience is delivered.

| Role | Vault carries | Direction | Effect |
|------|---------------|-----------|--------|
| **1 · Script management** | The versioned transformation scripts (formulas) | vault → server | Update filtering by updating the vault; per-deployment customisation; the MITM service injects the latest |
| **2 · Logging (append → S3)** | Server logs, via the **append** feature | server → vault → S3 | A whole auto-scaling fleet appends to one S3-backed vault → **one distributed, reopenable log store**; instances stay ephemeral; the same S3 files reopen as the vault from any environment |
| **3 · Vault apps** | Testing tools + the **UX launcher** | vault → user | A web page of supported-site icons; click opens the transformed site in an **iframe or VNC viewer**. Turns the proxy into a product the user just opens |

Role 2 is the architecturally interesting one: because the backing store is shared S3, N
instances behave as **one** vault — scaling out holds no unique local state. (This is the
correct home for "where does the captured/observed data go" — the vault append store, not
a bespoke flow API.)

---

## 6. Two modes → two load balancers

| Mode | Path | Load balancer | Notes |
|------|------|---------------|-------|
| **1 · Direct proxy** | user's own browser, configured to use the proxy → mitmproxy on EC2 | **Network LB (L4)** | User's browser renders; more setup on the client |
| **2 · Streamed remote browser (VNC)** | user's browser ──VNC──▶ remote browser-in-container → mitmproxy | **Application LB (L7)** | Nothing on the user's machine; easiest reach; **VNC server out of scope here** |

Behind either, an **auto-scaling group** of instances all feed the same S3-backed vault
(§5 role two), so scaling 2→5→10→100 is straightforward — no instance holds unique state.

---

## 7. The stack assembly — docker-compose (the required deliverable)

A full docker-compose stands up the four components reproducibly; the vault app reads/writes
vaults backed by S3.

```
 EC2 instance  (one image, docker-compose)
 ┌──────────────────────────────────────────────────────────┐
 │  mitmproxy (proxy) ──▶ FastAPI MITM service  :10011        │
 │                         (script injection)   x-api-key     │
 │                                                            │
 │  sg-playwright              vault app                       │
 │  (browser automation)       (SG API + vault + vault UI)     │
 └──────────────────────────────────────────────────────────┘
        │  vault app reads/writes vaults
        ▼
     S3  (shared vault store — §5)
```

**Deploy model:** spin the server up (the docker-compose) → **copy in the vaults that
belong on it** (the scripts, plus UX-launcher and testing vaults) → done. Because instances
are stateless beyond their vaults and vaults are S3-backed, the ASG grows/shrinks freely.

### 7.2 Compose services + env wiring

| Service | Image | Ports | Key env |
|---------|-------|-------|---------|
| `mitmproxy` | `mitmproxy/mitmproxy` (pin a 10.x per the VNC reverse-proxy/CSRF finding) | `:8080` proxy, `:8081` UI (network-local) | `--scripts` points at the MITM bridge; upstream = MITM service |
| `mitm-service` | `MGraph-AI__Service__Mitmproxy` image | `:10011` | `FAST_API__AUTH__API_KEY__{NAME=x-api-key,VALUE}`; `CONTENT_PROXY__SCRIPTS_VAULT=<vault ref>` (latest script source) |
| `sg-playwright` | `diniscruz/sg-playwright` | `:8000` | `X-API-Key`; optional `SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy:8080` + `IGNORE_HTTPS_ERRORS` when automation should transit the transform |
| `vault-app` | `SGraph-AI__App__Send` image | `:443`/`:8080` | `SEND__STORAGE_MODE` → S3; vault append target; serves `/pw/*` reverse-proxy to sg-playwright (v0.2.41 pattern) |

The vault app already carries the **`/pw` reverse proxy** (config-driven
`FAST_API__REVERSE_PROXY__ROUTES="pw=http://sg-playwright:8000"`, `X-Forwarded-Prefix`
handling) — so a script running in the vault page reaches the Playwright API same-origin
with `x-sgraph-access-token` → `X-API-Key` translation. That is the existing seam this
stack reuses for sg-playwright.

---

## 8. sg-playwright's role in detail (this repo)

sg-playwright is **not in the user's render path** in mode 1 (the user's own browser is).
Its jobs in this stack:

1. **QA the transformation** — drive a headless browser through mitmproxy, navigate a
   supported site, and assert the injected script blurred/removed what the policy demands
   (DOM/text extract, screenshot diff). This is the v0.33.21 vault-update-workflow QA path.
2. **Automation rendering** — navigate/screenshot/PDF/extract/sequences/sessions for
   build-to-render vaults and the UX-launcher previews.
3. **Reached two ways** — `x-sgraph-access-token` through the vault `/pw` proxy
   (same-origin, browser-friendly), or `X-API-Key` direct (server-to-server).

No new Playwright endpoints are required; the existing 16-route surface suffices. The
contribution here is **wiring + the QA sequences**, not new browser features.

---

## 9. Out of scope — the VNC server

Deliberately excluded (the project lead: "we are building this, except the VNC part"). The
VNC remote browser needs **one container per user** → a different isolation/scaling profile
from the four shared components. It can sit on this instance or a separate fleet; treated as
a separate concern. Mode 2's ALB and the UX launcher's "open in VNC viewer" anticipate it,
but provisioning it is not part of this stack.

## 10. Schemas + CLI (the assembly side)

Type_Safe, one class per file, `Safe_*` primitives, `Enum__*` not Literals.

| Schema | Key fields |
|--------|-----------|
| `Schema__Content_Proxy__Create__Request` | `mode: Enum__Content_Proxy__Mode`, `scripts_vault: Safe_Str__Id`, `vaults_to_copy: List__Safe_Str__Id`, `mitm_service_image`, `vault_app_image`, `region`, `instance_type` |
| `Schema__Content_Proxy__Stack__Info` | instance id/state/ip, `mode`, `scripts_vault`, `vaults_present`, component health |

CLI (8 standard verbs from `Spec__CLI__Builder` + extras):

```
sg-compute spec content_proxy create  [name?] --mode direct|vault-web
                                       --scripts-vault REF --copy-vault REF (repeatable)
                                       --region --instance-type --wait
sg-compute spec content_proxy list | info | delete | wait | health | connect | exec
sg-compute spec content_proxy copy-vaults [name?] --vault REF (repeatable)   # the deploy step
sg-compute spec content_proxy logs        [name?] --open-vault                # reopen the append→S3 log vault
```

`copy-vaults` is the "copy in the vaults that belong on it" deploy step (§7). `logs
--open-vault` surfaces role-two: open the shared S3-backed log vault from anywhere.

## 11. Testing — no mocks, layered

| Layer | Proves |
|-------|--------|
| L1 | sg-playwright pure CDP — browser launches, no proxy |
| L2/L3 | browser through a local HTTP proxy (in-process + real) |
| **L5 (new)** | **transform correctness** — drive a fixture page through mitmproxy + an in-memory MITM-service stub that injects a known script; assert the DOM is blurred/removed per policy. In-memory composition (`register_*__in_memory()`), no mocks |
| **L6 (new)** | **vault round-trip** — script published to a vault is the one injected; logs appended on the box reopen from a second environment (role-two S3 share) |
| deploy-via-pytest | `test_1__create_stack` → `test_2__component_health` (mitmproxy/MITM/playwright/vault) → `test_3__drive_through_transform` → `test_4__copy_vaults` → `test_5__logs_reopen` → `test_6__delete_stack` |

Real-Chromium integration gates on `SG_PLAYWRIGHT__CHROMIUM_EXECUTABLE`; skips when absent.

## 13. Open decisions

1. **Stack home** — does the 4-component docker-compose live as a `content_proxy` SG/Compute
   spec in *this* repo, or in `SGraph-AI__App__Send`? (Recommend: the **compose + deploy CLI
   here** as a spec; the MITM service and vault app stay their own repos/images.)
2. **mitmproxy ↔ MITM service wiring** — is the MITM service an mitmproxy **upstream**, or
   does a thin mitmproxy `--scripts` addon call `POST :10011` per flow to fetch the injected
   `<script>`? (The briefs say mitmproxy "hands the page to" the service — confirm the exact
   integration so the compose env is right.)
3. **Activation signal** — cookie today; is a header/policy-token wanted for the
   sg-playwright-driven QA path (which has no human cookie)?
4. **mitmproxy version pin** — reuse the VNC `10.4.2` pin, or has v11 been cleared here?
5. **Where the script vault and the log vault are referenced** — exact vault refs +
   the append-vault target the MITM/vault-app env expects.
