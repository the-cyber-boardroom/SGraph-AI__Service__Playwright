# Spec — content-transformation proxy stack

> **Implementation guidance** (diagrams, mockups, phased plan, testing, acceptance) lives in
> the brief pack: [`team/roles/architect/reviews/06/18/v0.2.63__content-transformation-proxy/`](../../../team/roles/architect/reviews/06/18/v0.2.63__content-transformation-proxy/00__README.md).
> This file is the contract.

A self-contained image runs the components that turn a request into a policy-transformed page:
a browser routes through **mitmproxy**, which (via a thin interceptor addon) hands every
HTML request/response to a **FastAPI MITM service**, which decides activation (cookie) and
**injects a `<script>`** that does the client-side transformation; **sg-playwright** drives
and QAs the result; the **vault app** ships the scripts in, streams logs out to S3, and serves
the UX. There are **two mitmproxy instances** (§3.1). The VNC remote browser is **out of
scope**. A **TUI** drives development, QA, and operations (§8).

---

## 1. The premise

Website transformation via a content proxy: based on criteria, blur/remove parts of a page so
the user sees only what their policy ("formula") allows. The **decision** to transform happens
server-side in the FastAPI service (keyed on a cookie); the **transformation** runs
client-side in an injected script, before render. The proxy stays light — it injects, it does
not rewrite the whole page.

---

## 2. The request-and-transform flow

```
  Browser (proxy configured)
        │  (1) GET
        ▼
  mitmproxy ──(2) fetch──▶ Origin
   (addon)  ◀─(3) page────┘
        │  (4) interceptor POSTs request, then response (with HTML body + Cookie header)
        ▼        to the FastAPI MITM service
  FastAPI MITM service  (:10011, x-api-key)
        │   • decide activation from mitm-* cookies
        │   • return modifications: modified_body (= page + injected <script>),
        │     headers add/remove, block, cached/override
        ▼  (5) interceptor applies modifications to the flow
  mitmproxy ──(6) deliver transformed page──▶ Browser
                                                 │  (7) injected <script> runs CLIENT-SIDE
                                                 ▼   blurs / removes before the user sees it
```

The integration is **not** an mitmproxy upstream. mitmproxy runs the **stock image** plus one
`--scripts` interceptor addon that calls the FastAPI service at `POST /proxy/process-request`
and `POST /proxy/process-response`. The exact contract (request/response payloads,
modification verbs, static-asset skipping, cookie control) is in brief-pack doc `03`.

## 3. The components and their roles

| Component | Role (one job) | Where it lives | Status |
|-----------|----------------|----------------|--------|
| **mitmproxy ×2** | **The proxy.** Stock image + the interceptor addon. Fetches origin, forwards HTML to the MITM service, applies the returned modifications, delivers the result. Does *not* decide or transform. | this repo (compose) over `mitmproxy/mitmproxy` | as-built |
| **FastAPI MITM service** | **Decide + inject.** Decides activation (cookie) and returns the modified body (page + injected `<script>`). Python 3.12 / OSBot stack; `x-api-key`; port **10011**; admin UI + console + mitm-scripts CLI. | `MGraph-AI__Service__Mitmproxy` | as-built |
| **sg-playwright** | **Browser automation / QA.** navigate · screenshot · PDF · extract · sequences · sessions. Drives a browser through the **internal** mitmproxy to exercise + assert the transform. Auth: `x-sgraph-access-token` via the vault `/pw` proxy, or `X-API-Key` direct. | **this repo** (`diniscruz/sg-playwright`) | as-built |
| **Vault app** | **Data backbone + UX.** SG API + vault + vault UI. Ships scripts in, streams logs out to S3, serves UX launcher + testing tools. | `SGraph-AI__App__Send` | as-built |

### 3.1 The two-mitmproxy model (key topology)

Playwright is hard and messy to drive through a proxy that enforces auth. So the stack runs
**two** mitmproxy instances, **both running the same interceptor and pointing at the same
FastAPI workflow**:

| Instance | Auth | Exposed to | For | Port |
|----------|------|-----------|-----|------|
| `mitmproxy-ext` | **Basic auth** | externally (the LB) | a human browser with the proxy configured (Mode 1) | `:8080` |
| `mitmproxy-int` | **none** | the docker network only (the Playwright browser) | sg-playwright scripted runs (the QA / automation path) | `:8081` |

This split *is* the pair of key deliverables (§9): one authed proxy a browser can use, and one
no-auth proxy sg-playwright can be scripted against — both reaching the same transformation.

---

## 4. The script is the formula

The injected `<script>` carries the rules (blur/remove). Updating filtering = shipping a new
script, not a redeploy. Today regex-and-graph, built **offline with LLMs** (off the request
path → deterministic runtime); direction of travel is semantic-graph. The script is
**version-controlled in a vault** (§5) and the MITM service injects the latest.

---

## 5. The vault's three roles + how vaults get onto the box

| Role | Vault carries | Direction | Effect |
|------|---------------|-----------|--------|
| **1 · Script management** | versioned transformation scripts | vault → server | update filtering by updating the vault |
| **2 · Logging (append → S3)** | server logs via the **append** feature | server → vault → S3 | a fleet appends to one S3-backed vault → one distributed, reopenable log store |
| **3 · Vault apps** | testing tools + the UX launcher | vault → user | the experience + the test harness |

**Loading vaults at build/deploy** (the script vault and the log vault are vaults *inside* the
vault app, released with this deployment, locally and on EC2). The stack must be able to
populate a set of vaults at build/launch time, by either:

- **zip** — a bundled vault archive copied in, or
- **`sgit clone`** — cloned from a live server or an S3 bucket (precedent:
  `sg_compute/platforms/ec2/user_data/Section__SGit_Venv.py`).

`Schema__Content_Proxy__Create__Request.vaults_to_load` carries the list; each entry is a
`Schema__Content_Proxy__Vault__Source` (`kind ∈ {ZIP, SGIT}`, `ref`, `target`). The deploy
verb `load-vaults` performs the copy-in (§7 deploy model).

## 6. Two modes → two load balancers

| Mode | Path | LB | Notes |
|------|------|----|-------|
| **1 · Direct proxy** | user's browser (proxy set) → `mitmproxy-ext` (basic auth) | **NLB (L4)** | user's browser renders |
| **2 · Vault / web** | user hits the vault app / web page (UX launcher; Mode-2 VNC viewer) | **ALB (L7)** | nothing on the user's machine; VNC out of scope |

Behind either, an **auto-scaling group** of stateless instances all feed the same S3-backed
vault (§5 role 2) — scaling 2→N is free because no instance holds unique state.

## 7. The stack assembly — this repo's `content_proxy` SG/Compute spec

All code lives here. Conformant to `v0.2.6__authoring-a-new-top-level-spec.md`.
`spec_id = content_proxy`, PascalCase `ContentProxy`. It owns the **compose template +
user-data + CLI + TUI + tests** that assemble the components; it references the MITM service
and vault-app images, it does not re-implement them.

### 7.1 Compose services + env

| Service | Image | Ports | Key env |
|---------|-------|-------|---------|
| `mitmproxy-ext` | `mitmproxy/mitmproxy` (pin per VNC precedent) | `:8080` | `--scripts interceptor.py --proxyauth user:pass`; `FASTAPI_BASE_URL=http://mitm-service:10011`, `FASTAPI_API_KEY_NAME`, `FASTAPI_API_KEY_VALUE` |
| `mitmproxy-int` | same image | `:8081` (network-local) | same `--scripts` + env, **no `--proxyauth`** |
| `mitm-service` | `MGraph-AI__Service__Mitmproxy` | `:10011` | `FAST_API__AUTH__API_KEY__{NAME,VALUE}`; script-vault ref |
| `sg-playwright` | `diniscruz/sg-playwright` | `:8000` | `X-API-Key`; `SG_PLAYWRIGHT__DEFAULT_PROXY_URL=http://mitmproxy-int:8081` + `IGNORE_HTTPS_ERRORS` |
| `vault-app` | `SGraph-AI__App__Send` | `:443`/`:8080` | `SEND__STORAGE_MODE`→S3; append target; `/pw` reverse-proxy to sg-playwright |

### 7.2 Deploy model

Spin up the docker-compose → **`load-vaults`** (copy in the script + log + UX vaults via
zip/sgit, §5) → done. Stateless beyond vaults; the ASG grows/shrinks freely. (cross-ref the
v0.33.2 aws-deployment and v0.32.4 ephemeral-compute briefs.)

## 8. The TUI (development · QA · operations)

A Textual TUI matching the **Sentinel / sg_edge** pattern (pure `*__Render` fns + thin screens
over `Content_Proxy__TUI__Source`; every command `--json` + a no-TTY plain fallback; chat /
`tui_api` shape ready but wiring deferred). Mounted as `sp content-proxy tui` (or
`sg content_proxy tui`).

| Screen | Shows |
|--------|-------|
| `status` | health of all 5 services (ext/int mitmproxy, MITM service, sg-playwright, vault app) + which script is active |
| `traffic` | live flows: per request — processed / skipped(static) / injected / blocked / cached / fallback |
| `scripts` | the script vault — versions, the active one, diff |
| `transform` | dev/QA: run a URL through the workflow, show before→after (DOM/text + screenshot), and the injected `<script>` |
| `logs` | the append→S3 log vault (reopen from anywhere — role 2) |

Full mockups: brief-pack doc `02`. The TUI is the operator surface for the testing strategy
(§ below) — drive a corpus, watch accuracy, inspect a single flow.

---

## 9. Key deliverables

1. **(a) An authed external mitmproxy endpoint** (`mitmproxy-ext`, basic auth) reachable by a
   browser with its proxy configured → the page is transformed by the FastAPI workflow.
2. **(b) A scriptable sg-playwright endpoint** that drives a browser through the **second,
   no-auth** mitmproxy (`mitmproxy-int`) into the **same** FastAPI workflow → automation/QA
   gets the identical transform without fighting proxy auth.
3. The **`content_proxy` spec** (compose + `create`/`load-vaults` CLI), the **TUI**, and the
   **test suite** (per-piece + integration), all in this repo.

---

## 10. Testing (summary — full strategy in pack doc `05`)

No mocks; in-memory composition; layered. Per-piece first, then integration:

- **Interceptor addon** — pure-function unit tests (`should_process_*`, `prepare_*_data`,
  `apply_*_modifications`) over fixture flows; no live mitmproxy needed.
- **FastAPI MITM contract** — `/proxy/process-request|response` round-trips against an
  in-memory service.
- **sg-playwright** — the L1–L4 proxy ladder + a new transform-correctness layer.
- **Integration** — browser→`mitmproxy-ext`→MITM→transformed page; sg-playwright→
  `mitmproxy-int`→MITM→transformed page (the two deliverables, asserted).
- **Traffic corpus** — labelled pages (should-blur / should-block / should-pass) replayed
  through the workflow with an accuracy + latency report (Sentinel `traffic` precedent), driven
  and inspected from the TUI.
- **deploy-via-pytest** — numbered stack lifecycle.

## 11. Open decisions (post-answers)

Resolved by the owner (2026-06-18): stack lives **here**; mitmproxy↔MITM is the **stock image
+ interceptor addon calling `:10011`** (not upstream); **cookie** activation (FastAPI-owned);
two mitmproxies (ext-auth / int-noauth); vaults loaded via **zip or sgit**. Remaining:

1. **mitmproxy version pin** — reuse the VNC `10.4.2` pin, or clear a newer line? (Recommend:
   reuse `10.4.2` until re-verified.)
2. **MITM-service image source** — pull `MGraph-AI__Service__Mitmproxy` from a registry, or
   build it in this repo's compose? (Recommend: pull a pinned image.)
3. **QA cookie path** — sg-playwright runs have no human cookie; the QA sequence sets the
   `mitm-*` cookie(s) explicitly via the Playwright context. Confirm the cookie names/values
   the FastAPI service expects (`mitm-show`, `mitm-inject`, `mitm-debug`, …).
4. **Basic-auth secret source** — `mitmproxy-ext` `--proxyauth` creds: env / vault / generated
   at launch (like the VNC operator password)?
