# TL;DR

- Browser **DNS caching is per-FQDN** — the user's intuition is correct. There is no
  "wildcard DNS cache." Each FQDN gets its own cache entry, its own TTL, its own resolved
  IP set.
- **But "DNS pinning" in browsers isn't really a DNS-layer phenomenon.** It's actually
  HTTP/2 (and H3) **connection coalescing** — a TLS/socket-pool feature that operates
  AFTER DNS resolution.
- For our specific setup (`<slug>.aws.sg-labs.app` and `waker.aws.sg-labs.app` both served
  by the same CloudFront distribution with the `*.aws.sg-labs.app` wildcard cert),
  coalescing **is met by design** — both subdomains share a cert and share CloudFront
  edge IPs. Chrome will route a fetch to `waker.aws.sg-labs.app` down the existing
  H2 connection that's pinned to a CloudFront IP for `<slug>.aws.sg-labs.app`.
- **The Lambda Function URL** (`<uuid>.lambda-url.<region>.on.aws`) has different IPs
  AND a different cert (`*.lambda-url.<region>.on.aws`). Coalescing fails on both
  conditions. That's the only known-good cross-origin polling target.
- Empirical test recipe at the bottom — verify in DevTools yourself before assuming.

# The two layers

## DNS layer (per-FQDN — user's intuition)

```
client                          authoritative
  │                                  │
  │ dig aaa.aws.sg-labs.app          │
  ├──────────────────────────────────►
  │                       A 99.86.x.1│  ← from * wildcard rule
  │                       A 99.86.x.2│     applied per-query
  │◄──────────────────────────────────┤
  │
  │ dig bbb.aws.sg-labs.app          │
  ├──────────────────────────────────►
  │                       A 99.86.x.1│  ← same * rule, same result
  │                       A 99.86.x.3│     (subset shuffled)
  │◄──────────────────────────────────┤
```

The browser caches each FQDN separately. `dig *.aws.sg-labs.app` fails — wildcards are
authoring-side rules, not queryable records. The user is 100% right about this.

## Transport layer (post-resolution — where coalescing lives)

After DNS resolves, the browser opens a TCP+TLS connection to one of the returned IPs.
That connection is kept in the **socket pool** keyed by (host, port). When a new request
arrives for a DIFFERENT hostname, modern browsers check if an existing socket can be
reused, based on cert + IP overlap. This is "connection coalescing" and it's defined by
RFC 7540 §9.1.1.

```
                    Browser socket pool
                ┌──────────────────────────┐
                │ conn-A   to 99.86.x.1    │  ← opened for <slug>.aws.sg-labs.app
                │   cert SAN: *.aws.sg-labs│
                │   protocol: H2           │
                └──────────────────────────┘

  new fetch to waker.aws.sg-labs.app
       │
       ├─► resolve  → {99.86.x.1, 99.86.x.2}
       │
       ├─► is conn-A's cert valid for waker.aws.sg-labs.app?
       │   (*.aws.sg-labs.app SAN match — YES)
       │
       ├─► is conn-A's remote IP (99.86.x.1) in the new resolved set?
       │   (YES — it's the first element)
       │
       └─► COALESCE. The fetch reuses conn-A. No new TCP connect.
           No new DNS work matters at this point.
```

This is why the user can `dig` two subdomains independently and see independent DNS
behaviour, but Chrome can still reuse one socket for both. The two layers are decoupled.

# The exact rule (Chrome)

Implemented in Chromium `net/spdy/spdy_session_pool.cc`:

- `SpdySessionPool::FindAvailableSession` — primary entry point. Gated on
  `enable_ip_based_pooling`.
- `SpdySessionPool::FindMatchingIpSession` — looks up the `aliases_` map (IP endpoint →
  session key) populated when each session is created via
  `available_session->GetPeerAddress(...)`.
- `SpdySession::VerifyDomainAuthentication(host)` — checks that the existing TLS cert
  authenticates the new host (SAN + HPKP/CT). If false, coalescing is refused.

Coalescing fires iff ALL of:

1. Both URIs are HTTPS, same port (always 443 for us)
2. Existing connection is H2 (or H3)
3. Existing connection's cert has a SAN matching the new hostname
4. The existing connection's **peer IP** is in the new hostname's resolved A/AAAA set
5. Matching `NetworkAnonymizationKey` (partition key — added M85+)
6. Matching `SocketTag`, `PrivacyMode`, `SecureDnsPolicy`
7. Same proxy chain
8. Connection is not a client-cert connection (Enterprise opt-in only)

Conditions 5-8 are usually trivially met for our scenario. The IP check (4) is the one
that disqualifies the Lambda Function URL approach from being coalesced.

# The exact rule (other browsers)

- **Firefox**: Same cert+IP rules but Bug 1420777 / 1363451 made the IP check
  "set-overlap" rather than "currently-used IP must be in new set." Slightly more
  aggressive than Chrome. Also the only browser that respects the H2 ORIGIN frame.
- **Safari/WebKit**: Coalesces similar to Firefox but does NOT honor `421 Misdirected
  Request` responses (`pomerium/pomerium#2150`).
- **Edge**: Follows Chromium.

# Applied to our config

| Pair                                                          | Cert match? | IP overlap? | Coalesces? |
|---------------------------------------------------------------|:-----------:|:-----------:|:----------:|
| `<slug>.aws.sg-labs.app` ↔ `waker.aws.sg-labs.app` (same CF)  | YES         | YES (same CF distribution → same edge IPs) | **YES** |
| `<slug>.aws.sg-labs.app` (direct to EC2 IP) ↔ `waker.aws.sg-labs.app` (CF) | YES (wildcard still covers waker) | NO (EC2 IP ≠ CF IPs) | NO |
| `<slug>.aws.sg-labs.app` ↔ Lambda Function URL                | NO (different cert: `*.lambda-url.<region>.on.aws`) | NO | NO |
| `<slug>.aws.sg-labs.app` ↔ `waker.sg-labs.app` (different parent zone) | NO (different cert) | NO | NO |

For warming-page polling, the **first row** is the case we care about — the warming page
is rendered exactly when DNS hasn't converged yet, so `<slug>.aws.sg-labs.app` still
resolves via the CF wildcard. Both conditions (cert + IP) hold → coalescing applies.

Once the per-slug A record converges, `<slug>` resolves to the EC2 IP and the IP check
fails for any new connection. But the EXISTING H2 connection (pinned to a CF IP) is
unaffected and can still be reused for waker fetches — and that's the connection we're
trying to let drain.

# Whether CloudFront actually returns overlapping IPs in practice

This is the one piece worth verifying yourself, because it's deployment-specific. The
documented CloudFront routing model returns IPs per (distribution + edge POP + client
geo/resolver) — NOT per-hostname. Two subdomains pointed at the same distribution
should get the same edge IP pool from a given client.

But "rotated subset" behaviour can vary. Quick test from the user's machine:

```bash
dig +short aaa.aws.sg-labs.app
dig +short bbb.aws.sg-labs.app
# Check: any IP in both result sets?
```

If yes (highly likely for same-distribution wildcards), the IP-overlap precondition for
coalescing is met. If no (unusual but theoretically possible with custom CF settings),
you'd be insulated by accident — but you can't rely on it staying that way.

# Recent Chrome changes (2024-2026)

Coalescing has gotten **more** restrictive, not less:

- Network-state partitioning (~M85+) adds the `NetworkAnonymizationKey` to the session
  key. A top-level site A iframe cannot coalesce onto a session opened by top-level
  site B even with SAN+IP match.
- Client-cert connections excluded from coalescing by default (Enterprise opt-in via
  `CoalesceH2ConnectionsWithClientCertificatesForHosts`).
- ORIGIN frame partially respected (still not by Safari).
- CORS layer is enforced AFTER coalescing decision — so a cross-origin `fetch()` with
  `mode: cors` still rides the coalesced connection at the socket level; CORS just
  decides whether the JS can READ the response. Coalescing happens either way.

Cloudflare's experiment data suggests subresource coalescing fires for ~78% of Chrome
connections in the wild. fetch/XHR results were more mixed but it does happen.

# Empirical verification (any team member can run)

1. Chrome → DevTools → Network panel
2. Right-click column headers → enable **Connection ID** and **Remote Address**
3. Load `https://tls-test-N.aws.sg-labs.app/` (warming page renders)
4. In DevTools Console, run:
   ```js
   fetch('https://waker.aws.sg-labs.app/__waker__/probe?slug=tls-test-N', {
     mode: 'cors', credentials: 'omit'
   }).then(r => r.text()).then(console.log)
   ```
5. In the Network panel, find the row for that fetch. Note its **Connection ID** and
   **Remote Address**.
6. Compare to the original document request. If both rows show the **same Connection
   ID**, coalescing is happening. If different IDs, they're separate sockets.

For deeper diagnostics: `chrome://net-export/` → record → reproduce → load into
[netlog-viewer](https://chrome.google.com/webstore/category/extensions) → search for
`HTTP2_SESSION_POOL_FOUND_EXISTING_FROM_IP_POOL` events.

(We can't run this yet because `waker.aws.sg-labs.app` doesn't have an admin app
deployed; needs Phase 2 of `v0.1.15__vault-admin-ui`. The Lambda Function URL approach
works today without any test — its different IPs + different cert preclude coalescing
unconditionally.)

# Recommended path

For warming-page **polling traffic**: keep using the Lambda Function URL approach. Its
different IPs and different cert preclude coalescing unconditionally.

For the **admin UI** (inventory, per-slug status, setup pieces): use `waker.aws.sg-labs.app`.
Operators load it separately, in their own tab — they don't care about coalescing
between this tab and a slug tab, because there isn't a workflow that requires the admin
tab to communicate with the slug tab via shared sockets.

Different concerns, different hosts.
