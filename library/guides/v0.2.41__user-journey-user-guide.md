# User-Journey — test it & watch browser traffic

> **Scope.** This is the operator/engineer guide for the **user-journey** tier: one
> declarative journey → a fan-out suite of Playwright browser workers, run and
> monitored by an on-box conductor. It explains (1) what you can test today, (2) how
> the per-run traffic capture works, and (3) the exact commands to run a journey and
> watch its browser's network traffic. Everything here is **code-verified**; the
> deployment shell (Docker images, CI, EC2, deploy-via-pytest) is **not built yet** —
> see [Gaps](#gaps--not-built-yet).

---

## The two test layers

| Layer | Needs | What it proves |
|-------|-------|----------------|
| **Unit suite** | nothing (pure / in-memory) | All the logic: planning, evaluation, aggregation, the conductor API, the tool-API gate, the CLI verbs, the env-JSON delivery round-trip. **~140 tests, no mocks.** |
| **Live run** | a real Chromium (+ a mitmproxy to capture) | A real browser actually executes a journey and you see the traffic it generated. |

### Run the unit suite (no browser)

```bash
python -m pytest sg_compute_specs/user_journey/
```

Green here means the logic is correct. It does **not** drive a real browser — that's the live run below.

## How traffic capture works

The browsers are pointed at a **mitmproxy sidecar** (the `sg_compute_specs/mitmproxy/`
package) at launch. Each journey stamps a unique **`X-SG-Run-Id`** header on every
request (`Journey__Sequence__Builder`), and a mitmproxy addon
(`core/addons/run_capture_addon.py`) buckets every flow by that header. You then read
one run's flows back by id.

```
Playwright browser ──(proxy :8080)──▶ mitmproxy ──┬─▶ upstream site
   every request carries X-SG-Run-Id              │
                                                  └─▶ run_capture addon buckets per run-id
                                                        │
   GET /capture/network-log/{run_id}  ◀────────────────┘   (admin API :8000, NDJSON)
```

The mitmproxy sidecar exposes:

- **`:8080`** — the forward proxy the browser uses
- **`:8000`** — the admin API, including `GET /capture/network-log/{run_id}` (NDJSON of that run's flows)
- **`:8081`** — the live **mitmweb** UI (also reverse-proxied under the admin API at `/web/*`) — watch flows in real time

## Watch traffic from ONE journey on your laptop — `run-local`

`sg user-journey run-local` runs a single journey against a real local Chromium and
prints the result. Point it at a mitmproxy and it also prints the captured flows. **No
conductor, no Docker, no AWS.**

### Prerequisites

- **Chromium** — set `SG_PLAYWRIGHT__CHROMIUM_EXECUTABLE` to a Chromium binary (e.g. the one Playwright installs). Without it the browser can't launch.
- **(optional) a local mitmproxy** — only needed to *capture* traffic. Easiest is to run the agent-mitmproxy image/service so `:8080` (proxy) and `:8000` (admin) are up. Without it, `run-local` still runs the journey; it just reports `0 flows`.

### A minimal journey file

`checkout.json`:

```json
{
  "journey_id": "checkout",
  "target_url": "https://example.com/",
  "environment": "dev",
  "steps": [
    {"action": "goto", "url": "https://example.com/"}
  ],
  "assertions": [],
  "tags": []
}
```

### Run it

Without capture (just see the result):

```bash
export SG_PLAYWRIGHT__CHROMIUM_EXECUTABLE=/path/to/chromium
sg user-journey run-local checkout.json
```

With capture (see the browser's traffic):

```bash
export SG_PLAYWRIGHT__CHROMIUM_EXECUTABLE=/path/to/chromium
sg user-journey run-local checkout.json \
    --proxy       http://127.0.0.1:8080 \
    --capture-url http://127.0.0.1:8000
```

Output (human form):

```
  run local-9f1c2a3b4d5e  journey=checkout  status=passed
  3 flow(s) captured
  GET    200  https://example.com/
  GET    200  https://example.com/style.css
  GET    204  https://example.com/favicon.ico
```

`--json` emits `{run_id, result, flows}` for piping. `--proxy` / `--capture-url`
also read `SG_PLAYWRIGHT__DEFAULT_PROXY_URL` / `SG_UJ__CAPTURE_URL` from the env.

## Watch traffic from a suite run — the conductor

When a suite runs on a conductor, view any worker run's flows through the control plane:

```bash
sg user-journey flows <run-id> --conductor http://<host>:<port> --api-key <key>
```

This proxies the conductor's `GET /suites/{run_id}/flows` (NDJSON) — which in turn
reads the mitmproxy capture. `--json` for the full records. You can also open the live
**mitmweb** UI (`:8081`) to watch flows as they happen.

## The full CLI surface — `sg user-journey` (alias `sg uj`)

| Command | Does |
|---------|------|
| `sg uj run-local <journey.json>` | Run one journey locally against real Chromium; print result + flows |
| `sg uj status <run-id>` | Cockpit snapshot of a suite run (worker grid + aggregates) |
| `sg uj flows <run-id>` | Captured network flows for a suite run |
| `sg uj scale <run-id> <count> <concurrency>` | Resize a running suite |
| `sg uj stop <run-id>` | Stop a running suite |
| `sg uj cockpit <run-id>` | Live Textual cockpit (interactive) |
| `sg uj chat [--workflow monitor\|operate\|load]` | Conversational cockpit — an LLM drives the conductor via the granted workflow tools |

`status` / `flows` / `scale` / `stop` / `cockpit` / `chat` talk to a **remote conductor**
(set `--conductor` / `SG_UJ__CONDUCTOR_URL` + `--api-key` / `SG_UJ__CONDUCTOR_API_KEY`).
`run-local` is the only one that needs no conductor.

## Environment variables

| Variable | Used by | Meaning |
|----------|---------|---------|
| `SG_PLAYWRIGHT__CHROMIUM_EXECUTABLE` | Browser launch | Path to the Chromium binary (required for any real run) |
| `SG_PLAYWRIGHT__DEFAULT_PROXY_URL` | Browser launch | Proxy the browser routes through (the mitmproxy `:8080`) — applied at launch |
| `SG_UJ__CONDUCTOR_URL` / `SG_UJ__CONDUCTOR_API_KEY` | conductor verbs | Conductor base URL + X-API-Key |
| `SG_UJ__CAPTURE_URL` / `SG_UJ__CAPTURE_API_KEY` | `run-local`, conductor `/flows` | mitmproxy admin URL + X-API-Key (flows source) |
| `SG_UJ__RUN_ID` / `SG_UJ__JOURNEY_JSON` / `SG_UJ__WORKER_ID` / `SG_UJ__JOURNEY_ID` / `SG_UJ__ENVIRONMENT` | worker container | Injected by the Docker runtime; read by `Journey__Worker__Entrypoint` inside a worker container |

## Gaps — not built yet

These are **PROPOSED — do not exist yet** (see `team/roles/librarian/reality/user-journey/proposed/index.md`):

- Worker + conductor **Docker images** and **Docker Hub CI**.
- EC2 **conductor-host** provisioning / lifecycle.
- **deploy-via-pytest** + live load runs (the full Docker+conductor+mitmproxy stack end-to-end).
- A one-command **local mitmproxy** launcher — today you bring your own (the agent-mitmproxy image/service).
- Vault-stored **suites by id** + a journey store.

So today the *fully wired, one-command* live path is **`run-local`** (single journey,
your own Chromium + optional mitmproxy). The multi-worker suite path runs in-memory
under the test suite; running it against real containers is the deploy harness, which
is the next milestone.
