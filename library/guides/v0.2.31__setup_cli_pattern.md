# The Setup-CLI Pattern: principles for multi-piece operational tools

- **version**: v0.2.31
- **updated**: 19th May 2026
- **case study**: `sg vp setup` — vault-publish shared-infra management
- **when to read**: Before building any CLI / API surface that manages **N independent-but-connected resources** (multi-AWS-region, multi-cloud, multi-stage deployments, infra setup, lifecycle orchestration). Read after `v0.24.2__fast_api_routes.md` if you're also adding HTTP routes.

---

## TL;DR

Every multi-piece operational tool (a thing that manages > 1 resource as a coherent system) MUST expose:

1. **Areas** — each resource concern is a named area (`iam`, `lambda`, `cf-function`, …).
2. **Five verbs per area** — `check / status / create / update / delete`.
3. **Global aggregator at the top level** — `<tool> setup check` runs all areas; `create` / `update` / `delete` do dependency-ordered orchestration.
4. **Drift-first vocabulary** — every mutation describes the *desired state*, not an action. Operators ask "what's different?" before "what should I do?".
5. **Three surfaces** — the same operations exposed via CLI, HTTP API, and (when applicable) a browser console.
6. **Mutation gates** — env-var-controlled to make mutations explicit.
7. **Identity + plan announcement** — every command prints *who is acting* and *what will change* before doing anything.
8. **Self-verification loop** — every mutation is followed by a re-check, and the re-check uses the same code path as the standalone `check` verb.

When you build a new tool that doesn't follow this, you accumulate ad-hoc one-off commands, your operators can't tell what's broken, and you can't recover from partial state. This guide exists because we re-discovered the cost three times before writing it down.

## The case study — what good UX looks like

A real workflow that took ~30 seconds and is conclusively diagnostic, fix-it-now, and self-verifying:

```bash
$ sg vp setup check
  ℹ  for this action, assuming role 'iam-admin'
  ✓  identity: arn:aws:iam::745506449035:user/SG-IAM-Actions

  Area           State      Detail
  ec2            ✓ OK       profile=playwright-ec2 ami=ami-0272ade54c4f22c84
  iam            ⚠ DRIFT    arn:aws:iam::745506449035:role/sg-compute-vault-publish-waker-role
  lambda         ✓ OK       https://i5dhd…lambda-url.eu-west-2.on.aws/
  cf             ✓ OK       d2n03kv7cxdjms.cloudfront.net
  cf-function    ⚠ DRIFT    attached → E2TOUXY8I7QAOG
  acm            ✓ OK       arn:aws:acm:us-east-1:…
  dns            ✓ OK       d2n03kv7cxdjms.cloudfront.net

$ sg vp setup iam               # implicit "discover what's here" — shows subcommands

$ sg vp setup iam update        # imperative-by-name, declarative-by-effect
  →  Updating IAM inline policy…
  IAM role: sg-compute-vault-publish-waker-role  ✓ OK
  ✓  Policy updated and matches template

$ sg vp setup cf-function update  # same vocabulary, different area
  →  Updating CF Function for *.aws.sg-labs.app…
  Stage        : LIVE
  Code matches : yes
  Attached     : yes  → E2TOUXY8I7QAOG

$ sg vp setup check               # verify — same command, every row ✓
  Area           State    Detail
  ec2            ✓ OK     …
  iam            ✓ OK     …      ← was ⚠ DRIFT
  lambda         ✓ OK     …
  cf             ✓ OK     …
  cf-function    ✓ OK     …      ← was ⚠ DRIFT
  acm            ✓ OK     …
  dns            ✓ OK     …
```

Why this is a good experience:

| Observable | Underlying principle |
|---|---|
| `ℹ for this action, assuming role 'iam-admin'` | **Identity announcement** (P1) — operator knows what credentials are in play |
| `✓ identity: arn:aws:iam::…:user/SG-IAM-Actions` | **Identity verification** (P1) — sts:GetCallerIdentity confirmed before anything else runs |
| Table of 7 rows with explicit state per area | **Drift-first** (P4) — operator sees current vs desired in one frame |
| `⚠ DRIFT` not `✗ ERROR` | **State has a vocabulary** (P4) — DRIFT means "fixable via update", ERROR means "needs investigation" |
| `setup iam` with no arg → typer help | **Self-documenting** (P8) — the help screen IS the spec |
| Same five verbs across `iam`, `cf-function`, `lambda`, etc. | **Uniform vocabulary** (P2) — one learning curve, N resources |
| `update` *describes desired state*, applies diff | **Idempotent** (P6) — running it twice is safe |
| Re-running `check` confirms the fix | **Self-verification loop** (P8) — verify uses the same code as the standalone check |
| Per-row "Detail" shows the actual resource identifier | **Greppable output** (P7) — easy to parse, share, grep, jq |

That's eight principles observed in a 6-command workflow. Below is the full set with implementation guidance.

## The 10 principles

### P1 — Identity announcement, before any action

Every command prints (i) who's about to act, (ii) what credentials are in play, BEFORE running. Use `sts:GetCallerIdentity` as the verification.

```
ℹ  for this action, assuming role 'iam-admin'
✓  identity: arn:aws:iam::745506449035:user/SG-IAM-Actions
```

Why: in multi-account / multi-role environments, the #1 cause of "I'm sure I deleted that" is "wrong account". Make the credentials boundary visible.

### P2 — Five verbs per area; no exceptions

Every area exposes exactly these five (omit any that don't apply, but don't introduce alternatives):

| Verb | Returns | Side-effect | Gate |
|---|---|---|---|
| `check` | Schema with `state`, `issues`, area-specific fields | None — read-only | None |
| `status` | Pretty-printed live config dict | None — read-only | None |
| `create` | Same shape as `check`, returns post-create state | Creates if missing; no-op if present and matching | `_REQUIRES_MUTATIONS` env gate |
| `update` | Same shape as `check`, returns post-update state | Modifies to match template; no-op if already matches | `_REQUIRES_MUTATIONS` env gate |
| `delete` | `True` on success | Removes the resource | `_REQUIRES_DELETES` env gate |

`check` and `status` are NOT the same:
- `check` is structured (boolean per concern, a list of issues, parseable). Used by `setup check` aggregator.
- `status` is human-readable, dumps full config. Used for ad-hoc inspection.

### P3 — Top-level aggregator runs every area

```
<tool> setup check    # runs all areas in any order, summary table
<tool> setup create   # runs all areas in dependency order
<tool> setup update   # ditto
<tool> setup delete   # reverse dependency order
```

Implementation: same `_AREAS` registry feeds the aggregator and the per-area sub-apps. Use `rich.live.Live` with a table that resolves row-by-row so the operator sees progress (no silent 30-second gaps).

### P4 — Drift is a first-class concept, not an error

Each area's `check` reports one of:

| State | Meaning | Operator action |
|---|---|---|
| `OK` | Live matches template | None |
| `DRIFT` | Resource exists but config differs from template | `<area> update` |
| `MISSING` | Resource doesn't exist | `<area> create` |
| `ERROR` | Couldn't determine state (API error, perms, network) | Investigate |
| `UNKNOWN` | Not yet checked / pre-init | Re-run |

This vocabulary lets the operator pick the right verb without thinking. `DRIFT` always maps to `update`; `MISSING` always maps to `create`; `ERROR` always needs human attention.

Implementation: drift detection MUST be at the semantic-statement level, not action-level. For IAM, compare `{(effect, sorted(actions), sorted(resources), condition_json)}` sets — NOT just the action list. For CF Functions, compare normalised source (whitespace-stripped). For DNS, accept either CNAME or A-alias as semantically equivalent.

### P5 — Self-describing help is the contract

```
$ <tool> setup iam            # no args → typer auto-prints subcommands + descriptions
```

Help text is the operator's API doc. Every verb's `help=` must describe:
- What it does (one sentence)
- What env vars / IAM perms it needs
- What's safe to re-run (idempotency contract)

Example:
```python
@iam_app.command(name='update', help='Sync inline policy with Waker__Policy__Template. Requires SG_AWS__VAULT_PUBLISH__SETUP__ALLOW_MUTATIONS=1.')
```

If you can't fit it in one help line, the verb is doing too much — split it.

### P6 — Idempotent always; "create" means "ensure exists matching template"

`create` on an already-existing matching resource is a NO-OP, returns OK. `create` on a non-matching existing resource MAY refuse (preferred — force the operator to `update` explicitly) or fall through to update (acceptable for non-destructive deltas). NEVER recreate-by-deleting unless `--force` is passed.

`update` re-asserts the desired state. Running it 10 times in a row makes no AWS changes after the first. Tests for `update` should include "no-op on second call" as a contract.

### P7 — Greppable, parseable output

Every detail line in `check` follows `<area>  <state-icon>  <detail-string>` so operators can:

```bash
sg vp setup check | grep DRIFT
sg vp setup check | awk '{print $1, $2}'
```

`status` outputs `key: value` pairs (one per line) for the same reason. NO multi-line nested structures in default output. Use `--json` or `--full` flags for the rich form.

### P8 — Self-verification loop

A mutation verb's success isn't `True` returned from the API — it's a successful `check` afterwards. Implementation:

```python
def update(self) -> Schema__Setup__Foo__Report:
    _require_mutations()
    self._actually_mutate()
    return self.check()           # ← critical
```

Two-fold benefit:
1. The operator sees the post-state immediately (no need to run `check` separately).
2. If the mutation succeeded but the resource is still drifted (rare AWS eventual-consistency case), the operator sees DRIFT — not a misleading "✓ updated" followed by a still-broken resource.

### P9 — Mutation gates, env-var-controlled

Every mutating method first calls:

```python
def _require_mutations():
    if not os.environ.get('SG_AWS__VAULT_PUBLISH__SETUP__ALLOW_MUTATIONS'):
        raise RuntimeError('Set SG_AWS__VAULT_PUBLISH__SETUP__ALLOW_MUTATIONS=1 to allow mutations')

def _require_deletes():
    if not os.environ.get('SG_AWS__VAULT_PUBLISH__SETUP__ALLOW_DELETES'):
        raise RuntimeError('Set SG_AWS__VAULT_PUBLISH__SETUP__ALLOW_DELETES=1 to allow deletes')
```

Why: when an LLM operates the tool, env-var gates prevent runaway. When a human operator copy-pastes a command from a doc, missing gate = no accidental damage. Two separate gates (mutations vs deletes) because deletes are categorically more dangerous.

### P10 — Three surfaces for the same operations

When the tool is non-trivial, expose the same operations through:

1. **CLI** — `<tool> setup <area> <verb>` — the primary surface
2. **HTTP API** — JSON endpoints on the deployed service for machine-readable polling and remote operation
3. **Browser console** — HTML+JS UI for ad-hoc operator inspection without leaving the browser tab

Each surface uses the same dispatcher / service classes. Routes are pure delegation. The browser console bootstraps from the HTTP API (calls `?name=help`) so adding a command in the dispatcher automatically appears in both CLI and browser.

Example from `sg vp`:

| Operation | CLI | HTTP | Browser |
|---|---|---|---|
| List commands | `sg vp setup lambda cmd help` | `GET /__waker__/cmd?name=help` | `/__waker__/console` dropdown |
| Find slug | `sg vp setup lambda cmd find-slug slug=X` | `GET /__waker__/cmd?name=find-slug&slug=X` | Dropdown + arg row → Run |
| Deploy info | `sg vp setup lambda invoke` | `GET /__waker__/deploy` | Link in console header |

## The skeleton (copy-paste starting point)

```python
# Area service class — repeat per area
class Setup__Foo(Type_Safe):
    _client_factory: Optional[Callable] = None

    def _client(self):
        return self._client_factory() if self._client_factory else FooAWSClient()

    def check(self) -> Schema__Setup__Foo__Report:
        live = self._client().describe(NAME)
        if not live.exists:
            return Schema__Setup__Foo__Report(state=Enum__Setup__State.MISSING, …)
        # Compare live to template at the SEMANTIC level — not API-call equality.
        if self._matches_template(live):
            return Schema__Setup__Foo__Report(state=Enum__Setup__State.OK, …)
        return Schema__Setup__Foo__Report(state=Enum__Setup__State.DRIFT, …,
                                          issues=self._issues(live))

    def status(self) -> dict:
        return self._client().status_dict(NAME)

    def create(self) -> Schema__Setup__Foo__Report:
        _require_mutations()
        if not self._client().exists(NAME):
            self._client().create(NAME, self._template())
        return self.check()                            # ← self-verification

    def update(self) -> Schema__Setup__Foo__Report:
        _require_mutations()
        self._client().update(NAME, self._template())
        return self.check()

    def delete(self) -> bool:
        _require_deletes()
        return self._client().delete(NAME)
```

CLI plumbing (typer):

```python
foo_app = typer.Typer(name='foo', help='Foo management.', no_args_is_help=True)

@foo_app.command(name='check',  help='…')
@foo_app.command(name='status', help='…')
@foo_app.command(name='create', help='… Requires <PROJECT>__ALLOW_MUTATIONS=1.')
@foo_app.command(name='update', help='… Requires <PROJECT>__ALLOW_MUTATIONS=1.')
@foo_app.command(name='delete', help='… Requires <PROJECT>__ALLOW_DELETES=1.')
```

Aggregator (rich.live for progress):

```python
@app.command(name='check')
def setup_check():
    checks = [
        ('foo', lambda: _foo().check(), lambda r: r.detail),
        ('bar', lambda: _bar().check(), lambda r: r.detail),
        # …
    ]
    results = [(name, None, '') for name, _, _ in checks]
    with Live(_build_table(results), refresh_per_second=8) as live:
        for i, (name, run, fmt) in enumerate(checks):
            try:
                r = run()
                results[i] = (name, r.state, fmt(r))
            except Exception as exc:
                results[i] = (name, Enum__Setup__State.ERROR, str(exc))
            live.update(_build_table(results))
```

## When to apply this pattern

| Situation | Pattern fits? |
|---|---|
| Tool manages 1 resource | ❌ No — over-engineering. Just `<tool> install / uninstall / status`. |
| Tool manages 3+ independent-but-connected resources | ✅ Yes |
| Multi-region or multi-cloud orchestration | ✅ Yes — each region/cloud is an "area" |
| Deployment lifecycle (provision, update, decommission) | ✅ Yes — `create/update/delete` are the natural verbs |
| Long-running orchestration with multiple stages | ✅ Yes — adds the live progress table; see `setup lambda update --invoke` |
| Pure data CRUD (one table) | ❌ No — use a REST router or a database CLI |
| One-shot ETL / batch job | ❌ No — single-verb is fine |

Heuristic: **if your operator needs to ask "is everything OK?" and "what's broken?" — you need this pattern.**

## Anti-patterns to call out in PR review

| Anti-pattern | Why it's bad | What to do instead |
|---|---|---|
| `<tool> deploy` (single command, no `check`) | Operator can't tell what's broken or what was already done | Split into `check + create + update + delete` |
| Different verbs per area (`reset` here, `recreate` there) | N learning curves for N areas | Stick to the five-verb vocabulary |
| `update` that always recreates | Wasteful, destroys state, surprising | `update` describes desired state; recreate only on explicit `--force` |
| Drift detection at API-payload level | Spurious "drift" on field reorder / casing | Compare normalised semantic forms (statement sets, source after whitespace strip) |
| Silent mutations | Operators can't audit, LLMs can run amok | Always announce identity + plan + require mutation env gate |
| `create` returns `True`/`False` without re-reading state | Operator doesn't know the actual post-state | `create` and `update` MUST end with `return self.check()` |
| Help text says "TODO" or describes implementation | Operator sees only this text | Help text is the contract — describe behaviour, gates, idempotency |
| Drift detection that says "DRIFT" without showing what differs | Operator has to guess what to fix | Include the diff in the report — first divergent statement / line / byte |
| Mixed-region operations without a region check | Resources land in wrong regions silently (we hit this) | Detect deploy-target region and abort on mismatch (`--force-region-mismatch` to override) |
| No `--invoke` / verify-after-deploy flag on long-running mutations | Operator wonders if the deploy is live | Wire `--invoke` (or equivalent) to run a smoke check on the post-state |

## Companion patterns

These work alongside the Setup-CLI Pattern in the same tools:

| Pattern | When to add | Reference |
|---|---|---|
| **Debug RPC channel** | Tool runs on a remote service (Lambda, container, etc.) and you need ad-hoc introspection | `Waker__Commands.py` in vault-publish — decorator-based dispatch, gate-controlled, accessible via CLI + HTTP + browser |
| **200-OK status page** (not 404) | Service returns HTML to humans for unrouted requests | Vault Waker 200 status page — operator-friendly even on the unhappy path |
| **Deploy metadata env vars** | Service is deployed with versioned code | `WAKER_VERSION`, `WAKER_GIT_COMMIT`, `WAKER_DEPLOYED_AT` baked in at deploy time, surfaced everywhere |
| **Browser-renderable diagnostic page** | Operators sometimes use a browser as the first-touch debug tool | `/__waker__/status?slug=X` — same data as CLI `eval`, but renders inline |
| **Versioned files for each agent-managed surface** | LLM-managed code needs traceability per change | `sg_compute_specs/vault_publish/version` + `FUNCTION_VERSION` in `Setup__CF__Function.py` |
