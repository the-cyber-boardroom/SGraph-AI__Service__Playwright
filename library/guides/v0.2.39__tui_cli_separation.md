# TUIs as a GUI over the CLI

> **The one rule.** A TUI is the *visual* way to reach the CLI. It must never be the
> *only* way to do anything. Every data retrieval and every data transformation is
> reachable from a non-TUI command. The TUI owns no logic — it composes, navigates,
> visualises, and edits what the CLI and backend classes already do.

If you can do it in the TUI, you can do it from the CLI. If you can only do it from
the TUI, that is a bug — move the work down a layer.

---

## 1. Why this matters

We are adding features to the `sg` ecosystem faster than any single flat CLI can stay
legible. Two forces pull in opposite directions:

- **Doing the work** wants small, composable, scriptable, testable units — classes and
  CLI commands that one can pipe, automate, and assert on.
- **Consuming the work** wants a coherent, low-friction experience — a way to navigate
  the growing surface, see what is going on, and act without memorising flags.

TUIs let us serve *both* by **separating them**:

| Layer | Job | Examples |
|---|---|---|
| **Backend classes / APIs** | actually do the work; own all logic | `CF__Logs__Sync`, `CF__Local__Store`, `Firehose__AWS__Client`, the S3 boundaries |
| **CLI commands (native)** | a thin, scriptable verb over the backend; canonical entry | `sp el lets cf sync`, `sp el lets cf cache`, `sg aws firehose ls` |
| **TUI screens** | a GUI over those same commands/classes; navigate, visualise, edit | `sp el lets cf tui sync`, `… tui cache`, `… tui architecture` |

The CLI and backend **focus on doing**. The TUI **focuses on how it is consumed**. That
split is what actually reduces complexity: each layer stays small because it has one
job. The TUI is allowed to be rich and opinionated about UX precisely because it is not
also responsible for correctness.

---

## 2. The rule, stated precisely

1. **No TUI-exclusive capability.** Any retrieval/transformation a screen performs has a
   CLI command that performs the same work and emits the result as text.
2. **The TUI never owns logic.** Screens call the *same* backend classes / builders the
   CLI calls. No parsing, fetching, writing, or mutating that lives only in a screen.
3. **The TUI does not behave like a CLI.** A TUI command launches a visual experience.
   When run head-less (piped / CI), it shows a *read-only* static view and points at the
   native command — it does not silently perform mutations to imitate a CLI.
4. **Mutations have a native home.** Downloads, writes, deploys, edits are invoked from a
   native command (scriptable, auditable). The TUI may *trigger* them interactively (a
   keypress), but the action is the same backend call, and it is reachable without the TUI.
5. **Actions are capability-gated, and the gate is rendered.** Whether an action can run
   *right now* is a backend question — separate from whether there is a TTY. The screen
   asks the backend and renders the disabled/pending state honestly (a greyed key with a
   reason) rather than offering a key that raises when pressed. SG/Edge's
   `SG_Edge__TUI__Data_Source.can_act()` is the reference: the AWS source returns `False`
   until live mutations land (Slice 5), so the screen shows a "pending" hint, not an error.
   The same shape covers an `…_ALLOW_MUTATIONS` env gate or any not-yet-wired seam.
6. **Pair a mutation with a preview — and make the preview native too.** Before a
   creating/destroying action, show what it will do (the field-diff or the predicted
   outcome) so the operator commits with intent (the simulate principle; idiom #7). That
   preview is itself a CLI capability, never TUI-only — e.g. `sg edge local request <slug>`
   simulates the proxy decision in plain text, and a `--dry-run` flag previews a mutation.
   The safety affordance obeys the same "no TUI-exclusive capability" rule as the action.

## 3. Worked example — raw-cf-logs sync

The work lives in backend classes (`CF__Logs__Sync.plan()` / `.download_missing()` over
`CF__Local__Store` + the S3 boundaries). Two front-ends sit over them:

```
                    CF__Logs__Sync / CF__Local__Store        ← backend (all the logic)
                          ▲                     ▲
        build_sync_service()                build_local_store()
                          │                     │
   sp el lets cf sync ────┘                     └──── sp el lets cf cache     ← NATIVE CLI (canonical, scriptable)
        --date --hour --mode list|download

   sp el lets cf tui sync                              sp el lets cf tui cache  ← TUI (visual GUI over the same)
        (browse the plan, press `g` to download)            (browse the stats)
```

- **`sp el lets cf sync --mode download`** — the canonical, scriptable path. Lists or
  downloads, prints plain text. Use this in scripts, CI, automation.
- **`sp el lets cf tui sync`** — the *visual* path. Same plan, same `download_missing()`,
  but you navigate it and trigger the download with `g`, watching live progress and the
  Debug Panel. Run head-less, it prints the plan (read-only) and points you at the native
  command — it does **not** download.

Both construct the work through the same `build_sync_service()` builder — there is one
implementation of the logic, two ways to reach it.

## 4. What the TUI is *for* (the value in "just" a GUI)

Calling the TUI "just a GUI" undersells it. Because it carries no logic, it is free to be
excellent at the things a CLI is bad at:

- **Navigation** — drill folder → file → record; tab between related screens; one app for
  a whole domain instead of a flag soup.
- **Visualisation** — diagrams (the architecture wiring), tables, sparklines, colour-coded
  state, honest ⚠ UNVERIFIED / pending markers.
- **Editing** — in place, with context, against the same backend that validates.
- **Under-the-hood transparency** — the shared **Debug Panel** (`d` toggles) shows every
  CLI/backend call the screen makes, so the GUI teaches the CLI underneath it.
- **Complexity absorption** — the TUI is where we design the UX for an ever-growing
  surface, without the backend or CLI having to compromise their small, sharp shape.

## 5. How to build one (checklist)

When adding a capability:

1. **Backend first.** Put the logic in a `Type_Safe` class with injectable seams (tests
   subclass them — no mocks).
2. **Native CLI next.** Add a command that calls the backend and prints a plain-text
   result. This is the canonical, scriptable entry. Test it head-less.
3. **TUI last.** Subclass `Tui__App` (`cli/tui/components/Tui__App`), implement
   `populate()`, and render the *same* data the CLI produced. Reuse the shared render
   helpers (`cli/tui/render/Tui__Text`) and the Debug Panel. Share the backend builder
   with the CLI — never re-implement the work.
4. **Keep plain renderers in the CLI layer.** Plain-text rendering belongs with the CLI
   (e.g. `cf/local/cli/CF__Local__Render`); the TUI's head-less fallback imports *from*
   the CLI layer (the TUI depends on the CLI, never the reverse). Rich-markup renderers
   for the interactive screen live with the screen. *(Valid variant, used by SG/Edge:
   keep a single **pure render module** in the TUI layer that emits a markup string and
   have both the screen and its head-less fallback share it — the invariant is
   no-logic-in-the-screen and a one-way dependency, not the renderer's exact folder.)*
5. **The framework is an optional, lazy dependency.** Registering a `tui` command must
   not import Textual — import it *inside* the command body (as `sg edge tui` does). The
   native CLI must keep working when the TUI framework is absent: it is the GUI, not a
   requirement. Declare Textual as a dependency, but never make it load-bearing for the CLI.
6. **Testing matches the layers.** Backend classes, builders, and pure render helpers are
   unit-tested directly with no mocks (subclass the seams). Textual screens are driven by
   `App.run_test()` pilots and `@skipUnless` the framework — exactly as CLI suites
   `@skipUnless` typer — so the framework's absence never breaks test collection, and the
   pure layers stay runnable on the minimal interpreter.

## 6. Anti-patterns (do not ship these)

- A screen that gunzips / parses / fetches / writes with code that exists nowhere else.
- A `tui <thing>` command that performs a mutation when piped, to act like a CLI.
- A plain-text renderer importing from `tui/screens/*` into the CLI layer (wrong
  direction — invert it).
- Duplicated logic between a CLI command and its screen (share the builder/backend).
- An action key that is always live — pressed against a backend that can't act yet it
  raises, instead of rendering a disabled/pending state (gate it on a capability check).
- A destructive key with no preview and no confirm — fires the mutation on a single
  keypress with nothing shown first (pair it with a native preview + a confirm step).

## 7. Status of the principle in the codebase (v0.2.39)

- ✅ `sp el lets cf sync` / `cache` — native CLI commands (`cf/local/cli/Cli__CF__Local`).
- ✅ `sp el lets cf tui sync` / `cache` — visual front-ends over the same builders;
  head-less = read-only + pointer.
- ✅ `sg aws firehose ls|describe` — native CLI; the architecture screen consumes it.
- 🟡 Traffic / Files / Inspector screens predate this guide; they already read through a
  data-source seam, but should each gain a documented native CLI sibling and the Debug
  Panel as they are revisited.
- 🟢 SG/Edge TUI already follows the spirit: every screen is **read-only** over the same
  `Local__Edge__Stack` / `SG_Edge__DNS__Helper` / `Pod__Runtime__Docker` that the
  `sg edge` / `sg edge local` / host-plane CLIs use; head-less = a static card or plain
  text (never a silent mutation); honesty is encoded in a `capabilities` seam (cost /
  instance panes render "pending Slice 5", never faked); and presentation lives in **pure
  render modules** testable without Textual. Its `Data_Source.can_act()` is the reference
  for rule 5 (capability-gated actions). 🟡 It still ships its own base app
  (`SG_Edge__TUI__App__Base`) + table helper (`SG_Edge__TUI__Table`) + tabbed dashboard
  (`SG_Edge__TUI__App`) — converge these onto the shared `cli/tui/` components (the Debug
  Panel especially). One gap to close on convergence: give `sg edge tui docker` a native
  `sg edge`-level sibling (it reuses `Pod__Runtime__Docker` but has no `sg edge docker`
  text command yet). A prototype found Textual `DataTable` wins for **list** surfaces
  (slugs / events / containers) while markup-into-Static stays better for **diagram /
  detail** surfaces — useful input when the shared library picks its rendering approach.
  The proposed **Control Center** screen (the read-only dashboard plus the already-wired
  `register`/`unregister`/`request`/`setup`/`teardown` actions — each with a native
  `sg edge local *` home) is the natural convergence vehicle and the first SG/Edge screen
  to build *on* `Tui__App`. Brief: `team/comms/plans/v0.2.39__sg-edge-tui-control-center/`.
