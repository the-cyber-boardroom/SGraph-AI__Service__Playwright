# Enabling script execution on sg-playwright

## The short version

The `evaluate` step and `wait_for.function` run **user-supplied JavaScript**. They are
**deny-by-default**: a stock instance rejects *all* such JS. This is deliberate
(CLAUDE.md rules 10-11 — the service must not be a general remote-code-execution surface).

Two environment variables — **both default OFF** — are the only way to open it. When
neither is set, behaviour is identical to every prior release (deny-all).

| Env var | Effect | Use when |
|---|---|---|
| `SG_PLAYWRIGHT__JS_ALLOW_ALL` | `1`/`true`/`yes`/`on` → **bypass the allowlist entirely** (arbitrary JS on `/sequence/execute` and `/inspect`). | A **trusted, internal** instance you fully control (e.g. an onboarding/recon EC2). |
| `SG_PLAYWRIGHT__JS_ALLOWLIST_FILE` | Path to a file of **exact-match** trusted expressions. Only those strings run; everything else is still denied. | You want scripting but must keep it **auditable / deny-by-default**. |

They compose (both may be set; `allow_all` wins). **Leave both unset on customer-facing
deployments.**

> ⚠️ **Security.** `JS_ALLOW_ALL=true` turns `/sequence/execute` and `/inspect` into an
> arbitrary-JS execution surface for anyone who can reach the instance (or the `/pw` proxy
> in front of it). Only enable it where the network boundary and the callers are trusted.
> Prefer the allowlist file for anything shared.

## What each surface already allows (before you change anything)

- **`get_dom_tree`, `get_a11y_tree`, `get_text`, `get_html`, `get_content`,
  `get_console_tail`, `get_network_failures`** — run **built-in** introspection JS that is
  *not* user-supplied, so they work on a stock instance with **no** configuration. Most
  recon needs nothing here.
- **`/screenshot`'s `javascript` field** — already runs with a bypassed allowlist in an
  isolated single-shot session (scroll / dismiss-modal hook). It does *not* return the JS
  result today (see the onboarding review, Q6, for the proposed `return_value`).
- **`evaluate` step and `wait_for.function`** — the only surfaces gated by the toggles below.

## Option A — full script capability (internal instance)

### Docker
```bash
docker run --rm -p 8000:8000 \
  -e SG_PLAYWRIGHT__JS_ALLOW_ALL=true \
  -e FAST_API__AUTH__API_KEY__NAME=X-API-Key \
  -e FAST_API__AUTH__API_KEY__VALUE=<secret> \
  diniscruz/sg-playwright:<version>
```

### Verify it took
```bash
curl -s -H 'X-API-Key: <secret>' http://localhost:8000/health/capabilities | jq .js_evaluate_enabled
# → true
```
`js_evaluate_enabled` on `/health/capabilities` is the discovery signal — callers (and the
console) can check it before attempting an `evaluate`.

### Use it
```bash
curl -s -X POST http://localhost:8000/sequence/execute \
  -H 'X-API-Key: <secret>' -H 'Content-Type: application/json' \
  -d '{"steps":[
        {"action":"navigate","url":"https://example.com"},
        {"action":"evaluate","expression":"document.querySelectorAll(\"article\").length","return_type":"number"}
      ]}'
```
`wait_for.function` is gated by the same policy:
```json
{"action":"wait_for","function":"() => document.querySelector(\".results .item\") !== null"}
```

## Option B — curated allowlist (auditable, deny-by-default kept)

Write one expression per line; blank lines and `#` comments are ignored. The strings must
match **exactly** what the caller sends (whitespace included).

```text
# /opt/sg-playwright/js-allowlist.txt  — trusted recon expressions
() => document.title
document.querySelectorAll('article').length
FilterDebug(80)
```

```bash
docker run --rm -p 8000:8000 \
  -e SG_PLAYWRIGHT__JS_ALLOWLIST_FILE=/opt/allow/js-allowlist.txt \
  -v /opt/sg-playwright/js-allowlist.txt:/opt/allow/js-allowlist.txt:ro \
  -e FAST_API__AUTH__API_KEY__NAME=X-API-Key -e FAST_API__AUTH__API_KEY__VALUE=<secret> \
  diniscruz/sg-playwright:<version>
```
`/health/capabilities` → `js_evaluate_enabled: true`. An `evaluate` whose `expression`
isn't in the file returns a per-step `FAILED` with `evaluate_expression_not_allowed` — it is
**rejected, not executed**.

**Fail-closed guarantee:** a missing or unreadable allowlist file is a silent no-op (the
instance stays deny-all). A bad path can never *accidentally* open scripts, and never
crashes boot.

## On EC2 (content_proxy / `sp docker` stacks)

Set the same env vars on the container the stack launches. If you reach the service through
the `/pw` content proxy, the toggles are still read by the service itself — the proxy passes
the request body through untouched. Keep `JS_ALLOW_ALL` off on any instance a customer can
reach through `/pw`; use the allowlist file, or a separate internal-only instance, for
recon/onboarding work.

## Notes

- The `/screenshot` runner is unaffected by these toggles — it has always used its own
  bypassed allowlist in an isolated session, by design.
- These toggles are read at service `setup()` (every boot). Changing them requires a
  restart, not a redeploy.
- The stock/customer image ships with **neither** set → unchanged, locked-down behaviour.
