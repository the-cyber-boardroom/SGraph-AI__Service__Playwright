# SG/Edge TUI — operator guide

A visually-rich, keyboard-driven terminal UI over the SG/Edge control plane. It is a
**thin rendering layer over the existing primitives** — every screen reads one
normalised snapshot from a data source and never owns state. Five exploratory
screens exist today; they are standalone commands (the canonical composite app is a
later decision).

> **Honesty first.** The TUI shows only real, DNS-grounded state. Panes with no data
> yet (instance ids, cost, request throughput, vault bindings) render an explicit
> **"pending Slice 5 / Phase 2 / observability"** label — never fabricated numbers.

---

## 1. The screens

| Command | Screen | Answers |
|---|---|---|
| `sg edge tui deployment` | Deployment Reality | what is deployed right now? |
| `sg edge tui topology` | Topology | how is the edge wired? (`Enter` drills into a slug) |
| `sg edge tui compare` | Local vs Edge | what differs between the local and AWS edge? |
| `sg edge tui slug [name]` | Slug detail | what is going on with one slug? |
| `sg edge tui events` | Live Activity | what changed just now? (feed + sparklines) |
| `sg edge tui dashboard` | Dashboard | all screens in one app, tabbed (`1..6` / `←→`) |
| `sg edge tui slugs` | Slug inventory | a Textual `DataTable` (cursor/scroll/click; Enter → detail) |
| `sg edge tui docker` | Local Docker | what containers are running here (`docker ps`) |
| `sg edge tui control` | **Control Center** | action cockpit — register / request / setup / teardown |
| `sg edge tui diagnose` | — | terminal capability self-check (no TUI) |

The **Control Center** is the action-capable cockpit and the first SG/Edge screen
built on the shared `cli/tui` `Tui__App` (so it carries the Debug Panel, `d` to
toggle). It owns no logic: every action key is one call on the same backend the
`sg edge local *` commands use — `register` (`n` / `N` dormant), `unregister` (`u`),
`request` (`g`, read-only simulate), `setup` (`S`), `teardown` (`X`). Actions are
**capability-gated**: on `--target aws` they render greyed with "pending Slice 5"
and a keypress is a no-op; destructive ones (`u` / `X`) require a y/n confirm. Type a
slug in the Input (Enter = register) or select a row in the DataTable as the target.
Each previewed action also has a native home — `sg edge local request <slug>` and
`sg edge local register|unregister|teardown --dry-run`.

Each screen takes `--target local|aws` (default `local`). `local` reads the
file-backed local edge (`edge.sg-labs.local`); `aws` reads the live
`edge.sg-labs.app` DNS registry, **read-only** until live-AWS mutations land
(Slice 5).

```bash
sg edge local setup && sg edge local register alice    # make some local state
sg edge tui deployment                                  # see it, live
sg edge tui topology                                    # ↑/↓ a slug, Enter → detail
sg edge tui compare                                     # local vs the AWS edge
sg edge tui events                                      # register/unregister elsewhere & watch
```

## 2. Keybindings

**Every screen:** `q` quit · `?` help overlay (context-aware) · `t` toggle
dark/light theme · `e` export the current snapshot as an ASCII card to the clipboard
(OSC-52 — survives SSH/SSM).

**Per screen:**

| Screen | Keys |
|---|---|
| Deployment | `r` refresh |
| Topology | `↑`/`↓` (or `k`/`j`) select a slug · `Enter` drill into Slug detail · `r` refresh |
| Compare | `r` refresh |
| Slug detail | `↑`/`↓` switch slug · `r` refresh |
| Live Activity | `space` pause · `a`/`s`/`f`/`i` filter (all/slugs/fleet/issues) · `c` clear · `r` poll |

`?` shows the active screen's bindings; the footer always lists them too.

## 4. The deployment chain (SSH/SSM + `docker exec`)

The TUI is reached `laptop terminal → SSH/SSM → EC2 → docker exec -it → container`.
It survives this well **if**:

- the laptop terminal supports 24-bit truecolor + a Unicode font (iTerm2, WezTerm,
  Kitty, Windows Terminal);
- `docker exec -it` uses **both** flags (no `-t` → no TTY → dumb fallback);
- the container has a UTF-8 locale and a sane `$TERM`.

The service image (`sg_compute_specs/playwright/Dockerfile`) already sets
`LANG=C.UTF-8 LC_ALL=C.UTF-8 TERM=xterm-256color`. A **dedicated TUI image** should
additionally install the terminfo + locales:

```dockerfile
ENV LANG=C.UTF-8 LC_ALL=C.UTF-8 TERM=xterm-256color
RUN apt-get update && apt-get install -y ncurses-term locales && locale-gen C.UTF-8
```

Run `sg edge tui diagnose` inside the container to self-check `$TERM`, `$LANG`,
`tput colors`, a Unicode block test, and a truecolor probe before reporting issues.

**Graceful degradation:** when stdout is not a TTY (piped, CI, broken chain), the
screens print a static ASCII card (or, for `compare`/`slug`, a plain-text view) and
exit — so the commands are safe to pipe.

```bash
sg edge tui deployment | cat     # → static card, no Textual
```

## 5. Under the hood (for the next agent)

- **One snapshot, many views.** `tui/schemas/Schema__SG_Edge__TUI__Snapshot` is built
  by `tui/service/SG_Edge__TUI__Snapshot__Builder` from a `SG_Edge__DNS__Helper`;
  `Local_Source` and `AWS_Source` (`tui/source/`) feed it. Screens render it; they
  hold no parallel state.
- **Pure render + thin screen.** Each screen has a pure `*_markup()` render module
  (testable on 3.11, no Textual) and a thin Textual `App` subclass of
  `SG_Edge__TUI__App__Base` (which provides q/?/t/e). Logic lives in the pure layer.
- **Textual is lazy + gated.** Registering `sg edge tui` never imports Textual; view
  tests `@skipUnless` it (like the CLI suites gate on typer).
- **No mocks.** Pilot tests drive `App.run_test()` with real in-memory sources
  (local stack in a temp dir; `Route53__AWS__Client__In_Memory` for AWS).

Run the suite: `python3.12 -m pytest sg_compute_specs/sg_edge/tui/tests/`.
